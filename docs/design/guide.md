# Web 디자인 가이드

## 목적과 문서의 책임

새 도메인의 페이지를 추가해도 같은 앱처럼 읽히고 조작되게 한다. 데이터·할 일·기록을 읽고 편집하는 웹 UI가 대상이며 로그인·설정·검색·에이전트 연결 안내도 같은 기준을 따른다.

| 문서 | 소유하는 기준 |
| --- | --- |
| 이 문서 | 디자인 원칙, 접근성·반응형 기준 |
| [시각 규격](visual-spec.md) | 색·글자·간격·크기·곡률의 기본값과 변경 방법 |
| [컴포넌트와 상호작용](ui-patterns.md) | 페이지·목록·모달·폼·태그·타임라인의 구조와 동작 |

공식 shadcn 컴포넌트·Tailwind 구현과 화면 검증 상태는 해당 [GitHub issue·PR](https://github.com/kimyongin/agent-workspace-template/issues)에서 확인한다. 도메인별 브랜드는 공통 토큰에서 바꾸고, 페이지마다 별도 스타일을 만들지 않는다.

## 직접 조작하는 샘플

[디자인 샘플 사용법](samples.md)에서 HTML 샘플을 열 수 있다. 문맥별 버튼·폼 상태·표준 목록·자료 설정의 편집과 이력·편집/확인 모달을 공용 스타일과 컴포넌트로 확인한다. UI 변경 시 해당 사례도 함께 검수하고, 새 기준을 추가하면 관련 사례를 맞춘다. 원칙과 동작 계약은 위 문서가 소유하며 샘플의 예시 데이터·모의 결과는 실제 API 정책의 정본이 아니다.

## 디자인 방향과 시각 검수

기존 앱을 정돈하는 작업은 [합의한 UI·UX 정돈 방향](ui-refinement-direction.md)을 함께 적용한다. 기존 흐름 유지, 역할에 맞는 행동 배치, 편집 위치의 변경 표시, 선택적인 미리보기, 자연스러운 반응형 구성을 기준으로 한다. 해당 방향은 승인된 목표이며 현재 앱의 구현 완료를 뜻하지 않는다.

**차분하고 정교한 업무 도구. 내용을 먼저 읽고, 필요한 조작을 바로 찾는다.** 공식 shadcn의 neutral 테마·Geist와 한국어 fallback·Lucide 아이콘을 하나의 체계로 사용한다. 기존 디자인 재현보다 공식 컴포넌트의 적극적인 조합을 우선한다. 개성은 자료를 읽고 조작하는 정돈된 행과 안정된 정렬에서 만든다. 업무 화면의 실제 내용과 행동을 설계의 중심에 둔다.

에이전트가 정보 위계·밀도·글자·색·배치·조작 크기를 함께 판단한다. 사용자는 목적과 업무 의미를 결정하며 일상적인 디자인 세부 사항을 지정할 필요가 없다. 먼저 현재 화면과 해당 규격을 읽고 가장 큰 시각적 문제를 구체적으로 짚은 뒤 개선한다. 기능과 사용자 합의는 보존하고, 더 나은 표현에 기존 시각 값이 방해되면 이유를 남기고 규격·소비 화면·샘플을 함께 수정한다.

- **위계:** 첫 화면에서 현재 대상과 주된 작업이 읽혀야 한다. 제목·값·보조 정보·행동은 서로 다른 시각적 무게를 갖는다. 같은 역할의 반복은 안정시키고 중요한 차이는 분명히 한다.
- **경계:** 간격·정렬·배경으로 먼저 묶고, 외곽선은 독립 작업이나 입력 범위를 구별할 때 쓴다. 하나의 그룹을 카드·내부 박스·푸터 선으로 거듭 나누기 전에 각 경계의 역할을 확인한다. 설정의 독립 저장 섹션은 별도 카드로 유지한다.
- **밀도:** 촘촘한 작은 조작과 과한 빈 공간이 섞이지 않게 한다. 충분한 누름 영역 안에서도 아이콘은 선명하게 읽혀야 한다. 넓은 화면은 제목과 입력의 정렬 축으로 훑기 쉽게 하고, 좁은 화면은 같은 순서로 쌓는다.
- **강조:** 실행 가능한 주요 행동·현재 선택·초점에 강조색을 쓴다. 비활성 조작은 알아볼 수 있는 중립 표현으로 낮춘다. 중요한 값까지 흐리게 만들지 않는다.

규격 검사·기능 테스트와 별도로 실제 브라우저 캡처를 보고 시각 검수를 한다. 변경한 화면의 전체 구성과 주요 상태를 모바일·넓은 화면에서 확인하고, **제목/값의 위계, 정렬 축, 간격/밀도, 경계/강조, 아이콘/상태 가독성**을 대조한다. 보기 어색한 부분을 구체적으로 고친 뒤 다시 캡처한다. 테스트 통과나 수치 일치만으로 화면을 완료 처리하지 않는다. 기존 앱 정돈 작업은 별도 시안 웹을 선행하지 않고 실제 앱에서 구현→캡처→이미지 검토→수정→재캡처를 수행한다. 같은 데이터·상태·가용 폭의 변경 전후를 비교하고 직접 조작으로 펼침·편집·저장·취소·복귀도 확인한다. 이미지 검수는 동작 검증을, 동작 테스트는 이미지 검수를 대신하지 않는다. 캡처·직접 검수한 화면과 상태, 발견해 고친 문제, 실행하지 못한 범위는 해당 이슈·PR의 검수 근거에 남긴다. 사용자에게 매번 시안 승인을 요청할 필요는 없으며, 새로운 제품 의미나 합의 범위를 벗어나는 방향만 확인한다.

참고: [Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)의 제품 문맥·절제·자기 비평, [OpenAI frontend-app-builder](https://github.com/openai/plugins/blob/main/plugins/build-web-apps/skills/frontend-app-builder/SKILL.md)의 전체 구성·컨테이너 절제·실제 렌더 비교를 2026-10-15 검토했다. 이 앱에는 업무 도구의 가독성과 연속 작업에 맞게 적용하며, 원문의 이미지 생성·홍보 페이지 구성·승인 흐름을 기본 절차로 도입하지 않는다. 이 문서는 앱의 시각 품질 기준을 소유하며 개발 작업 방법은 기존 원본 스킬을 따른다.

## 업무 흐름 설계와 사용성 검수

시각 규격 준수와 사용성은 별도로 확인한다. 먼저 “상품 종류에 쿠팡 상품 번호를 연결해 자료를 등록한다”처럼 사용자의 목적·시작 상태·완료 결과를 정한다. 화면이나 API 목록을 순회한 것만으로 그 업무를 완료할 수 있다고 판단하지 않는다.

- **업무의 순서:** 필요한 선행 선택과 다음 행동을 같은 문맥에서 찾을 수 있게 한다. 저장소의 테이블·정의·연결 구조를 사용자가 먼저 배워야 진행할 수 있는지 점검한다.
- **선택과 관리:** 기존 대상을 고르는 조작과 대상을 추가·편집하는 조작을 구별한다. 드롭다운을 기본 선택으로 삼지 않고 선택지 수·비교 필요·전환 빈도를 고려한다. 단일 선택과 다중 선택을 혼동시키지 않는다. 유효한 선택지가 하나이면 불필요한 재선택을 요구하지 않되 중요한 저장값은 확인할 수 있게 한다.
- **질문과 명칭:** 현재 작업에 필요한 정보만 필요한 시점에 묻는다. 데이터 모델의 이름보다 실제 입력·결과를 나타내는 이름을 쓴다. 검증 패턴을 설정하지 않는 기능을 ‘규칙’이라고 부르는 등 기대와 실제 기능이 어긋나는지 확인한다.
- **점진적 공개:** 주된 작업을 완료하는 데 필요한 선택·저장은 보이게 두고 드문 옵션만 접는다. 핵심 동작을 숨긴 뒤 긴 설명으로 길을 안내하지 않는다. 설명 제거가 목표가 아니라 설명 없이도 이해할 수 있는 구조가 목표다.
- **완료와 복귀:** 한 대상의 편집은 같은 작업 공간에서 끝낸다. 관련 정의를 추가해야 할 때도 원래 초안·선택·초점을 보존해 돌아온다. 자동 발급이면 수동 입력을 요구하지 않는 등 선택한 방식과 다음 입력이 대응해야 한다. 실제 지원하지 않는 가져오기·연동 완료를 암시하지 않는다.
- **대표 업무 검수:** 처음 상태에서 선택→추가/입력→검토/저장→결과 확인을 직접 수행한다. 선행 설정 없음·선택 하나/여러 개·취소·실패도 확인한다. 버튼 작동·줄바꿈 검사는 업무 이해 가능성 검수를 대신하지 않는다. 실제 사용자를 대상으로 검증한 것인지 에이전트의 시나리오 검토인지 구분한다.

빈 상태는 API가 반환한 개수보다 사용자가 실제로 선택할 수 있는 후보를 기준으로 판단한다. 이미 선택한 항목·보관 항목 등을 제외한 뒤 남은 후보와 다음 페이지를 확인하고, 검색 실패를 ‘없음’으로 표시하지 않는다. 검색 결과가 없으면 같은 자리에서 조건을 풀 수 있게 한다. 선택 전환으로 숨겨진 변경·오류는 선택 목록에서도 표시하고 바로 돌아갈 수 있게 한다. 한 저장 버튼이 확정하는 변경 범위는 현재 보이는 입력과 구별해 확인한다.

[NN/g 사용성 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/)·[점진적 공개](https://www.nngroup.com/articles/progressive-disclosure/)와 GOV.UK의 [선택기](https://design-system.service.gov.uk/components/select/)·[질문 구성](https://design-system.service.gov.uk/patterns/question-pages/)을 참고했다. 공공 신청서의 기본 구조를 그대로 복제하지 않으며 반복 업무와 한 화면 편집 합의에 맞춰 적용한다. 원문 요약과 이 앱의 적용 가설은 [UX 조사 노트](ux-research.md)에서 구분한다.

사용자가 설정을 처음 만드는 흐름은 목록 조회에서 끝내지 않는다. 생성 → 첫 하위 항목 → 사용할 모델에 연결 → 실제 업무 등록까지 이어서 검수한다. 중간 저장을 허용할 때는 저장된 부분을 표시하고, 다음 단계의 취소·실패가 앞선 성공을 지우거나 반복하지 않는지 확인한다. 같은 화면의 드롭다운은 조회·선택에 사용하고, 관리 대상의 추가·편집·상태 확인은 목록에서 제공한다.

## 필터와 태그의 공통 작업 방식

조회 조건은 박스 안에서 초안으로 준비하고 맨 아래 `필터 적용`으로 함께 반영한다. 검색창은 박스 밖에서 기존 검색 방식을 유지한다. 속성 조건은 데스크탑 한 줄·모바일 두 줄의 번호 없는 같은 목록이며, 화면 폭에 따라 선택 의미나 실행 범위를 바꾸지 않는다. 모든 태그 선택은 선택 칩과 기존 확인창 계열의 검색 가능한 중앙 모달을 사용한다. 자세한 적용 시점·초안/URL·초기화·모달 복귀는 [필터와 목록](ui-patterns.md#필터와-목록)·[태그](ui-patterns.md#태그), 크기·배치는 [시각 규격](visual-spec.md#반응형과-레이아웃)을 따른다. 공통 규칙을 변경하면 실제 목록·폼·변경 확인·설정·샘플을 함께 전환한다.

## 변경별 읽기와 검수

이 문서의 [디자인 원칙](#디자인-원칙)과 [접근성·반응형 기준](#접근성과-반응형-검수)을 유지하며, 아래에서 변경에 해당하는 구역을 선택한다. 시각 값은 시각 규격, 사용자 행동은 UI 패턴의 연결된 제목부터 다음 같은 수준 제목 전까지 읽고 필요한 하위 제목을 포함한다. 작업 중 영향이 다른 구역으로 이어지면 그 구역도 읽는다. 코드 경로·컴포넌트 이름은 구현을 찾는 단서이며 동작 계약의 대체물이 아니다.

국소 변경은 [화면 완료 체크리스트](#화면-완료-체크리스트)에서 영향받는 화면·상태·조작·viewport를 선택한다. 긴 문구가 레이아웃을 바꾸거나 간격이 누름 영역·초점을 바꾸면 그 영향까지 검수한다. 공통 shell·탐색·반응형·토큰을 바꾸거나 영향 범위가 불확실하면 소비 화면과 체크리스트 범위를 넓히고, 필요한 경우 UI 패턴·시각 규격 전체를 읽는다. 브라우저 자동 검사의 실행 범위는 스펙의 누적 변경을 기준으로 [로컬 E2E 실행 기준](../development/verification.md#로컬-e2e-실행-기준)을 따른다.

## 디자인 원칙

1. **모바일에서 먼저 읽고 조작할 수 있게 한다.** 넓은 화면에서는 비교·편집 효율을 높인다. 반응형은 열·여백·줄바꿈을 바꾸며 기능이나 읽을 정보를 임의로 없애지 않는다.
2. **현재 대상과 핵심 내용을 먼저 보여준다.** 긴 기록·설명은 상세에서 읽는다. 같은 소개·합계·제목을 여러 카드에 반복하지 않는다. 빈 구획을 채우기 위한 장식이나 요약을 만들지 않는다.
3. **데이터는 반응형 키–값 그리드로 읽고 편집한다.** 키는 보조색, 값은 기본 글자색으로 구분하고 들여쓰기 없이 정렬한다. 키–값 쌍을 한 묶음으로 두어 가용 폭에 따라 가로 배치와 세로 배치를 함께 사용한다. 접힌 자료 목록은 제목 템플릿의 결과를 제공하고, 펼친 목록·보기·편집은 제목에 참여한 속성까지 같은 전체 속성을 같은 순서·위치에 제공한다. 같은 역할의 제목·라벨·필터·저장 버튼도 공통화한다.
4. **대표 행동을 분명히 한다.** 한 작업 영역에서 가장 중요한 행동 하나를 강조한다. 삭제·보기·필터·설정은 저장과 구별한다. 필수 행동을 hover·스와이프·길게 누르기에만 숨기지 않는다.
5. **상태를 정확히 알린다.** 원본 저장, 작업 접수, 처리 중, 완료, 실패를 구분한다. 검색 결과 없음·색인 지연·검색 장애도 구분한다. 색만으로 상태를 전달하지 않는다.
6. **읽기와 편집, 초안과 저장값을 구분한다.** 보기·편집은 같은 전체 정보를 유지하고 값의 수정 가능 여부와 행동만 바꾼다. 태그는 데이터 영역 마지막에 두고 보기에서 독립적으로 연결·해제하며 편집에서는 읽기 전용으로 유지한다. 읽기만으로 쓰기가 발생하지 않는다. 실패·확인 취소·화면 회전으로 초안을 잃지 않는다. 메인 목록과 연결 항목은 같은 자리에서 펼쳐 읽는다. 제목 링크로 펼치기 전부터 보기 영역을 열고, 제목 왼쪽 화살표로 미리보기를 펼치고 접는다. 편집은 보기 안에서만 시작한다. 넓은 화면에서는 오른쪽 상세 탭, 좁은 화면에서는 모달을 사용한다. 저장·취소는 같은 보기로 돌아간다. 상세 탭은 개별 닫기와 패널 숨김을 구별하며, 모달의 이전·전체 닫기는 처음 상세·목록 문맥으로 돌아간다.
7. **권한과 데이터 의미를 디자인으로 바꾸지 않는다.** 읽기 전용은 명확히 표시하고 허용되지 않은 변경 조작을 제공하지 않는다. UI 숨김은 서버 권한 검증을 대신하지 않는다. 필터 범위·날짜·단위·누락값은 업무 계약에 맞게 표시한다.

8. **설명보다 배치와 조작으로 이해되게 한다.** 중복되는 제목·라벨·선택값과 자명한 동작을 설명하는 상시 문구를 제거한다. 대상과 행동이 읽히도록 정보 순서·그룹·컨트롤을 먼저 다듬는다. 입력의 의미를 구분하는 라벨과 접근성 이름은 유지하며, 오류·처리 결과·삭제 영향 등 판단에 필요한 안내는 해당 상황과 조작 가까이에 짧게 표시한다. 구체적인 적용은 [라벨과 설명](ui-patterns.md#라벨과-설명)을 따른다.

## 화면 구조와 공통 표현

화면의 페이지·목록·상세·편집 패턴과 글자의 역할·상태는 사용자가 읽을 정보와 완료할 행동에 맞춘다. 정보 구조와 탐색 메뉴는 새 앱의 실제 기능에 맞춰 정하며 고정된 도메인 메뉴를 복제하지 않는다.

데이터 집합과 태그의 작업 범위는 [데이터 표시와 모드 일치](ui-patterns.md#데이터-표시와-모드-일치), 색·정렬·반응형 배치는 [키–값과 반응형 데이터 그리드](visual-spec.md#키값과-반응형-데이터-그리드)를 따른다. 이 기준은 구현 목표이며 문서 갱신만으로 실제 화면의 전환이 완료된 것은 아니다.

기존 공통 표현과 다른 설계가 필요하면 목적·대안·영향받는 화면·검증 방법을 티켓에 남긴다. 일반적인 방향 변화는 디자인 기준 자체를 갱신하고 실제 소비 화면과 관련 스킬·검증을 함께 맞춘다. 특정 조건에만 필요한 차이만 제한된 예외로 기록한다. 설계 방법은 [codebase-design](../../.agents/skills/codebase-design/SKILL.md), 제품·구조 결정권은 [ADR-0008](../adr/0008-document-ownership.md)을 따른다. 픽셀 조정마다 ADR을 만들 필요는 없다.

코드 배치는 [폴더 구조](template-structure.md)를 따른다.

## 접근성과 반응형 검수

다음은 템플릿 자체의 검수 기준이며 인증된 접근성 준수를 주장하는 문구가 아니다.

- 실제 HTML 제목 순서·랜드마크·label 연결을 유지한다. 버튼은 실행, 링크는 이동에 사용한다. 아이콘 조작에는 대상과 행동을 알 수 있는 이름을 붙인다.
- 키보드만으로 주요 흐름을 완료할 수 있어야 한다. 초점은 보이고 고정 영역에 가려지지 않아야 한다. 대화상자는 이름·초기 초점·초점 유지·닫기 후 복귀를 제공한다.
- 일반 텍스트 대비 4.5:1, 큰 글자와 필수 조작 경계·초점 표시 대비 3:1을 검수 목표로 삼는다. 장식용 구분선과 입력 식별에 필요한 테두리를 구분한다. 실제 합성 배경에서 확인한다.
- 조작 영역은 기본 최소 44×44 CSS px을 확보하며 서로 겹치지 않는다. 작은 아이콘과 텍스트는 실제 누름 영역을 별도로 확보한다. 목록 보기 선택기도 같은 최소 조작 영역을 유지한다.
- 200% 확대, 긴 한국어·공백 없는 문자열, 작은 화면에서 읽기 순서와 기능을 유지한다. 전역 overflow 숨김이나 글자 축소로 넘침을 가리지 않는다.
- 성공·실패·처리 상태는 텍스트로 표시하고 필요한 변경만 적절한 live region으로 알린다. 자동 갱신이 초점을 빼앗지 않게 한다. 장식 동작은 줄이고 reduced-motion 설정을 존중한다.

## 화면 완료 체크리스트

변경에 적용되는 항목을 검수하고 결과·예외·미검증 범위를 기존 티켓·PR에 기록한다. 국소 수정에 새 티켓이나 별도 체크리스트 문서를 만들 필요는 없다. 적용되지 않는 항목과 수행하지 못한 검증을 구분한다. 공통 컴포넌트 변경 시 실제 소비 화면을 함께 확인한다.

폭 목록은 새 화면·공통 레이아웃·반응형 변경의 기본 검수 범위다. 국소 수정은 영향받는 폭과 실제 규격의 전환 경계 양쪽을 선택하며, 높이·배율 조건이 있으면 함께 확인한다. 상태 항목은 바뀐 흐름이 가지는 상태에 적용하고, 공통 상태·폼·탐색 변경은 영향을 받는 모든 흐름으로 넓힌다. 검수 범위를 줄여도 위의 접근성·초안·권한·반응형 보장은 유지한다.

- [ ] 320 / 360 / 390 / 639 / 640 / 768 / 1024 / 1440px에서 관련 화면을 확인했다.
- [ ] 동일 역할의 실제 computed style이 규격과 일치하며 버튼 상속·페이지별 덮어쓰기가 없다.
- [ ] 실제 캡처에서 위계·정렬·밀도·경계·조작 가독성을 검수하고 발견한 어색함을 수정했다.
- [ ] 최초 로딩·빈 데이터·조건 결과 없음·조회 실패·긴 값·0·미확정 값·읽기 전용을 구분했다.
- [ ] 저장 중·저장 실패·비동기 처리 중/실패에서 초안과 실제 완료 여부가 정확하다.
- [ ] 목록 필터·페이지·스크롤·초점이 상세/편집 왕복 후 유지된다. 대상 삭제 시 유효한 위치로 복귀한다.
- [ ] 등록·보기·편집이 같은 shell이며 실제 레이아웃 전환 경계·본문 스크롤·고정 헤더/footer·동적 viewport를 확인했다.
- [ ] 목록·검색·선택·연결·상세가 같은 제목 템플릿 결과를 표시하고, 펼친 목록·보기·편집의 전체 속성·연결 정보·태그가 같은 순서와 위치에 있다. 키–값 쌍의 열 전환과 긴 값·많은 태그를 실제 패널 폭·배율에서 확인했다.
- [ ] 태그는 데이터 영역 마지막에 있으며 보기의 연결·해제와 편집의 읽기 전용 표시를 구분한다. 본문·속성 저장/취소가 독립적으로 확정한 태그 연결을 덮지 않는다.
- [ ] 상세의 이전·닫기와 목록·검색·연결 상세·직접 링크 복귀를 확인했다. 기본 정보·본문·관련 정보, 편집 취소·확인 취소와 삭제·저장 배치를 확인했다.
- [ ] 상단 기능과 하단 목록 구획, 본문 장식 제거, 공식 ScrollArea 또는 브라우저 기본 스크롤 영역의 실제 wheel·키보드·코드/표 가로 스크롤을 확인했다.
- [ ] 검색어 지우기와 조건 초기화, 한글 IME, 범위별 태그·기록 종류가 서버 계약과 일치한다.
- [ ] 키보드, 200% 확대, 대비, 조작 영역, 모달 닫기·확인 취소를 확인했다.
- [ ] 일반 페이지 가로 넘침이 없고 고정 탐색·액션이 본문을 가리지 않는다.
- [ ] 실기기 키보드·safe-area·스크린리더의 실제 확인 여부를 자동 검사와 구분해 기록했다.

가이드 작성, UI 구현, 자동 검사, 시각 검수, 실기기 확인은 서로 다른 완료 상태다. 수행하지 않은 항목은 남은 검증으로 기록한다.

자동 검사의 선택 범위는 [변경 영향 분류기](../../scripts/ci-impact.mjs)와 [CI](../../.github/workflows/ci.yml)가 정한다. 자동 검사로 확인한 범위와 실제 화면·기기 확인의 차이는 [검사 도구의 한계](../development/verification.md#검사-도구의-한계)에서 설명한다.
