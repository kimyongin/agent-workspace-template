# 기존 UI·UX 정돈 방향

- 합의: 2026-10-21 사용자 대화. 구체적인 화면 배치와 검수는 에이전트가 책임진다.
- 상태: 승인된 제품·디자인 방향. 문서 저장은 실제 앱 반영·사용성 검증 완료를 뜻하지 않는다.
- 책임: 이 문서는 정돈 방향과 판단 경계를 소유한다. 색·크기·접근성은 [디자인 가이드](guide.md)와 [시각 규격](visual-spec.md), 초안·저장·탐색은 [상호작용](ui-patterns.md), 권한·데이터 의미는 PRD·ADR을 따른다.

## 목표

익숙한 흐름 안에서 각 요소가 제자리에 있고, 대상·행동·변경 결과를 화면 자체로 이해할 수 있게 한다. 설명의 양이나 빈 공간을 채우는 정도를 개선의 척도로 삼지 않는다.

## 방향

1. **기존 흐름을 유지한다.** 자료 종류별 탐색, 목록 펼침, 상세 작업 영역, 별도 설정의 큰 구성을 유지한다. 전면 재설계·새 온보딩·설정 마법사를 기본 해법으로 삼지 않는다.
2. **쓰면서 확장한다.** 처음부터 자료 종류·입력 항목·관계를 완성하도록 요구하지 않는다. 필요할 때 추가하고 원래 작업의 초안·선택·위치로 돌아온다.
3. **역할이 배치를 결정한다.** 목록 전체의 행동은 목록 헤더, 개별 항목의 행동은 해당 항목, 확정 행동은 그 편집 영역에 둔다. 입력 항목 목록의 추가 버튼은 목록 제목과 같은 헤더의 오른쪽에 두는 것이 대표 사례다.
4. **대상과 변화를 직접 드러낸다.** 현재 편집 대상·적용 범위·변경 상태가 읽혀야 한다. 관계는 실제 자료 종류 이름과 사용자 업무 표현으로 나타낸다. 상시 설명문보다 배치·정렬·컨트롤의 대응을 먼저 개선한다.
5. **편집한 자리에서 판단하고 적용한다.** 추가·수정·삭제 예정 상태를 해당 입력·행에 표시한다. 보통의 편집을 별도 변경 검토 영역에서 반복하지 않는다. 일반 편집은 수정→적용으로 끝내고 데이터 손실·기존 연결 교체·값 변환처럼 판단이 필요한 경우에만 추가 확인을 제공한다.
6. **중요도에 맞게 정돈한다.** 제목과 업무 속성·현재 작업을 먼저 보여준다. 번호·출처·이력은 보조 정보로 정리한다. 중복 정보, 반복된 보기 조작, 의미 없는 빈 구획과 경계를 줄인다. 필요한 정보·행동·접근성 이름은 유지한다.
7. **반응형은 의미 있는 묶음과 정렬을 함께 설계한다.** 역할과 관계를 먼저 정하고 가용 폭에 맞게 행 구성·입력 폭·행동 묶음을 조정한다. 버튼 하나만 어색하게 다음 줄에 남거나 쓰지 않는 격자 칸이 생기지 않게 한다. 빈칸을 채우려고 버튼을 과도하게 늘리거나 관계없는 조작을 끼워 넣지 않는다. 제목과 오른쪽 행동 사이, 정보 묶음 사이의 의도된 여백은 유지한다.
8. **보조 화면은 선택적으로, 결과는 일관되게 제공한다.** ERD는 자료 설정의 마지막 `미리보기` 탭에서만 읽기 전용으로 제공한다. 편집 화면에 상시 미리보기·좌우 ERD 패널·인라인 자료 입력 미리보기를 두지 않는다. 적용한 결과는 관련 목록·상세·연결·권한 기반 행동에 일관되게 반영한다.

9. **같은 역할은 같은 구조로 표현한다.** 목록·상세·보기·편집·모달을 화면마다 새로 디자인하지 않는다. 행의 정보·행동·펼침 위치, 키–값, 변경 표시와 빈 상태를 공통 패턴으로 정의하고 같은 컴포넌트로 구현한다. 기능과 의미가 다른 예외는 이유를 명시한다.
10. **정보의 계층과 화면의 계층을 일치시킨다.** 변경 이력은 선택한 자료 종류에 속한 형제 섹션이며 입력 항목 목록의 하위 내용으로 넣지 않는다. 목록 안의 보기·편집 내용을 다시 카드·박스로 감싸는 대신 같은 정렬 축과 여백으로 이어준다. 선·면·외곽선을 같은 경계에 중복하지 않는다.
11. **읽는 방식과 비어 있는 방식도 통일한다.** 개별 데이터 표시는 왼쪽 키·오른쪽 값을 기본으로 하며 데이터 아이콘은 필요한 경우 키 쪽에만 둔다. 연결·작성 흐름의 빈 관련 자료 영역은 동일한 상태 표현과 소속 헤더의 행동으로 다음 조작을 알려준다. 자세한 예외와 상태 구분은 [공통 화면 패턴](ui-patterns.md#공통-화면-패턴)을 따른다.
12. **접기는 목적이 있을 때만 제공한다.** 유일한 주 작업을 불필요하게 숨기지 않는다. 여러 독립 섹션이나 긴 보조 내용을 선택적으로 읽는 등 실제 이점이 있을 때 사용하며 선택값을 바꾸는 드롭다운과 구별한다. 기록 자동 완성의 단일 주 편집 영역은 기본적으로 펼쳐 제공한다.

## 시안의 해석과 개선 범위

사용자가 별도로 지적하지 않은 시안은 대체로 마음에 드는 출발점이다. 해당 화면의 좋은 구조는 보존하면서 공통 방향에 맞게 다듬는다. 언급하지 않았다는 이유로 세부 표현이 모두 확정됐다고 보거나, 전체 화면을 다시 설계할 필요가 있다고 보지 않는다. 피드백은 특정 스크린샷의 부품만 고치는 지시가 아니라 같은 역할의 모든 소비 화면에 적용할 방향이다.

생성 이미지는 방향 탐색 자료이며 정보 계층·기능·정렬의 정본이 아니다. 이미지의 이상한 행이나 잘못 중첩된 이력을 실제 앱 버그로 단정하지 않고 현재 앱·코드와 대조한다. 실제 앱을 직접 수정하고 공통 컴포넌트로 렌더링한 화면을 캡처해 검수한다. 별도 웹 프로토타입을 선행 단계로 요구하지 않는다. 서로 독립적으로 생성한 이미지만으로 화면 간 일관성을 검증하지 않는다.

## 적용 순서

1. 기존 지침과 이번 합의를 대조해 충돌을 해소하고 화면 역할별 구조·행동·반응형·예외 기준을 정한다.
2. 기존 조사와 캡처를 재사용해 실제 화면을 공통 패턴·컴포넌트에 대응시킨다. 시안 오류·실제 결함·방향 개선을 구분하고 구현 스펙과 작업 범위를 정한다.
3. 실제 앱의 공통 부품과 대표 소비 화면부터 수정한다. 별도 프로토타입을 만들지 않으며 기존 [디자인 샘플](samples.md)은 공통 부품 변경에 따른 불일치를 함께 정리한다.
4. 수정한 앱의 데스크톱·모바일·중간 폭과 긴 값·빈 값·변경·오류·읽기 전용을 실제 캡처한다. 이미지를 직접 보고 위계·정렬·밀도·경계·행동 소속을 판단해 수정하고 재캡처한다. 대표 화면에서 기준을 검증한 뒤 공통 패턴 단위로 소비 화면에 확장한다.
5. 실제 업무 흐름과 저장 후 갱신을 검증하고 같은 대상·데이터·상태·화면 폭의 실제 변경 전후 캡처로 비교한다. 시각·행동·데이터 검증을 구분해 완료 근거를 남긴다.

## 구현 판단의 경계

- **저장 범위:** 각 버튼이 확정하는 대상과 변경 묶음을 분명히 한다. 독립 저장 계약을 유지하고 다른 자료 종류·관계의 변경을 묵시적으로 함께 저장하지 않는다.
- **변경 표시:** 색과 함께 작은 상태 표식을 사용한다. 원래 값을 모든 행에 상시 복제하지 않는다. 삭제 예정 항목은 적용 전 되돌릴 수 있고 적용 후에는 확인된 저장 상태로 갱신한다.
- **검증·위험 확인:** 검증과 영향 분석은 유지한다. 오류는 해당 입력에서 보완하고 초안을 보존한다. 별도 검토 UI 제거를 서버의 버전 검사·권한 검사·멱등성·원자적 저장·변환 보장 제거로 해석하지 않는다. 긴 변환 분석과 복구는 필요한 상황에서만 제공한다.
- **변경 메모:** 기존 기록 계약에 필요한 메모·태그 입력을 누락하지 않는다. 실행 확인이 필요한 화면은 대상과 실제 전후 변경을 먼저 보여주며 일반 입력을 중복 편집하게 하지 않는다.
- **미리보기:** 현재 초안을 반영하고 미적용 상태를 구분한다. 미리보기 전환·복귀는 저장·초안 폐기·다른 대상의 암묵적 편집을 일으키지 않는다. 종류·관계는 각 편집 화면에서 따로 관리한다.
- **너비·밀도:** 의미 있는 순서와 최소 입력·조작 크기를 우선한다. 관련 행동 묶음이 통째로 다음 줄로 가는 것은 허용한다. 데이터 속성은 모바일에서도 좌(키)–우(값)를 우선하며 실제 가용 폭·긴 라벨·글자 확대 때문에 읽기 어려울 때만 위(키)–아래(값)로 바꾼다. 세로 배치는 키를 값보다 작은 보조 글자로 두고 키와 값·속성 사이 간격을 컴팩트하게 유지한다. 모바일이라는 이유만으로 일괄 세로 전환하거나 좌우 배치를 고수하려고 글자를 축소하지 않는다. 편집·읽기 전환과 오류·긴 값·동적 버튼 수에서도 정렬을 확인한다.
- **정확한 결과:** 저장 성공과 후속 조회 실패를 구분한다. 관련 화면의 오래된 상태, 읽기 불가와 실제 빈 결과, 미적용 초안과 게시 정의를 혼동시키지 않는다.

## 화면별 검수 질문

1. 무엇을 보고 편집하는지, 각 행동의 대상과 적용 범위가 설명 없이 읽히는가?
2. 같은 정보·변경을 두 번 읽거나 불필요한 단계를 거치는가?
3. 행동이 의미상 소속된 헤더·행·편집 영역에 있는가?
4. 빈칸을 억지로 채우거나 관련 요소 하나만 다음 줄에 남기는가?
5. 320·360·390·640·768·1024·1440px 및 실제 줄바꿈 경계에서 읽기 순서·초안·조작성이 유지되는가?
6. 긴 이름·오류·빈 결과·읽기 전용·삭제 예정·저장 실패에서도 같은 기준이 유지되는가?
7. 적용 후 다른 목록·상세에도 확인된 결과가 일치하는가?

화면 조사·캡처·시안은 실행 증거이며 제품 기준과 구분한다. 이미지 시안만으로 서버 검증·반응형 구현·접근성 검증이 완료됐다고 주장하지 않는다.
