## 1. 목적: 출처를 보존하면서 같은 업무로 관리한다

이 앱은 여러 외부 플랫폼의 자료를 공통 업무 구조와 화면으로 모아 관리한다. 쿠팡·네이버·지마켓·옥션의 상품은 **상품**, 각 마켓의 주문은 **주문** 자료로 관리한다. 플랫폼마다 새로운 자료 종류를 만들거나 원본의 모든 필드를 그대로 복사해야 하는 구조는 피한다.

사용자가 합의한 관리 단위는 **한 마켓의 등록 건이 한 자료 행**이라는 것이다. 같은 운동화가 쿠팡과 네이버에 판매돼도 서로 다른 상품이다. 각 행은 자신의 마켓 번호·판매가·상태를 유지한다. 함께 관리할 필요가 있으면 **상품 그룹** 자료를 만들고 개별 상품들을 연결한다.

```text
상품 그룹 · 운동화 · 앱 / 자동 발급 번호
  ↔ 상품 · 운동화 · 쿠팡 / 00123 · 89,000원
  ↔ 상품 · 운동화 · 네이버 / 00123 · 87,000원

주문 · 쿠팡 / 00123
  ↔ 상품 · 쿠팡 / 00123
```

상품과 주문의 번호가 우연히 같아도 별개다. 관계는 사용자가 대상을 선택해 연결하며 번호 일치만으로 자동 연결하지 않는다. 상품 그룹은 별도 자료 종류다. 스키마 상속·값 자동 전파·마켓 상품 자동 병합을 도입하지 않는다.

이 앱은 일반 자료·할 일·기록도 계속 다룬다. 이번 목적을 이유로 모든 기존 모델을 상품/주문으로 바꾸지는 않는다.

## 2. 이미 합의한 조건과 이번 추천

| 사용자와 합의한 조건 | 설계에 주는 제약 |
| --- | --- |
| 마켓 등록 건마다 별도 행 | 한 행에 여러 마켓 번호를 배열로 넣지 않음 |
| 그룹은 별도 상위 자료 | 기존 양방향 연결을 재사용 |
| 추가 내부 자료 UUID를 강제하지 않음 | 외부 번호 또는 앱 발급 번호로 대상을 찾음 |
| 상품 번호는 등록 후 불변 | 번호·발급처·종류를 일반 편집에서 변경하지 않음 |
| 외부 번호가 없으면 앱에서 자동 발급 | 자체 재료·그룹도 같은 등록 흐름 사용 |
| 번호는 문자열 | 앞자리 0·대소문자·큰 숫자 문자열 보존 |
| 하나의 식별자가 여러 발급처를 지원 | 종류 설정은 여러 발급처, 실제 자료 값은 한 쌍 |
| 최대 길이를 별도 설정하지 않음 | 사용자 설정을 없애되 공통 서버 한도는 유지 |
| 가져오기는 아직 구현하지 않음 | API 인증·호출·매핑·동기화 화면을 만들지 않음 |

**이번 추천은 필수 자료 식별자를 일반 입력 항목 밖으로 분리하는 것이다.** 자료 설정에 `식별자` 섹션을 두고 번호의 화면 이름과 지원 발급처를 정한다. 상품명·가격·옵션 같은 업무 속성은 기존 `입력 항목`에서 관리한다.

앞선 시안은 입력 항목 하나를 대표 식별자로 지정했다. 유연하지만 모든 자료에 반드시 있어야 하고 불변이어야 하는 식별자를 삭제·타입 변경·스키마 마이그레이션 대상에 섞게 된다. 별도 섹션은 이런 충돌을 줄이고 현행 고정 식별자 저장 구조도 재사용한다. 이 선택은 설계안에 대한 사용자의 진행 지시로 승인되었다. 구현 완료 여부는 별도 검증한다.

## 3. 사용자가 이해해야 할 개념은 세 가지다

- **자료 종류:** 상품·주문·재료·상품 그룹처럼 무엇을 관리하는지.
- **발급처:** 그 번호를 발급하거나 관리하는 곳. 보통 쿠팡·네이버·앱처럼 보인다.
- **번호:** 그 발급처 안에서 해당 자료를 찾는 문자열.

화면에는 `대표 식별자`, `PK`, `복합키`, `내부 속성키`를 반복해서 노출하지 않는다. 자료 설정의 섹션 이름은 `식별자`, 상품 등록 폼에서는 설정한 `상품 번호`, 주문 등록 폼에서는 `주문 번호`를 사용한다. 같은 개념을 업무 문맥에 맞춰 표시하는 것이다.

**식별자 규칙**은 발급처가 관리하는 번호의 의미와 발급 방식이다. 쿠팡의 상품 ID와 주문 번호는 같은 규칙이 아니다. 자료 종류는 지원하는 발급처마다 정확히 한 규칙을 연결한다. 상품에서 쿠팡 상품 ID를 사용하고 주문에서 쿠팡 주문 번호를 사용한다. 앱 규칙은 기존 자동 발급을 사용한다.

한 종류에 같은 발급처의 상품 ID와 판매자 ID를 모두 대표 번호로 허용하지 않는다. 무엇을 한 건으로 보는지가 모호해지기 때문이다. 종류와 발급처의 번호 의미는 참조가 생긴 뒤 교체할 수 없다. 표시 이름은 바꿀 수 있다.

추가 업무 번호인 판매자 번호·물류 코드 등은 이번 단계에서는 문자열 입력 항목으로 두는 것을 추천한다. 모든 번호를 새 복합 데이터 형식으로 만들 필요는 없다. 별도 발급처를 가진 보조 식별자나 보조 번호로 조회하는 요구가 실제로 생기면 그 범위를 따로 설계한다. 앞선 범용 ‘식별자 속성’ 구상 전체를 구현하는 것보다 이번 목적에 필요한 기반이 작다.

## 4. 저장: 단일 참조 키를 쓰되 구성 정보도 보관한다

### 추천 구조

자료의 논리적 식별은 **소유자 + 자료 종류 + 발급처 + 원본 번호**다. 앱과 연결 테이블에서는 이 구성을 정해진 방식으로 결합한 **하나의 문자열 ID**를 사용한다. 별도 무작위 자료 UUID를 추가하지 않는다.

```text
id = 발급처의 고정 코드 : 자료 종류의 고정 키 : 원본 번호

설명을 위한 예:
coupang:product:00123
naver:product:00123
coupang:order:00123
```

`product`와 `order`는 읽기 쉬운 예다. 실제 구현에서는 현재 자료 종류의 불변 설정 ID를 활용한다. 사용자에게 타입 코드 입력란을 추가하지 않으며, 종류 이름을 상품에서 판매 상품으로 바꿔도 ID는 바뀌지 않는다. 발급처 코드도 표시 이름과 구분한다. 설정 객체의 ID는 자료마다 숨겨진 새 번호를 만든다는 뜻이 아니다.

| 자료 테이블의 값 | 역할 |
| --- | --- |
| `owner_id` | 소유자 격리 |
| `entity_type_id` | 자료 종류와 입력 스키마 |
| `source` | 발급처의 고정 코드 |
| `external_id` | 원본 번호 문자열, 앱 발급 번호도 여기에 저장 |
| `id` | 위 값을 결합한 단일 참조 키 |
| `properties` | 버전이 있는 JSON Schema로 검증하는 업무 속성 |
| 기존 버전·삭제·시각 정보 | 충돌 검사, 삭제/복원, 변경 기록 |

식별자를 `properties`에도 중복 저장하지 않는다. 화면 이름 `상품 번호`는 종류 설정의 표시값이다. 저장 시 클라이언트가 임의의 ID와 구성값을 따로 보내 불일치시키지 못하도록 서버가 계산하고 DB도 일치 조건을 보장한다.

SQL의 기본키는 현재처럼 **`(owner_id, id)`** 형태를 유지하는 것을 추천한다. 앱에서 단일 문자열로 참조한다는 것과 다중 사용자 DB가 한 컬럼만 PK로 사용한다는 것은 다르다. id의 구성값 일치 제약과 기본키로 종류+발급처+번호의 유일성도 보장한다. 같은 사실을 보장하는 UNIQUE 인덱스를 관행적으로 하나 더 만들지 않는다. 실제 migration에서는 기존 중복 인덱스의 사용처와 조회 경로를 함께 확인한다. 종류별 목록 등 필요한 보조 인덱스는 실제 쿼리에 맞춘다.

### 왜 이 절충인가

| 대안 | 판단 |
| --- | --- |
| 발급처:번호만 결합 | 상품/주문 번호가 같은 경우 충돌하므로 종류의 구분이 필요 |
| 구성 컬럼을 모두 FK로 전달 | 가능하지만 모든 연결·기록·MCP 참조가 여러 값으로 길어짐 |
| 문자열 ID만 저장하고 나머지를 매번 분해 | 화면·종류별 필터·발급처별 조회가 오히려 복잡해짐 |
| 임의 속성을 PK로 지정 | 스키마 변화와 자료의 고정 정체성이 얽힘 |
| 별도 내부 UUID | 이번 사용자의 의도와 맞지 않음 |
| 단일 파생 ID + 구성 컬럼 | 기존 참조 구조를 유지하면서 조회와 표시도 단순하므로 추천 |

구분자는 고정된 앞 두 구간에만 사용한다. 고정 코드/종류 키에는 `:`가 없고 원본 번호는 그 이후의 전체 문자열로 보존한다. `A:B`, `/`, `%`, `_`, 한글을 포함한 원본 번호를 전체 `split(':')`나 숫자 변환으로 훼손하지 않는다. URL에는 정상적인 경로 인코딩을 적용한다. 식별자 생성·분해·유효성 검증은 HTTP/MCP가 공유하는 한 계약으로 둔다.

### 검색과 인덱스

번호로 한 자료를 찾는 기본 동작은 `=` 정확 조회다. 발급처·자료 종류 필터는 구성 컬럼을 사용한다. 사용자의 번호 입력을 `LIKE` 패턴으로 그대로 전달하지 않는다. prefix 검색이 필요하면 `%`/`_`를 이스케이프하고 인덱스를 검토한다.

PostgreSQL B-tree는 고정된 앞부분의 `LIKE 'foo%'`에 사용될 수 있지만 항상 사용되는 것은 아니다. C가 아닌 locale에서는 적절한 operator class가 필요할 수 있다. 이 때문에 ‘prefix LIKE가 가능하다’는 사실만으로 구성 컬럼을 없애지 않는다. 이번에는 문서를 확인했으며 실제 실행 계획이나 성능 벤치마크를 측정하지 않았다. [인덱스 유형](https://www.postgresql.org/docs/17/indexes-types.html), [operator class](https://www.postgresql.org/docs/17/indexes-opclass.html).

## 5. 설정 화면: 일상 설정과 재사용 설정을 분리한다

우측 상단 설정 메뉴로 다섯 화면을 전환한다. 각 화면 안에서는 동일 대상의 편집을 끝낸다. 처음부터 여러 페이지를 오가며 자료 종류 하나를 완성하도록 만들지 않는다.

| 화면 | 내용 | 저장 단위 |
| --- | --- | --- |
| 기본 설정 | 프로필, 날짜와 시각, 화면 표시·메뉴 바로가기 | 섹션별 저장 |
| 자료 설정 | 종류 선택 → 기본 정보 → 식별자 → 입력 항목 → 변경 이력 | 기본/식별자는 섹션 저장, 입력 구조는 검토·적용 |
| 태그 설정 | 자료·할 일·기록 선택, 태그 목록 | 태그 추가/편집 단위 |
| 기록 설정 | 상품·주문·재료·할 일 선택, 액션, 메모 템플릿·변수, 기록 태그 | 대상·액션별 저장 |
| 발급처 설정 | 발급처 선택, 기본 정보, 식별자 규칙과 발급 방식 | 기본 정보/규칙 단위 |

모바일 하단 메뉴는 프로필 아이콘과 사용자가 고른 업무 바로가기를 유지한다. 상품·주문 등 자료 종류의 이름과 아이콘도 바로가기로 고를 수 있다. 많은 종류를 자동으로 모두 넣지 않는다. 공간이 부족하면 우선순위가 낮은 항목을 프로필 메뉴에서 진입하도록 빼고, 설정 화면의 위쪽 메뉴는 설정 범주 전환에만 사용한다. 일상 업무 탐색과 설정 탐색의 위치를 섞지 않는다.

### 자료 설정 예

```text
자료 설정                                      ≡
[ 상품                                  ▾ ] [종류 추가]

기본 정보                                      ›
식별자                                         ∨
  이름                 [상품 번호]
  기본 발급처          [쿠팡                 ▾]
  지원 발급처
  ✓ 쿠팡               [상품 ID              ▾]
  ✓ 네이버             [상품 ID              ▾]
  ✓ 지마켓             [상품 ID              ▾]
  ✓ 옥션               [상품 ID              ▾]
  ✓ 앱                  자동 발급
                                  [취소] [저장]
입력 항목                                      ›
변경 이력                                      ›
```

시안의 화면 문구는 한국어이며 `식별자` 섹션의 라벨·컨트롤을 최소화한다. 선택한 자료 종류를 아래 라벨로 반복하지 않는다. `문자열`, `필수`, `중복 불가`, `등록 후 불변`을 상시 설명 목록으로 나열하지 않는다. 실제 편집 화면은 번호를 읽기 전용으로 표시하고, 잘못된 등록이나 충돌 때만 필요한 이유를 가까이에 표시한다.

규칙이 하나뿐이면 이름을 텍스트로 표시하고 불필요한 드롭다운을 만들지 않는다. 여러 규칙이 있는 경우에만 선택기를 사용한다. 지원 발급처 추가는 기존 번호를 바꾸지 않는다. 참조 중인 연결 규칙은 제거/교체할 수 없고 새 등록에 사용하지 않도록 중지할 수 있다. 종류에는 활성 지원 발급처를 하나 이상 유지하고 기본 발급처는 그 목록 안에서만 선택한다. 새 등록은 기본값을 제안하되 사용자가 입력한 발급처/번호를 다른 발급처로 조용히 바꾸지 않는다.

발급처를 추가·수정할 때는 현재 편집을 유지한 채 편집 모달을 연다. 확인이 필요하면 편집 모달 위에 작은 중앙 확인 모달과 dim을 올린다. 확인 취소는 입력 중인 편집 모달로 복귀한다. 설정 메뉴 전환·자료 종류 전환 시 미저장 변경을 조용히 버리지 않는다.

모바일은 한 열, 넓은 화면은 적절한 행 배치를 쓰되 같은 작업 순서와 기능을 유지한다. 본문 작은 조작의 실제 누름 영역은 44px을 확보하고 입력 옆의 종류 추가는 입력 높이에 맞춘다. 목록의 세로 표시선은 펼친 전체 행 높이를 따라가고 열기/접기는 항상 오른쪽 끝이다. 필드와 설명을 여러 박스로 중첩하지 않는다.

## 6. 사용자는 어떻게 쓰는가

### 처음 설정하는 사람

새 종류는 앱 자동 발급과 이름 입력 항목을 기본으로 만들어 바로 사용할 수 있게 한다. 외부 자료를 관리할 때만 마켓 발급처와 추가 항목을 설정한다. 처음부터 모든 설정을 끝내야 등록할 수 있게 만들지 않는다.

1. 자료 설정에서 상품을 만든다. 기본 정보에서 이름과 아이콘을 고른다.
2. 식별자에서 이름을 상품 번호로 정하고 쿠팡·네이버·앱 등을 연결한다. 쿠팡에는 상품 ID 규칙을 고른다. 기본 발급처를 정한다.
3. 입력 항목에 상품명·판매가·상태 등을 만든다. 상품명을 자료 이름으로 선택한다. 번호를 다시 일반 항목으로 만들지 않는다.
4. 입력 항목의 변경 검토를 누르면 같은 화면의 변경 이력에 변경안이 추가된다. 그 안에서 읽기 전용 항목 정의와 차이·검토 결과를 보고 적용하거나 폐기한다.
5. 기록 설정에서 상품을 선택하고 수정 액션의 문구·기록 태그를 정한다. 미설정 값은 고정 기본 문구를 사용한다. 공통 문구 설정을 다시 만들지 않는다.

발급처의 규칙을 처음 만들 필요가 있으면 상품 설정의 지원 발급처 추가에서 모달로 만든다. 이후 다른 종류에서도 같은 발급처를 사용할 수 있다. 전역 발급처 설정은 여러 자료 종류에 영향을 주는 유지관리 때 쓴다. 한 번의 상품 설정을 위해 강제로 왕복하지 않는다.

### 쿠팡 상품을 등록하는 사람

1. 상품 목록에서 작성을 연다.
2. 상품 번호의 발급처를 쿠팡으로 고르고 원본 번호 `00123`을 입력한다.
3. 상품명·가격 등은 직접 입력하고 저장한다. 이번 단계에는 정보를 가져오는 동작이 없다.
4. 등록 후 번호와 발급처는 잠금 상태다. 상품명·가격은 수정할 수 있다.
5. 같은 쿠팡 상품을 다시 만들려고 하면 기존 자료를 안내한다. 자동으로 덮어쓰거나 새 행을 만들지 않는다. 삭제된 자료면 복원 동작을 제안한다.

### 자체 재료나 상품 그룹을 등록하는 사람

발급처가 앱이면 번호 입력을 요구하지 않는다. 저장과 함께 번호를 발급하며 저장 이후 표시한다. 앱만 지원하는 종류는 발급처 선택기까지 생략한다. ‘내부 번호를 따로 생성’하는 흐름이 아니라 해당 자료의 정식 번호를 받는 것이다.

### 같은 상품의 여러 마켓 판매를 묶는 사람

쿠팡 상품과 네이버 상품을 각각 등록한다. 상품 그룹에서 운동화를 만들고 상품 연결을 눌러 두 자료를 선택한다. 그룹 안에서 각 상품의 발급처·번호·가격을 확인한다. 연결 해제는 상품 삭제가 아니며 그룹 삭제도 상품 삭제를 전파하지 않는다. 그룹에서 마켓 가격을 일괄 수정하거나 동기화하지 않는다.

그룹은 별도 계층 시스템이 아니므로 여러 그룹 연결을 금지하는 제약은 도입하지 않는다. 실제 업무에서 한 상품이 반드시 그룹 하나에만 속해야 한다면 그때 별도 계약을 만든다.

### 주문을 관리하는 사람

주문 자료에서 쿠팡의 주문 번호 규칙을 연결한다. 쿠팡/00123 상품과 쿠팡/00123 주문을 동시에 보관하고 두 자료를 연결할 수 있다.

다만 양방향 링크만으로 주문 당시 수량·옵션·가격을 표현할 수는 없다. 이런 값이 필요하면 주문 항목 자료를 추가해 주문과 상품에 각각 연결하고 수량·당시 가격을 항목에 보관한다. 상품의 현재 가격을 주문의 과거 가격으로 해석하지 않는다. 주문 처리·정산·재고 로직은 이번 기반 범위가 아니다.

## 7. 실패와 흔하지 않은 경우

아래는 **설계 시나리오 검토**이며 실제 DB/API 테스트 결과가 아니다.

| 시나리오 | 기대 정책 | 이유·구현 조건 |
| --- | --- | --- |
| 쿠팡 상품00123과 네이버 상품00123 | 서로 다른 행 | 발급처 구분 |
| 쿠팡 상품00123과 쿠팡 주문00123 | 서로 다른 행 | 종류 구분 |
| 같은 소유자가 같은 종류·발급처·번호 동시 등록 | 하나만 확정, 다른 요청은 충돌 안내 | DB 유일성·트랜잭션, 사전 조회만으로 불충분 |
| 다른 소유자가 같은 번호 등록 | 각자 가능, 서로 조회 불가 | 소유자 포함 키·권한 검사 |
| 00123과123, abc와ABC | 서로 다른 번호 | 문자열 원형·대소문자 보존 |
| 큰 숫자 모양의 번호 | 정밀도 손실 없이 문자열 보존 | HTTP/MCP도 문자열만 허용 |
| 번호 A:B/한글_% | 원형 보존, 참조·URL 왕복 가능 | 고정 두 구간만 파싱, URL 인코딩, 검색 패턴 이스케이프 |
| 번호 앞뒤 공백 | 앞뒤 공백은 입력 오류로 안내, 공백만이면 거부 | 무음 trim을 피함; HTTP/MCP/웹 동일 검증 |
| 번호 내부 공백/제어문자 | 내부 일반 공백 보존, 제어문자 거부 | 임의 대소문자/Unicode 정규화 없음 |
| 앱 번호 발급 후 응답 유실 | 같은 요청 키로 같은 확정 번호와 결과 반환 | 매번 재발급하지 않음 |
| 외부 등록 응답 유실 후 재시도 | 원래 성공 재현 | 새로운 생성 요청과 재시도 구분 |
| 두 탭에서 설정 수정 | 낡은 버전의 저장을 충돌로 알리고 초안 보존 | 최신 저장을 조용히 덮어쓰지 않음 |
| 발급처/종류 이름 변경 | 기존 자료 ID·연결 유지 | 표시 이름을 키에 쓰지 않음 |
| 기존 자료 번호·발급처·종류 변경 요청 | 웹/MCP/서버 모두 거부 | 읽기 전용 UI만으로 막지 않음 |
| 참조 있는 규칙 교체/삭제 | 막고 사용 중지로 유도 | 상품 ID를 판매자 ID로 재해석하지 않음 |
| 발급처 사용 중지 | 새 등록 제한, 기존 조회·일반 편집·복원 가능 | 과거 자료가 고아가 되지 않음 |
| 삭제된 번호 재등록 | 기존 삭제 자료 안내, 명시적 복원 | 같은 정체성을 다른 대상으로 재사용하지 않음 |
| 그룹 또는 그룹 연결 삭제 | 원본 상품은 유지 | 링크와 대상의 수명 분리 |
| 한 마켓 번호가 판매자 계정마다 중복 | 같은 발급처로 섞지 않음 | 계정 단위 번호라면 발급처 구분에 계정 범위가 필요 |
| 작성 중 선택한 발급처가 중지됨 | 저장을 거부하고 원래 입력을 보존 | 앱 발급이나 다른 마켓 번호로 자동 대체하지 않음 |
| 자료 설정 전환/확인 취소 | 초안 유지 또는 명시적 폐기 | 화면 이동 최소화와 데이터 손실 방지 |

잘못 입력한 번호를 바로잡는 경우에는 기존 자료를 삭제하고 올바른 번호로 새로 등록한다. 새 행은 다른 정체성이고 예전 기록/연결을 조용히 새 번호로 바꾸지 않는다. 번호 변경 도구나 자동 연결 이관은 이번 범위에 넣지 않는다.

공백 처리는 새 추천 정책이며 현행 계약과 구분한다. 저장된 원본 번호를 조회할 때는 무단 trim하지 않는다. 구현 전에는 전체 호출자와 기존 번호의 호환성을 확인해야 한다.

## 8. 실제 외부 연동 전에 확인해야 할 것

**마켓 이름은 곧 번호의 유일성 범위라는 뜻이 아니다.** 상품 번호가 플랫폼 전체에서 유일한지, 판매자 계정 안에서만 유일한지, 옵션/판매 단위 번호인지 확인해야 한다. 쿠팡 API에서 사용할 구체적인 번호 규칙은 아직 공식 문서로 조사하거나 확정하지 않았다. 시안의 ‘상품 ID’는 예시다.

번호가 계정 범위라면 발급처를 ‘쿠팡 · 판매자 A’, ‘쿠팡 · 판매자 B’처럼 구분할 수 있도록 번호 문맥을 확정한 뒤 연동한다. 지금 계정 인증·비밀값·토큰 관리 화면이나 플랫폼 어댑터 프레임워크를 만들지는 않는다. 기존 자료가 생긴 뒤 하나의 발급처 의미를 조용히 변경해서 충돌을 해결하지 않는다.

가져오기를 구현할 때는 새 자료인지 같은 자료 갱신인지, 수동 수정값을 외부 값이 덮어쓸지, 응답 필드와 공통 스키마를 어떻게 맞출지, 외부 삭제를 어떻게 반영할지를 별도 스펙으로 정한다. 이번 기반은 식별과 연결을 안정시키며 그 정책들을 미리 구현하지 않는다.

## 9. API·MCP·테이블의 책임

HTTP와 MCP가 동일한 핵심 유스케이스·식별자 검증을 사용한다. 웹에서만 불변을 검사하거나 MCP에서만 다른 문자열을 생성하지 않는다. 발급처별 복제된 CRUD 도구를 만들지 않는다.

| 기능 | 계약 방향 |
| --- | --- |
| 자료 생성 | 종류 + 발급처 + 문자열 번호 + properties. 앱 자동 발급은 번호 생략. 불필요한 임의 id 입력을 받지 않음 |
| 자료 응답 | 단일 id와 종류·발급처·번호를 함께 반환, 화면용 이름은 별도 |
| 자료 정확 조회 | 응답의 id로 조회. 또는 종류·발급처·번호를 지정해 서버에서 같은 id를 생성 |
| 자료 목록 | 종류·발급처 필터와 기존 속성 필터, 페이지네이션 유지 |
| 자료 수정 | 업무 속성·태그 등의 허용값만 수정. identity/rekey 입력 제거 |
| 삭제/복원 | 같은 id로 기존 삭제 상태와 연결·이력을 이어감 |
| 자료 연결 | 기존 두 id와 양방향 매핑 사용. 셀프 연결/중복/다른 소유자 연결 거부 |
| 자료 종류 설정 | 입력 schema와 식별자 표시·지원 규칙 설정을 구분, 버전/충돌 검사 |
| 발급처 설정 | 재사용 가능한 발급처·규칙 CRUD와 사용 중지, 참조된 규칙의 의미 변경 제한 |
| 기록 템플릿 | 자료 종류 및 기존 업무 모델·액션별 설정; 미설정은 고정 상수 |

자료 종류 조회는 활성 JSON Schema, 자료 이름/표시 설정, 번호 라벨, 지원 발급처와 연결 규칙·발급 방식·기본값을 함께 제공한다. MCP 에이전트도 이를 읽고 같은 자료 생성 계약을 사용한다. 속성 라벨만 추측해서 prop_n을 임의로 만들거나 번호를 숫자로 전달하게 하지 않는다.

공개 계약 이름과 필드는 공유 contracts·HTTP/MCP 진입점에서 확인한다. 발급처 `/entity-issuers`, 번호 규칙 `/entity-issuers/:code/rules`와 `/entity-identifier-rules/:rule_id`, 종류별 설정 `/entity-types/:type_id/identity`가 저장 책임을 나눈다. 전역 `entity_identity` 설정과 구 rekey 입력은 제거한다. 식별자 라벨/번호/발급처는 기존 공통 변수와 목록·필터·연결·기록·검색 표현에서 직접 사용할 수 있어야 한다. `properties`에 없는 번호를 동적 렌더러가 누락하지 않게 공통 식별 정보와 업무 속성을 함께 구성한다.

테이블은 기존 `entities`, `entity_types`, `entity_relation_links`와 schema/version 구조를 재사용한다. 발급처와 그 규칙의 재사용 정의, 종류별 지원 규칙 연결은 별도 설정 저장 책임으로 둔다. 이 정의를 매 자료 행이나 여러 설정 위치에 복제하지 않는다. 재사용 관계와 참조 제약이 필요하므로 설정용 정규화 테이블을 추천하되 최종 컬럼/인덱스 DDL은 구현 스펙에서 정한다.

기본 식별자 하나를 일반 props에서 빼므로 JSON Schema primitive 지원을 구조화된 식별자 객체까지 일괄 확장할 필요가 없다. 실제 데이터 검증은 고정 식별 계약 + 종류별 버전 JSON Schema 검증으로 나눈다. 일반 속성 마이그레이션은 그대로 필요하고 식별자를 직접 바꾸지 않는다.

## 10. 현재 코드와의 차이, 진행 범위

현행 [ADR-0016](../adr/0016-entity-source-identity-and-restoration.md) 및 `entity-identity.ts`는 **발급처:번호**를 자료 ID로 사용한다. `entities`의 기본키는 `(owner_id,id)`, 발급처/번호 컬럼과 일치 제약이 이미 있다. 추가 내부 UUID가 없다는 방향과 문자열 결합은 새로운 발명이 아니다.

이번 추천의 주요 변화는 종류의 식별 범위 추가, 등록 후 identity 변경 금지, 재사용 발급처 규칙, 종류별 식별자 설정, 설정 탐색과 기록 설정 재배치다. 현행 `rekey_entity`와 자료 수정 계약은 아직 이 새 불변 정책을 구현하지 않는다. 현재 유일성 범위가 종류를 포함하지 않으므로 같은 소유자의 동일 발급처·번호 상품과 주문을 동시에 등록할 수 없다.

기존 자료를 그대로 보존해야만 한다고 가정해 큰 이관을 시작하지 않는다. 사용자는 기존 테스트 자료 삭제를 허용했다. 다만 구현 시점의 실제 자료와 연결·기록·요청 receipt·검색 상태를 확인하고 전환 범위를 정해야 한다. 이번 설계 작업에서는 삭제나 이관을 실행하지 않았다.

### 구현을 나눌 때의 순서

1. 승인된 identity 불변/범위 변경은 [ADR-0021](../adr/0021-type-scoped-immutable-identity.md)에 기록한다.
2. 서버·DB에서 발급처/종류별 규칙·불변 identity·정확 조회·동시 등록/재시도·삭제/복원을 먼저 함께 맞춘다.
3. HTTP/MCP와 모든 참조 소비자·제품 스킬을 전환한다. 구 rekey 경로와 미사용 계약을 정리한다.
4. 설정 다섯 화면, 작성/편집, 목록·검색·연결·기록 렌더링을 공통 계약에 맞춘다.
5. 격리 로컬 환경에서 DB/HTTP/MCP와 모바일/데스크톱 실제 E2E를 검증한다. 독립 리뷰와 필요한 CI 뒤 별도 사용자 배포 지시를 따른다.

각 단계는 실행 가능한 상태로 나누며 식별자 계약이 신구로 섞인 상태를 배포하지 않는다. 외부 가져오기·동기화·일괄 편집·주문/재고 엔진·범용 보조 식별자 엔진은 포함하지 않는다.

## 11. 이번 결과물과 검증의 한계

이 문서와 HTML 시안은 목적에 맞는 설계를 확인하기 위한 결과다. 시안은 기본·자료·태그·기록·발급처 설정, 상품 작성/편집, 상품 그룹 화면을 같은 스타일로 비교한다. 목록의 실제 데이터, 설정 저장, schema 적용, 외부 API는 구현하지 않았다.

현행 코드와 식별/관계/스키마 계약을 대조했고 위의 충돌·재시도·수명·계정 범위 사례를 검토했다. 시안 검수와 구현 검증 증거는 [#426](https://github.com/kimyongin/agent-workspace-template/issues/426)과 연결된 PR에 남긴다. 시안 버튼 동작 확인은 운영 기능 테스트나 DB/HTTP/MCP/E2E 통과를 뜻하지 않는다.

문구는 [디자인 가이드](guide.md)와 [라벨과 설명](ui-patterns.md#라벨과-설명)을 따른다. 중복된 선택값·자명한 설명을 제거하되 오류·삭제 영향·필수 판단·접근성 이름은 보존한다.
