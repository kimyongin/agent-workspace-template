# 업무 흐름 중심 UX 기준 조사

2026-10-15 조사 노트. 공식 원문을 비교한 제안이며, 현재 디자인 정본이나 제품 계약을 변경하는 문서는 아니다. 적용 여부는 [디자인 가이드](guide.md)와 [UI 패턴](ui-patterns.md)의 소유 기준에 맞춰 결정한다.

## 현재 문제에 대한 판단

색·크기·간격의 일관성과 사용자가 일을 완료할 수 있는지는 별도로 검수해야 한다. 현 가이드에는 위계·상태·초안 보존이 있지만, 어떤 질문을 언제 묻고 어떤 선택기를 사용할지, 설정 간 선후 관계가 실제 업무에 맞는지 판단하는 기준은 더 구체화할 필요가 있다. 아래 적용안은 이 앱에 대한 해석이며 원문의 직접 지시가 아니다.

## 원문과 적용안을 구분한 비교

| 1차 출처 | 원문 권고 요약 | 이 앱에 적용할 제안 |
| --- | --- | --- |
| [NN/g: 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | 사용자에게 익숙한 개념을 사용하고, 기억보다 보이는 선택을 돕고, 상태를 알려 오류를 예방한다. | 발급처 설정을 DB 필드의 나열로 설계하지 않는다. “쿠팡 상품 번호를 사용하는 상품 종류를 설정한다” 같은 실제 업무에서 출발해 필요한 선택과 완료 상태를 배치한다. |
| [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | 자주 필요한 기능을 먼저 노출하고 부가 기능을 요청할 때 공개한다. 다음 단계의 진입점과 이름은 명확해야 한다. | 발급처·번호 방식의 선택을 기본 흐름으로 두고 드물게 바꾸는 규칙만 펼침에 둔다. 완료에 반드시 필요한 발급처 연결이나 저장을 “추가 설정”에 숨기지 않는다. |
| [GOV.UK: Select](https://design-system.service.gov.uk/components/select/) | 공공 서비스에서 select 사용을 신중히 판단한다. 먼저 선택지를 줄이거나 다른 컨트롤을 검토한다. 기존 설정의 기본 선택과 질문의 응답 유도는 구분한다. | “드롭다운 금지”로 옮기지 않는다. 적은 발급 방식을 비교해야 하면 라디오, 종류를 전환하는 기존 컨텍스트 선택이면 select를 검토한다. 선택인지 텍스트 입력인지 외형과 조작에서 분명히 한다. |
| [GOV.UK: Radios](https://design-system.service.gov.uk/components/radios/) | 하나를 고르는 질문에 라디오를 사용한다. 질문과 선택을 그룹화하고, 여러 선택이 필요하면 체크박스를 사용한다. | 발급처 하나를 고르는 자료 등록과, 허용 발급처 여러 개를 정하는 자료 종류 설정을 서로 다른 선택 의미로 표현한다. 개수에 따른 임의의 고정 임계값은 만들지 않는다. |
| [GOV.UK: Question pages](https://design-system.service.gov.uk/patterns/question-pages/) | 필요한 정보만 묻고 같은 답을 반복 입력시키지 않는다. 한 질문부터 시작하되 반복 업무에서는 관련 질문을 함께 묶을 수 있다. | 관련 설정을 한 화면에서 편집한다는 기존 합의를 유지한다. 발급처 관리와 자료 종류의 연결은 다른 대상이므로 관리 진입점은 구별하되, 현재 편집 중인 초안·선택·복귀 위치를 보존한다. |

GOV.UK의 공공 신청서용 한 질문·한 페이지 기본값을 이 업무 앱에 그대로 적용하지 않는다. 같은 원문은 반복 작업이 많은 내부 서비스의 관련 질문 묶음을 인정한다. 이 앱은 한 대상의 편집 흐름을 유지하면서 섹션별 저장·조건부 펼침으로 복잡도를 낮추는 편이 기존 합의와 맞는다.

## 발급처 기능에 적용할 작업 흐름 가설

다음은 구현 확인과 사용성 검증이 필요한 설계 가설이다. 서버 계약 변경을 뜻하지 않는다.

1. **발급처 관리:** 쿠팡 같은 발급처를 만들거나 선택하고, 그 발급처가 지원할 번호 방식을 관리한다. 현재 어디에서 사용 중인지 확인할 수 있어야 한다.
2. **자료 종류 설정:** 상품 종류에서 허용할 발급처와 번호 방식을 연결한다. 새 발급처가 필요하면 현재 편집 문맥 안에서 등록하고 돌아올 수 있어야 한다.
3. **자료 등록:** 허용된 발급처·방식만 선택한다. 직접 입력이면 번호 입력, 자동 발급이면 입력 대신 발급 예정 상태를 보여준다. 선택지가 하나면 불필요한 선택을 요구하지 않는다.
4. **저장 후 확인:** 발급처와 번호를 묶어 식별 정보로 읽을 수 있게 한다. 변경 불가 정책은 편집 컨트롤과 맞추고, 목록의 모든 행에 기술 정보를 같은 비중으로 반복하지 않는다.

외부 API 가져오기는 이번 기반 작업 범위 밖이다. 가져오기 버튼이나 연동 완료처럼 오해할 표현을 제공하지 않는다. 불변성·중복 판정·삭제 영향 등 제품 결정이 필요한 항목은 설명 삭제로 감추지 않는다.

## 정본에 추가할 만한 검수 질문

- 첫 화면에서 현재 대상과 다음 행동을 알 수 있는가? 선택·입력·실행 컨트롤이 서로 구별되는가?
- 각 입력값은 지금 작업을 완료하는 데 필요한가? 이미 선택한 내용이나 저장된 값을 다시 묻고 있지 않은가?
- 선행 선택 전에 무관한 입력을 요구하지 않는가? 자동 발급과 직접 입력의 차이가 화면에 반영되는가?
- 기본 작업은 바로 보이고 드문 설정만 펼침에 있는가? 핵심 기능이 과도하게 숨겨져 있지 않은가?
- 저장되는 대상과 범위가 분명한가? 연결 대상 추가·취소 후 원래 초안과 작업 위치로 돌아오는가?
- 처음 사용하는 사람이 문서 설명 없이 대표 시나리오를 완료할 수 있는가? 운영자 관점의 모든 필드 노출만 검사한 것은 아닌가?

대표 시나리오는 앱 자동 번호로 자료 등록, 쿠팡 번호 직접 입력, 발급처가 없는 상태에서 신규 연결, 여러 종류가 같은 발급처 사용, 중복 번호·사용 중 삭제·저장 실패 후 복구를 포함한다. 기능 자동 검증과 별도로 행동 순서·선택의 이해 가능성을 살핀다.

## frontend 디자인 스킬과의 관계

이 절은 위 UX 근거에 따른 프로젝트 판단이다. 기존 가이드가 참고한 frontend 스킬의 레이아웃·타이포그래피·시각 비평은 도움이 되지만, 이 앱의 발급처·식별자 업무 의미와 저장 범위를 대신 결정하지 않는다. 스킬 추가만으로 완료하지 않고 **대표 작업 정의 → 입력·선택·저장 흐름 설계 → 렌더 검수 → 처음 사용자 시나리오 검수**를 함께 수행해야 한다.

조사 범위는 위 5개 공식 원문이다. 실사용자 조사나 실제 기기 사용성 검증을 수행했다는 뜻은 아니다.
