# 에이전트와 일하는 방법

이 문서는 사람이 개발 에이전트(Codex, Claude Code)에게 어떻게 일을 시키는지 안내한다. 처음 쓰는 사람도 이 순서만 따르면 된다. 에이전트가 따르는 상세 규칙은 [개발과 검증 방법](workflow.md)에 있다. 처음 보는 용어는 [용어집](../glossary.md)에서 찾는다.

## 1. 역할: 사람은 "무엇을, 왜", 에이전트는 "어떻게"

| 누가 | 무엇을 소유하나 | 하는 일 |
| --- | --- | --- |
| 사람 | PRD(제품 요구사항), ADR(아키텍처 결정) | 만들 것과 중요한 결정을 정하고 승인한다. 배포를 지시한다 |
| 에이전트 | 티켓, 구현, 테스트, 리뷰, 가이드, 스킬 | 정해진 방향 안에서 계획하고 만들고 검증하고 머지한다 |

[티켓](../glossary.md#일하는-방식)은 작업 지시서, [가이드](../glossary.md#일하는-방식)는 일하는 방법을 정리한 문서, 스킬은 에이전트가 읽는 작업 지침이다. 에이전트는 작업 중 PRD·ADR을 벗어나야 하면 멈추고 묻는다. 그 외에는 끝까지 진행한다. 근거는 [ADR-0008](../adr/0008-document-ownership.md)이다.

- **PRD:** [docs/product/concept.md](../product/concept.md). 어떤 앱을 왜 만드는지, 어떤 기능이 필수인지.
- **ADR:** [docs/adr/](../adr/README.md). 기술 스택처럼 되돌리기 비싼 결정과 그 이유.

## 2. 시작하기

| 에이전트 | 스킬 호출 | 모델 바꾸기 |
| --- | --- | --- |
| Codex | `$develop-agent-app 요청 내용` | `/model` |
| Claude Code | `/develop-agent-app 요청 내용` | 앱의 모델 선택 메뉴 또는 `/model` |

스킬 이름을 붙이지 않고 그냥 요청해도 저장소의 AGENTS.md(Claude Code는 CLAUDE.md)가 같은 규칙을 읽게 한다. 새 독립 작업은 새 세션(앞의 대화를 모르는 새 대화)에서 시작하는 것이 좋다. 진행 중인 작업의 역할과 결과는 티켓으로 이어받는다.

## 3. 기본 흐름

```text
정리해봐 ─→ (PRD·ADR 영향 있음) ─→ PRD 반영해 / ADR 초안 만들어 ─→ [사람 승인]
   │
   └─→ (영향 없음) ─→ 티켓 만들어 ─→ 티켓 진행해 ─→ [리뷰(에이전트가 띄운 새 서브 에이전트)] ─→ 에이전트가 머지
                                                                        │
                                                              배포해 ←──┘ [사람 지시]
```

| 단계 | 이렇게 말하면 된다 | 에이전트가 하는 일 | 사람이 할 일 |
| --- | --- | --- | --- |
| 1. 정리 | `정리해봐: <하고 싶은 것>` | 내용을 정리하고 PRD·ADR에 영향이 있는지 알려 준다 | 결과를 읽는다 |
| 2. 결정 | `PRD 반영해` / `ADR 초안 만들어` | PRD·ADR 변경 [PR](../glossary.md#코드를-바꾸고-내보내는-과정)(검토 요청)을 만든다 | PR을 읽고 승인한다 |
| 3. 계획 | `티켓 만들어` | [티켓 양식](../tickets/README.md)에 맞춰 목표·관련 PRD/ADR·PR 분할 계획·검증 방법을 적는다 | 없음 |
| 4. 구현 | `티켓 진행해` | 본 세션이 작은 기능으로 나눠 새 서브세션에 구현·검증을 맡기고 통합한다 | 없음 |
| 5. 리뷰 | 말할 필요 없음 | 구현 맥락이 없는 새 세션에서 정확한 PR head를 검토하고, 원래 구현 세션이 발견 사항을 반영한다 | 없음. 에이전트가 서브세션을 띄울 수 없다고 알리면 새 세션에서 `PR #N 리뷰해줘`. 다른 에이전트의 교차 리뷰를 원하면 그 에이전트에게 `PR #N 교차 리뷰해줘` |
| 6. 머지 | 말할 필요 없음 | [머지 조건](workflow.md#머지)(리뷰·자동 검사 통과 등)을 충족하면 원본 코드에 합친다([머지](../glossary.md#코드를-바꾸고-내보내는-과정)). 실제 서비스 반영은 아니다 | 없음 |
| 7. 배포 | `배포해 (환경)` | 올릴 곳과 검사를 통과한 버전을 확인하고 실제 서비스에 올린다 | 명령이 곧 승인이다 |

"푸시해"(GitHub에 올리기)는 따로 말하지 않아도 된다. 에이전트가 PR을 올리고 [머지 조건](workflow.md#머지)이 맞으면 머지한다.

사람과 본 세션이 함께 설계하고 결정한다. 구현 세션은 구현·테스트·문제 조사·수정·재검증까지 맡고 본 세션은 배정·통합 조정·증거 확인·머지·결과 설명을 맡는다. 여러 결과의 통합 테스트도 담당 서브세션에 맡길 수 있다. 본 세션의 직접 작업 예외와 역할은 [세션 배정과 인계](workflow.md#세션-배정과-인계)를 따른다. 새 세션은 이전 대화의 결정을 놓칠 수 있고 긴 작업 중에는 대화가 압축될 수 있으므로, 티켓에 승인 범위·계약·검증을 남긴다. 기술 리뷰 이견의 재현·해결과 실제 사람 결정은 [리뷰](workflow.md#리뷰)를 따른다.

서브세션이 보내는 진행·문제·결과 보고는 본 세션에서 전달받는다. 사용자 보고에는 `[구현 서브세션]`, `[리뷰 서브세션]`, `[통합 서브세션]`, `[메인]` 등 실행 주체를 표시하고, 전달된 결과와 본 세션의 증거 확인·직접 실행을 구분한다. 상세는 [세션 운영 브리핑](workflow.md#세션-운영-브리핑)에 있다.

## 4. 사람이 개입하는 네 가지 경우

1. **PRD·ADR PR 승인:** PR 맨 위의 "사람이 결정할 것"을 읽고 GitHub에서 승인하거나 에이전트에게 `승인, 머지해`라고 한다.
2. **에이전트가 멈추고 물을 때:** "ADR-0003과 다르게 해야 합니다. 이유는…"처럼 묻는다. 승인하면 에이전트가 ADR을 갱신하고 이어서 진행한다. 거절하면 기존 방향으로 다시 계획한다.
3. **교차 리뷰를 원할 때:** 리뷰는 에이전트가 새 서브 에이전트로 알아서 한다. 다른 에이전트의 시각이 필요하면(예: Claude가 만든 PR을 Codex에게) 직접 요청한다([리뷰 규칙](workflow.md#리뷰)).
4. **실행 지시:** 운영 배포(실제 서비스에 올리기), 운영 DB(실제 사용자 데이터베이스) 변경, 비용이 드는 서비스 생성, 비밀값(API 키 같은 접속 정보) 교체, 데이터 복원은 사람이 직접 지시한다. 지시하면 CLI로 할 수 있는 일은 에이전트가 하고, 사람에게는 웹 콘솔에서만 되는 단계와 비밀값 입력만 부탁한다([배포 방법](../deployment/release.md#최초-설치)).

## 5. 요청 예시

**새 기능을 만들 때**

```text
정리해봐: 기록에 사진을 첨부하고 싶어
→ 에이전트: "PRD에서 첨부는 요구가 있을 때 별도 PRD로 추가하는 범위입니다. PRD 변경이 필요합니다."
PRD 반영해
→ PR 승인
티켓 만들어
티켓 진행해
→ (에이전트가 PR마다 새 서브 에이전트로 리뷰하고 반영한 뒤 머지)
배포해 운영
```

**PRD·ADR과 관계없는 작은 일**

```text
목록 화면 빈 상태 문구가 어색해. 티켓 만들고 끝까지 진행해
```

**버그**

```text
할 일 완료 후 웹에 결과가 안 보여. 원인 찾고 고쳐줘
```

**이어서 하기(새 세션)**

```text
최신 main 확인하고 Template-02 T02-1 이어서 진행해줘
```

## 6. 모델 고르기

단계보다 작업의 성격으로 모델을 고르고 추론 강도를 따로 고른다. 일반 구현·일반 리뷰는 균형 모델의 medium으로 시작한다. 본 세션이 난이도·위험·실패 근거에 따라 배정을 조정하며 사람에게 매번 모델 변경을 요구하지 않는다. 등급·강도·상향/하향·갱신의 상세 규칙은 [개발 방법의 단일 정책](workflow.md#모델과-추론-강도-선택갱신)에 있다.

현재 모델과 지원 강도는 [선택표](agent-models.json)에서 관리한다. 개발하는 날 첫 작업에서 실제 목록과 새 후보를 조회하고 그날 결과를 재사용하는 규칙은 [공통 정책](workflow.md#모델과-추론-강도-선택갱신)을 따른다. 같은 모델의 high/xhigh(extra-high)도 독립적으로 선택하므로 고성능 모델을 택했다는 이유로 최대 강도를 쓰지 않는다. 본 대화·서브세션·새 세션에서 실제 모델과 강도가 적용됐는지 확인하며 계정/클라이언트가 달라지면 다시 검증한다. 모델 이름을 영구 고정하거나 검증하지 않은 신규 모델을 자동 채택하지 않는다. 재개 때 모델·강도를 바꾸는 실제 경로와 새 세션 인계는 [배정 확인 도구와 클라이언트별 연결](agent-model-execution.md)을 따른다.

본 세션은 서브세션 배정·중요한 변화·결과 인계 때 작업 목적, 모델과 추론 강도 각각의 선택 이유, 결과·미확인·다음 판단을 짧은 세션별 표로 알려 준다. 실제 실행 정보가 보이지 않으면 명시 배정과 미확인을 구분하므로, 표를 보고 계속 진행할지·범위를 바꿀지 판단할 수 있다. 일반 배정은 매번 승인을 기다리지 않는다. 세션 작업 완료 뒤에도 리뷰·CI·머지가 남을 수 있으며 자세한 근거는 티켓에 있다([운영 브리핑](workflow.md#세션-운영-브리핑)).

## 7. 이럴 때는

| 상황 | 이렇게 한다 |
| --- | --- |
| PR이 너무 커서 읽기 어렵다 | `이 PR을 작은 PR로 나눠줘` |
| 방향이 잘못된 것 같다 | `멈추고 지금까지 한 것과 남은 것을 정리해줘` 후 다시 결정 |
| 에이전트가 같은 실패를 반복한다 | `원인과 두 번의 수정 결과를 확인하고 모델·추론 강도를 각각 조정해줘`([선택 정책](workflow.md#모델과-추론-강도-선택갱신)) |
| 어디까지 했는지 모르겠다 | `티켓 진행 상태 정리해줘` (티켓의 진행 기록 표를 본다) |
| 기다리는 세션의 작업과 모델 선택을 알고 싶다 | `세션별 작업·모델·추론 강도 선택 이유와 확인 범위, 다음 판단을 보고해줘` |
| PRD·ADR을 바꾸고 싶다 | `정리해봐`부터 시작한다. 직접 고쳐도 되지만 관련 티켓에 영향이 있는지 에이전트에게 확인시킨다 |
