# 개발과 검증 방법

## 에이전트에게 위임하기

사람이 에이전트에게 일을 시키는 방법(명령 흐름·예시·모델 선택)은 [에이전트와 일하는 방법](working-with-agents.md)에 있다. 이 문서는 에이전트가 따르는 작업·검증 규칙이다.

저장소의 [develop-agent-app 스킬](../../.agents/skills/develop-agent-app/SKILL.md)은 설계·구현·리뷰·배포·운영의 공통 진입점이다. 문서를 복사하지 않고 요청에 필요한 정본으로 안내한다. 개발 스킬과 앱 사용자를 위한 제품 플러그인 스킬은 별개다.

Codex는 `$develop-agent-app`, Claude Code는 `/develop-agent-app`으로 호출한다. Codex는 `.agents/skills/`의 정본을, Claude Code는 `.claude/skills/develop-agent-app/`의 연결 파일을 거쳐 같은 정본을 읽는다. 지침 진입은 Codex가 AGENTS.md, Claude Code가 AGENTS.md를 가져오는 CLAUDE.md다. 새 스킬의 자동 발견 여부는 해당 클라이언트/세션에서 확인한다. 자동 발견이 없으면 AGENTS.md에 연결된 SKILL.md를 직접 읽도록 요청하면 된다. 전역 설치는 필요하지 않으며 이 스킬은 저장소의 docs와 함께 사용한다.

두 에이전트를 함께 쓸 때의 규칙은 [AGENTS.md](../../AGENTS.md)를 따른다. 동시 작업은 branch나 worktree를 나누고 단계 인계는 티켓의 상태·검증 기록으로 한다. 개발 에이전트는 하나만 써도 되며, 리뷰 방법은 아래 [리뷰](#리뷰)를 따른다.

예시 요청(Codex 기준, Claude Code는 `$` 대신 `/`):

- `$develop-agent-app 고객 관리 기능의 시나리오와 HTTP/MCP 계약을 설계해줘.`
- `$develop-agent-app 확정한 첫 기능 티켓을 구현하고 관련 검증을 수행해줘.`
- `$develop-agent-app 현재 변경의 권한·데이터 일관성과 플러그인 호환성을 리뷰해줘.`
- `$develop-agent-app 검증한 revision의 운영 배포를 준비하고 남은 조건을 정리해줘.`
- `$develop-agent-app 검색 작업이 지연되는 원인을 운영 로그와 큐 상태로 조사해줘.`

설계·준비·조사는 해당 범위의 결과로 끝내며, 실제 구현·배포·복구를 요청하면 그 범위에서 수행한다. 초기 런타임·CI가 아직 없으면 스킬은 존재하지 않는 명령의 성공을 보고하지 않고 필요한 구현/검증 인계를 남긴다.

## 작업의 출발점

[PRD](../product/concept.md), 관련 [ADR](../adr/README.md), [코드 설계 원칙](../architecture/principles.md)을 읽고 구체적인 사용자 시나리오 하나를 선택한다. 관련 티켓에는 변경 데이터, 유지할 불변 조건, HTTP/MCP 기능, 필요한 화면과 완료 조건을 적는다. 미정인 업무·권한·저장 계약은 구현 전에 확정한다. 티켓 파일의 이름·상태·양식은 [티켓 작성 규칙](../tickets/README.md)을 따른다.

설계는 검토 가능한 문서와 구현 인계로 마친다. 구현 시작은 명시적으로 구분한다. 제안·확정·구현·검증·배포 상태를 혼동하지 않는다.

웹 화면 설계·수정 전에는 [디자인 가이드](../design/guide.md)와 그에 연결된 시각 규격·상호작용을 읽는다. 티켓에 소비할 공통 패턴과 상태, 예외, viewport·키보드·초안 보존 검증을 명시한다. 공통 UI 변경은 실제 소비 화면을 함께 검사하고 여러 화면에 영향을 주면 전체 브라우저 E2E를 수행한다.

## 구현과 지침을 함께 발전시키기

이 저장소는 도메인 앱을 시작하는 템플릿이다. 문서의 소유와 변경 권한은 [ADR-0008](../adr/0008-document-ownership.md)을 따른다. PRD·ADR은 사람이 소유하고, 티켓·구현·가이드·스킬은 에이전트가 소유한다. 가이드는 에이전트가 일관되게 작업하기 위한 수단이며 구현에서 얻은 판단을 다시 반영해 발전시킨다.

변경할 때는 관련 PRD·ADR과 가이드·스킬을 함께 확인한다. 충돌이 있으면 다음과 같이 처리한다.

| 판단 | 처리 |
| --- | --- |
| 기준이 적절하고 구현이 잘못됨 | 구현을 기준에 맞게 수정하고 재발을 확인할 검증 보완 |
| 가이드·스킬의 방법을 바꾸는 것이 적절함 | 에이전트가 담당 가이드와 관련 스킬·구현·테스트를 같은 PR에서 갱신 |
| PRD·ADR의 범위·결정을 벗어나야 함 | 작업을 멈추고 이유·대안·영향을 담은 PRD 변경안 또는 ADR 초안(상태 `제안`)으로 사람의 승인을 받음. 승인 전에는 이탈하는 구현을 머지하지 않음 |
| 특정 조건에서만 다른 동작이 필요함 | 적용 범위·이유·유지할 공통 기준·재검토 조건을 예외로 기록. PRD·ADR과 충돌하면 위 행을 따름 |

어느 쪽인지 애매하면 ADR-0008의 분류 기준(제품 의미→PRD, 되돌리기 비싼 결정→ADR, 방법→가이드)으로 판단한다. 같은 예외가 여러 곳에서 반복되면 예외를 쌓지 않고 기준 자체를 재검토한다.

기존 문장을 남긴 채 상충하는 최신 규칙을 덧붙이지 않는다. 적용되지 않는 예시·링크·스킬 지침은 수정하거나 제거하고 과거 검증 기록은 당시의 증거로 구분한다.

완료 기준은 변경 위치 하나가 동작하는 데 그치지 않는다. 영향받는 공통 코드·웹/HTTP·MCP/제품 스킬·문서·검증이 같은 의미를 갖는지 확인한다. 관련 없는 영역까지 일괄 수정할 필요는 없다. 단계적으로 옮겨야 하면 임시 차이·남은 소비자·담당 작업·종료 조건을 명시하고 전환 완료로 보고하지 않는다.

## 변경 단위와 PR·리뷰

### 작게 나누기

- 티켓의 각 단계는 시작할 때 PR 분할 계획을 티켓에 먼저 적는다. PR 하나에는 실제로 동작하는 기능 한 조각 또는 결정 하나만 담는다.
- PR 크기는 lockfile·자동 생성 파일을 빼고 약 400줄, 30분 안에 리뷰할 수 있는 정도를 기준으로 한다. 넘으면 PR 설명에 이유를 적거나 나눈다.
- 되돌리기 비싼 선택이 구현 전에 필요하면(기술 검증 결과, 공개 계약, schema 정본 등) 먼저 짧은 PR이나 티켓 메모로 확정한다. PRD·ADR에 해당하면 위 승인 절차를 따른다.
- 앞 PR의 코드나 문서에 실제로 의존하는 PR만 앞 PR의 브랜치 위에 쌓는다. 앞 PR이 바뀌면 뒤 PR을 다시 맞춘다. 티켓 기록 표의 몇 줄처럼 작은 충돌만 예상되면 쌓지 말고 각자 `main`에서 브랜치를 만든 뒤, 나중에 머지하는 PR에서 충돌을 해결한다.
- 쌓은 PR은 아래부터 머지한다. 아래 PR을 머지하기 전에 바로 위 PR의 base를 `main`으로 바꾼다(`gh pr edit <위 PR> --base main`). base 브랜치가 먼저 지워지면 GitHub가 위 PR을 닫는다. squash 머지 뒤에는 위 PR에 아래 PR의 원래 커밋이 남아 충돌하므로, 위 PR 브랜치에서 자기 커밋만 `main` 위로 옮기고(`git rebase --onto origin/main <아래 PR의 머지 전 head>`) 강제 푸시(`--force-with-lease`)한 뒤 머지한다. 아래 PR의 머지 전 head는 `gh pr view <아래 PR> --json headRefOid`로 확인한다.

### 브랜치와 PR

- `main`에 직접 푸시하지 않는다. 작업마다 브랜치를 만들고 PR을 연다. 브랜치 이름은 `<종류>/<짧은-설명>`(예: `feat/task-complete`, `docs/adr-0009`)으로 한다.
- PR 설명은 [PR 템플릿](../../.github/pull_request_template.md)을 따른다. 관련 티켓·PRD/ADR, 변경 내용, 검증 명령과 결과, 검증하지 못한 항목, 리뷰어가 볼 부분을 적는다.
- 커밋 메시지는 `feat:`·`fix:`·`docs:`·`refactor:`·`test:`·`chore:` 접두어를 쓴다. 머지는 squash를 기본으로 한다.
- 두 에이전트는 같은 브랜치를 동시에 수정하지 않는다.

### 리뷰

- 모든 PR은 머지 전에 리뷰를 받는다. 리뷰어는 구현한 작업 맥락과 분리되어야 한다. 구현한 에이전트가 PR을 올린 뒤 이전 대화 맥락이 없는 새 서브 에이전트를 띄워 리뷰를 맡긴다. 사람이 따로 요청하지 않아도 매 PR에 한다. 서브 에이전트를 띄울 수 없는 환경이면 머지하지 말고, 사람에게 새 세션에서 `PR #N 리뷰해줘`를 요청해 달라고 알린다.
- 리뷰어에게는 PR 번호·diff·관련 티켓·PRD/ADR·지침의 위치만 넘긴다. 구현 과정의 설명이나 "문제없다"는 판단을 함께 넘기지 않는다. 리뷰 결과는 PR 코멘트로 남긴다.
- 다른 개발 에이전트(예: Claude Code가 만든 PR을 Codex가)의 교차 리뷰는 사람이 요청할 때만 한다.
- 리뷰어는 결함과 함께 PRD·ADR 이탈 여부를 확인한다. 점검 기준은 해당 가이드를 따른다: HTTP/MCP 동등성·데이터 수명·실패와 재시도(이 문서의 기능 계약), 권한·입력·비신뢰 콘텐츠([보안 가이드](../security/guide.md)), 화면([디자인 가이드](../design/guide.md)), 검색([검색 가이드](../architecture/search.md)), 플러그인([배포 방법](../deployment/release.md)).
- 리뷰 결론은 셋 중 하나로 남긴다: `머지 가능`, `수정 필요`(발견 사항과 근거), `사람 승인 필요`(PRD·ADR 변경 또는 이탈).
- 작성자는 발견 사항을 반영하거나 반영하지 않는 이유를 답한다. 의견이 맞서면 결론을 `사람 승인 필요`로 올린다.

### 머지

머지·리뷰 조건의 정본은 이 절과 위 "리뷰" 절이다. 에이전트의 머지 권한은 [ADR-0010](../adr/0010-merge-authority.md)이 정하고, 다른 문서는 이 절을 링크한다. 다음을 모두 만족하면 에이전트가 머지한다.

- PRD·ADR을 바꾸지 않고 벗어나지도 않는다.
- 자동 검사(CI)가 통과했다. `main`은 CI의 `check`·`integration` job을 필수 상태 검사로 걸어 두므로, 실패했거나 실행되지 않은 PR은 관리자도 머지할 수 없다. 검사를 건너뛰거나 보호를 잠시 풀어 머지하지 않는다.
- 구현한 세션과 분리된 리뷰의 결론이 `머지 가능`이다.
- 필수 검증의 증거 또는 검증하지 못한 이유가 티켓에 기록되어 있다.

필수 검사는 PR 브랜치가 최신 `main`을 포함할 것도 요구한다(strict). 뒤처진 PR은 `main`을 반영해 CI를 다시 통과시킨 뒤 머지한다. 쌓은 PR은 위 "작게 나누기"의 rebase 절차가 이 조건을 함께 맞춘다. CI 파일이 없는 브랜치(필수 검사 등록 이전에 갈라진 브랜치 등)는 검사가 생기지 않아 머지할 수 없으므로 `main`을 반영해 CI가 실행되게 한다.

CI의 job 이름을 바꾸거나 job을 추가·삭제하면 같은 PR에서 필수 검사 목록도 바꾼다. 필수 검사 변경은 저장소 관리자 권한이 필요하며 사람이 승인한 뒤 에이전트가 GitHub API로 바꾸거나 사람이 설정한다. 바꾼 뒤 보호 설정 조회 결과를 해당 티켓에 남긴다. 새 프로젝트의 같은 설정은 [Template-02](../tickets/template-02-implementation-base.md) T02-6의 초기화 절차에 넣는다.

PRD·ADR을 바꾸는 PR은 사람이 승인한다. 머지는 배포가 아니다. 운영 배포·운영 DB 적용·비용이 드는 작업은 ADR-0008의 실행 예외에 따라 사람이 지시한 범위에서만 한다.

## 기술 실험

되돌리기 비싼 기술 가정(드라이버·인증 방식·외부 공급자 품질 등)은 앱 코드를 쓰기 전에 `experiments/`에서 작게 시험한다. 실험 코드는 근거로 보존하지만 앱의 일부가 아니다.

| 규칙 | 내용 |
| --- | --- |
| 위치 | 주제마다 `experiments/<주제>/` 하나(예: `t02-1`). 폴더마다 자체 `package.json`·Supabase 설정을 두고 다른 실험·사용자의 로컬 프로젝트와 겹치지 않는 포트를 쓴다 |
| README | 폴더마다 목적, 필요한 도구, 준비·실행·정리 명령, 결과를 기록한 티켓 링크를 둔다. 목록은 [`experiments/README.md`](../../experiments/README.md)에 추가한다 |
| 앱과 분리 | 앱 코드·테스트·배포는 `experiments/`를 가져오지 않는다. 채택한 방식은 앱 코드에 새로 구현하고 앱의 테스트로 다시 검증한다 |
| 환경 | 로컬 또는 사람이 승인한 격리 환경만 쓴다. 운영 프로젝트·운영 데이터와 기존 프로젝트를 쓰지 않는다 |
| 비밀값 | `.env*`·서명 키·생성된 설정은 각 폴더의 `.gitignore`로 제외한다. 시험 계정 값도 이 파일에만 둔다 |
| 결과 | 실행 환경·명령·결과·채택/기각 판단은 해당 티켓에 남긴다. 실험 PR은 결과 기록과 함께 머지한다 |
| 수명 | 실험은 지우지 않고 계속 보존한다. 결과가 더 이상 맞지 않으면(예: 버전 변경으로 다른 방식 채택) [`experiments/README.md`](../../experiments/README.md) 목록의 상태를 `대체됨`으로 바꾸고 대체한 실험을 링크한다. 템플릿으로 만든 새 프로젝트도 실험 폴더를 유지한다 |

## 최소 기반과 완결된 기능

첫 기능이 사용하는 도메인·저장·HTTP/MCP·화면·테스트를 함께 연결한다. 공통 기반에는 즉시 사용할 기능과 종료 조건을 적는다. 실제 두 번째 사용처에서 공통성이 확인되면 확장한다. 모든 DB, 모든 API, 모든 화면을 각각 먼저 완성하는 방식은 기본으로 삼지 않는다.

공통 기반의 첫 소비자는 할 일·기록·검색 기능이다(이 템플릿에서는 [Template-01](../tickets/template-01-task-record-search.md)). 기반만 구현했거나 모의 화면만 연결한 상태를 사용자 기능 완료로 보고하지 않는다.

## 기능 계약과 교차 검증

인증·권한·입력·외부 통신·데이터 수명 변경에는 [보안 가이드](../security/guide.md)를 적용한다. 기능 티켓에 보호 대상·신뢰 경계·거부 테스트와 미적용 항목의 이유를 기록한다. AGENTS.md와 개발 스킬의 작업별 문서 연결을 유지한다.

각 기능 티켓에서 아래 항목을 관리한다. 실제 경로·도구 이름·필드·오류는 해당 티켓의 계약에 한 번 정의한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 웹/MCP 동등성 | 지원 행위, 전체 편집 필드, 단건·페이지 탐색, 동일한 권한과 부수효과 |
| 데이터 수명 | 정본, 참조, 삭제·정정 영향, 파생 데이터 갱신 |
| 실패와 재시도 | 부분 실패, 응답 유실, 중복 요청, 충돌, 오래된 비동기 결과 |
| 에이전트 사용 | 도구 schema·설명·실제 호출 일치, 제품 스킬의 필요한 안내 |
| 플러그인 제공 | Claude·Codex 각 manifest·연결 설정과 공유 스킬의 통합 패키지, 클라이언트별 설치·업데이트·서버 호환성과 실제 행동 |

웹 생성→MCP 조회·변경→웹 재조회와 반대 방향을 해당 범위에서 검증한다. 미지원 기능은 표기하며 공통 유스케이스를 쓴다는 이유만으로 동등성을 통과 처리하지 않는다.

## 검증 환경과 증거

세션 시작과 환경 전환 시 checkout·commit·미커밋 변경과 필요한 런타임·연결 도구를 확인한다. 로컬 앱의 접속 대상이 로컬 DB라고 가정하지 않는다. 일반 개발 데이터, 초기화 가능한 격리 테스트, 운영 데이터를 구분한다. 운영 DB를 격리 테스트 대신 사용하지 않는다.

| 변경 대상 | 검증 위치 |
| --- | --- |
| 도메인 판단 | DB 없는 단위 테스트 |
| 저장·RLS·원자성·경쟁 | 실제 격리 DB 통합 테스트 |
| HTTP/MCP | 인증·입출력·오류 계약과 실제 호출 |
| 웹 흐름 | 관련 브라우저 E2E, 모바일·데스크톱 상태와 조작 |
| 검색 | 실제 모델의 관련/무관 질문 평가, 원문 접근, 색인 지연·실패 구분 |
| 제품 스킬 | 자동 계약 검사와 별도로 Claude·Codex 각 클라이언트에서 행동 확인 |
| 문서 | UTF-8 BOM 없음·LF, 링크, 공백, 문서 간 계약 일치, Claude 스킬 연결 파일과 정본 frontmatter 일치 |

### 문서 검사

문서·스킬·설정 파일을 바꾸면 저장소 루트에서 다음을 실행하고 결과를 PR과 티켓에 남긴다. Node 22 이상만 필요하며 설치할 의존성은 없다.

| 명령 | 검사 |
| --- | --- |
| `node scripts/check-docs.mjs` | Git이 추적하거나 무시하지 않는 텍스트 파일의 UTF-8 유효성·BOM 없음·LF·줄 끝 공백·마지막 줄바꿈, 마크다운 내부 상대 링크(코드 블록·인라인 코드 제외)와 HTML의 href·src 상대 경로(script·style·주석 제외. 둘 다 앵커는 미검사), 개발 스킬 정본과 Claude 연결 파일의 name·description 일치 |
| `node --test "scripts/*.test.mjs"` | 검사기 자체의 시험. 정상 저장소 통과와 깨진 링크(마크다운·HTML)·CRLF·BOM·UTF-8이 아닌 바이트·줄 끝 공백·frontmatter 불일치 검출 |
| `git diff --check` | 변경분의 공백 오류 |

문서 변경의 검증 근거는 저장소 밖 검사기 대신 이 명령의 결과로 남긴다. 실패 메시지는 `파일:줄: 문제` 형식이다.

### 실행 검증

필요한 도구는 Node 22 이상과 Docker다. Deno와 Supabase CLI는 `npm ci`가 `package.json`에 고정한 버전으로 설치하며 `npm run`이 그 버전을 쓴다. 명령의 정본은 `package.json`의 `scripts`와 [CI](../../.github/workflows/ci.yml)다.

| 명령 | 하는 일 |
| --- | --- |
| `npm ci` | 잠금 파일대로 의존성 설치 |
| `npm run setup:local` | 서명 키 생성(처음 한 번), 로컬 Supabase 시작, `.env.local`과 개발용 사용자 A·B 준비. 다시 실행해도 키와 비밀번호를 유지 |
| `npm run dev` | 웹 개발 서버(`http://127.0.0.1:55480`) |
| `npm run check:boundaries` | 의존 경계: contracts는 zod만, core는 contracts·core·zod만(Deno API·네트워크·HTTP 타입 금지), 웹은 서버 코드를 `@contracts`로만 가져오고 제품 데이터에 supabase-js `.from`/`.rpc`를 쓰지 않음 |
| `npm run check:deno` | 서버 코드의 Deno 타입·lint·형식 검사 |
| `npm run test:core` | DB 없는 contracts·core 테스트 |
| `npm run test:web` | 웹 단위 테스트(Vitest) |
| `npm run build` | 웹 타입 검사와 정적 빌드 |
| `npm run test:db` | 격리 로컬 DB 테스트: 사용자 격리, 직접 쓰기 차단, 연결 재사용 시 문맥 해제, 원본·큐 원자성, contracts와 DB 한도 parity, 유스케이스 부분 실패 롤백 |
| `npm run serve:functions` | 로컬 Edge Functions 실행(`/functions/v1/api`, `/functions/v1/mcp`). HTTP·MCP 테스트 전에 다른 터미널에서 띄운다 |
| `npm run test:http` | 실제 진입점과 로그인 토큰으로 HTTP 계약 테스트: 인증·입력 오류, 격리, 완료·동시 완료·재시도, 반복 회차, 커서 |
| `npm run test:mcp` | 실제 OAuth 흐름(동적 등록·PKCE·동의 API·코드 교환)으로 받은 MCP 토큰과 공식 MCP 클라이언트로 도구 계약 검사: 토큰 audience 구분, `tools/list` schema, 웹 작성→MCP 완료→웹 확인, HTTP와 같은 결과·오류, 제품 스킬의 도구 이름 |
| `npm run test:e2e` | Playwright(데스크톱·모바일 viewport): 웹 작성→브라우저 동의 화면 승인으로 MCP 연결→MCP 완료→웹 확인, MCP 작성→웹 편집→MCP 확인, 다른 사용자의 URL 접근 거부. 웹 개발 서버는 자동으로 띄운다. 처음 한 번 `npx playwright install chromium` |
| `npm run stop:local` | 로컬 Supabase 정지(데이터 유지) |

로컬 Supabase 포트는 55420~55429, 웹은 55480, Edge inspector는 8483이다. 다른 로컬 프로젝트·실험(55320~55329)과 겹치지 않는다. CI는 운영 secret 없이 `check` job(문서·공백·Deno·core·웹)과 `integration` job(러너 안의 로컬 Supabase로 DB·HTTP·MCP·E2E 테스트)을 실행한다. 새 검사는 추가되는 단계에서 이 표와 CI에 넣는다.

환경상 실행할 수 없는 검사는 대상 commit·명령·데이터 조건·실행 가능한 격리 환경을 기록해 인계한다. CI에서 수행하는 경우 해당 revision의 결과까지 확인한다.

## 변경과 완료 기록

영향받는 계약·도구 설명·제품 스킬·스키마 색인을 함께 갱신한다. 적용된 migration 이력과 무관한 사용자 변경을 보존한다. 비밀값은 문서·로그·버전 관리에 남기지 않는다.

티켓에는 실제 명령·결과·검증 revision·남은 검사를 남긴다. 구현 완료, 자동 검사 통과, 운영 배포, 실제 에이전트 클라이언트 확인은 각각 기록한다. 서버·DB·웹·플러그인의 배포가 동시에 완료된다고 가정하지 않는다.

검증한 revision의 공개는 [배포 방법](../deployment/release.md), 공개 후 점검과 장애 처리는 [운영 방법](../operations/runbook.md)을 따른다. 실행 기반을 만들 때 문서에 실제 명령·설정·조회 위치를 채우고 재현한 증거를 남긴다.
