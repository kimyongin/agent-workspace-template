# 개발과 검증 방법

## 에이전트에게 위임하기

사람이 에이전트에게 일을 시키는 방법(명령 흐름·예시·모델 선택)은 [에이전트와 일하는 방법](working-with-agents.md)에 있다. 이 문서는 에이전트가 따르는 작업·검증 규칙이다.

저장소의 [develop-agent-app 스킬](../../.agents/skills/develop-agent-app/SKILL.md)은 설계·구현·리뷰·배포·운영의 공통 진입점이다. 문서를 복사하지 않고 요청에 필요한 정본으로 안내한다. 개발 스킬과 앱 사용자를 위한 제품 플러그인 스킬은 별개다.

Codex는 `$develop-agent-app`, Claude Code는 `/develop-agent-app`으로 호출한다. Codex는 `.agents/skills/`의 정본을, Claude Code는 `.claude/skills/develop-agent-app/`의 연결 파일을 거쳐 같은 정본을 읽는다. 지침 진입은 Codex가 AGENTS.md, Claude Code가 AGENTS.md를 가져오는 CLAUDE.md다. 새 스킬의 자동 발견 여부는 해당 클라이언트/세션에서 확인한다. 자동 발견이 없으면 AGENTS.md에 연결된 SKILL.md를 직접 읽도록 요청하면 된다. 전역 설치는 필요하지 않으며 이 스킬은 저장소의 docs와 함께 사용한다.

개발 에이전트는 하나만 써도 된다. 여러 세션의 역할·작업 공간·환경 조정은 아래 [세션 배정과 인계](#세션-배정과-인계), 독립 검토는 [리뷰](#리뷰)를 따른다.

예시 요청(Codex 기준, Claude Code는 `$` 대신 `/`):

- `$develop-agent-app 고객 관리 기능의 시나리오와 HTTP/MCP 계약을 설계해줘.`
- `$develop-agent-app 확정한 첫 기능 티켓을 구현하고 관련 검증을 수행해줘.`
- `$develop-agent-app 현재 변경의 권한·데이터 일관성과 플러그인 호환성을 리뷰해줘.`
- `$develop-agent-app 검증한 revision의 운영 배포를 준비하고 남은 조건을 정리해줘.`
- `$develop-agent-app 검색 작업이 지연되는 원인을 운영 로그와 큐 상태로 조사해줘.`

설계·준비·조사는 해당 범위의 결과로 끝내며, 실제 구현·배포·복구를 요청하면 그 범위에서 수행한다. 초기 런타임·CI가 아직 없으면 스킬은 존재하지 않는 명령의 성공을 보고하지 않고 필요한 구현/검증 인계를 남긴다.

## 작업의 출발점

[PRD](../product/concept.md), 관련 [ADR](../adr/README.md), [코드 설계 원칙](../architecture/principles.md)을 읽고 구체적인 사용자 시나리오 하나를 선택한다. 관련 티켓에는 변경 데이터, 유지할 불변 조건, HTTP/MCP 기능, 필요한 화면과 완료 조건을 적는다. 미정인 업무·권한·저장 계약은 구현 전에 확정한다. 티켓 파일의 이름·상태·양식은 [티켓 작성 규칙](../tickets/README.md)을 따른다.

설계는 검토 가능한 문서와 구현 인계로 마친다. 구현 시작은 명시적으로 구분한다. 제안·확정·구현·검증·배포 상태를 혼동하지 않는다.

웹 화면 설계·수정 전에는 [디자인 가이드](../design/guide.md)와 그에 연결된 시각 규격·상호작용을 읽는다. 티켓에 소비할 공통 패턴과 상태, 예외, viewport·키보드·초안 보존 검증을 명시한다. 공통 UI 변경은 실제 소비 화면을 함께 검사하고 여러 화면에 영향을 주면 전체 브라우저 E2E를 수행한다.

## 세션 배정과 인계

사람과 본 세션이 함께 설계하고 결정하는 것이 기본이다. 본 세션은 사용자 시나리오·제품 의미·권한·공통 계약·승인 범위를 사람과 합의하고 기능을 나누며 의존성·담당자를 정한다. 조사와 기술 실험은 위임할 수 있지만 결과를 본 세션으로 모아 사람과의 설계·결정에 반영한다. 설계만 전담하는 자식 세션을 기본으로 두지 않는다. 구현 결과의 통합 확인, 최신 `main` 반영, 해당 head의 CI·독립 리뷰 확인, 머지와 사용자 브리핑도 본 세션이 책임진다. 구현 결과를 받았다는 사실만으로 완료를 선언하지 않는다.

구현은 검증 가능한 작은 기능별로 새 서브세션에 맡긴다. 구현 세션은 합의한 설계·계약 안에서 파일 배치·함수·상세 구조를 정하고, 미정인 제품 의미나 권한·공통 계약이 나오면 본 세션의 설계·결정으로 돌려보낸다. 대화 전체를 상속하지 않고 [티켓 인계 필드](../tickets/README.md#인계와-작업-배정)에 정리한 티켓·승인 범위·base commit·담당 변경·계약/의존성·완료 조건·환경을 전달한다. 새 세션은 그 자료와 실제 checkout을 확인해 시작한다. 리뷰 수정은 원래 구현 세션에 돌려주어 기존 검증과 함께 반영한다.

짧은 수정은 본 세션에서 직접 해도 된다. 서브세션 도구가 없는 환경에서도 본 세션이 구현할 수 있으며 독립 리뷰와 머지 조건은 그대로 적용한다. 새 세션도 작업이 길면 대화가 압축될 수 있고, 앞의 맥락을 모르면 결정을 놓칠 수 있다. 이를 막기 위해 일반 단계 인계와 결정·검증 결과는 티켓에 남긴다. 세션을 새로 만들거나 작업을 전달해도 기존 사용자 지시의 범위와 실행 권한은 늘어나지 않는다.

### 세션 운영 브리핑

본 세션은 배정 시, 중요한 변화(재개·재시도·모델/강도 변경·범위/차단/검증 결과 변화) 시, 결과 인계 시에 사용자에게 아래 세션별 표를 짧게 보고한다. 작업 목적과 선택 이유가 운영 판단에 필요한 수준이면 충분하다. 변화 없는 대기·반복 조회를 같은 표로 다시 보고하지 않는다. 실행 근거와 이력은 [티켓 실행 기록](../tickets/README.md#세션-실행-기록)에 남기고 브리핑에서 연결한다.

| 세션·역할 | 작업·이유 | 모델 등급·이름 / 선택 이유 | 추론 강도 / 선택 이유 | 상태·결과·미확인 | 다음 행동·사람의 판단 |
| --- | --- | --- | --- | --- | --- |
| 식별자 / 구현·리뷰 등 | 맡긴 결과와 필요한 이유 | 명시 배정 값과 근거 | 모델과 별도의 근거 | 확인한 결과와 확인 범위 | 담당·다음 단계 또는 필요한 결정 |

모델과 강도의 증거는 **요청한 값 → 도구에 명시 배정한 값 → CLI/클라이언트가 수락한 값 → 관찰된 실제 모델·backend effort**를 구분한다. 확인한 단계와 근거 위치를 쓰며 수락 응답이나 모델 목록만으로 backend 실행까지 확인했다고 하지 않는다. 실제 metadata가 없으면 `미노출/미확인`으로 남긴다. 계정·클라이언트별 별칭과 실제 모델 ID는 확인된 대응만 기록하고, 내부 helper 사용이 드러나면 배정 세션과 구분한다. 추측으로 별칭을 해석하거나 내부 helper를 별도 개발 세션으로 세지 않는다.

재개·재시도·상향·하향은 같은 세션인지 새 세션인지 식별하고 이전/이후 모델·강도, 원인, 선택 이유, 결과를 남긴다. 모델 변경 이유와 추론 강도 변경 이유는 각각 설명하며 유지했다면 그 값과 이유를 쓴다. 시간·재시도 횟수·검증 성공/실패·세션별 토큰/비용 등 지표는 출처·측정 범위가 확인된 것만 제공한다. 없는 사용량·비용을 추정하지 않으며 계정 전체 사용량을 개별 세션에 귀속하지 않는다. 보고를 위해 원본 프롬프트·개인정보·비밀값을 공개하지 않고 목적·근거를 요약한다.

세션의 구현/조사 완료와 PR의 독립 리뷰·CI·머지 완료를 구분한다. 기존 권한 안의 일반 배정과 모델/강도 조정은 본 세션이 진행하며 브리핑을 승인 대기로 만들지 않는다. 승인 범위 밖 실행, PRD·ADR 이탈, 미정인 사용자 결정이 필요하면 대상·이유·영향·선택지를 명확히 표시하고 그 결정에 의존하지 않는 작업을 계속한다. 브리핑은 사용자와 본 세션의 운영 자료다. 독립 리뷰어에게 전달할 자료는 [리뷰 규칙](#리뷰)의 허용 범위를 유지하고 구현 판단·선택 이유·예상 결론을 주입하지 않는다.

### 병렬 작업

- 독립적인 기능만 병렬로 구현한다. 처음에는 두 구현 정도로 시작하고 의존성과 조정 부담을 보고 늘린다. 고정된 개수 제한은 아니다.
- 구현 세션마다 별도 worktree 또는 checkout과 브랜치를 쓴다. 브랜치 이름만 달리해 같은 checkout을 동시에 수정하지 않는다. 여러 세션이 같은 tracked 파일을 동시에 편집하지 않도록 변경 담당을 정한다.
- 시작 전에 공통 파일·계약·migration·환경 변경 담당과 선행 결과를 [작업 배정표](../tickets/README.md#인계와-작업-배정)에 정한다. 공유 계약 변경은 소비자가 구현·검증하기 전에 확정하고, 의존 결과가 바뀌면 뒤 작업의 기준과 검증을 다시 맞춘다.
- 코드 작업 공간과 실행 환경의 격리는 별개다. 공유 로컬 환경의 실행 담당·순서는 [공유 환경과 테스트 자료](#공유-환경과-테스트-자료)를 따른다.

### 모델과 추론 강도 선택·갱신

본 세션은 새 구현·리뷰 배정과 재개 때 작업의 난이도·실패 영향으로 모델 등급을 고르고 추론 강도를 별도로 고른다. 모드마다 규칙을 복제하지 않는다. 일반 구현과 일반 리뷰는 **균형 모델 + medium**이 기본이다. 좁은 파일 탐색·명확한 문구/기계적 수정은 **경량 + 지원되는 low**, 중요한 권한·데이터 일관성·복잡한 조사/미정 계약은 **고성능 선배정 + high**를 고려한다. 모델이 바뀌어도 기존 강도를 묵시 상속하지 않는다.

같은 모델에서 medium→high 조정과 모델 등급 상향은 별개 판단이다. 원인을 분류하고 그 원인에 맞춘 **두 번의 수정에도 진전이 없으면** 문제 범위를 좁혀 추론 강도/모델 상향을 판단하고 각각의 이유·수정·결과를 티켓에 남긴다. 도구 권한·네트워크·계정에서 미지원 모델처럼 환경 실패는 능력 부족으로 세지 않고 환경을 해결하거나 실행 가능한 곳으로 인계한다. high에서도 근거 기반 정체가 계속되는 제한된 문제에만 xhigh(extra-high)를 고려한다. max/ultra는 기본값으로 쓰지 않는다. 어려운 범위를 해결하면 다음 일반 작업은 균형/medium 또는 경량/low로 낮추고 기록한다.

현재 모델 ID·지원 강도·근거·확인일·대체 조건은 [단일 선택표](agent-models.json)가 소유한다. 등급은 light/ balanced/ advanced이며 기본 강도는 배정의 시작값일 뿐이다. CLI·desktop·공급자·계정 문맥마다 지원 목록이 다르다. `capability`는 목록/강도 지원 확인, `nativeExecution`은 해당 실행 경로의 증거, `evaluation=baseline`은 가이드에 따른 현재 기본(품질·과금 우수성 검증이 아님), `passed`는 대표 평가를 통과한 신규 후보, `pending`은 미완료다. 미검증을 완료로 바꾸지 않는다.

개발하는 날 첫 작업에서 계정·공급자·클라이언트별 실제 목록과 새 후보를 한 번 조회하고, 저장소 밖 snapshot을 그날 재사용한다. ‘그날’은 사용자가 명시한 IANA 시간대의 달력 날짜이며 호스트 시간대나 최근 24시간이 아니다. 개발하지 않는 날은 조회하지 않으며 별도 스케줄러나 cache 서비스를 만들지 않는다. 계정·공급자·클라이언트 변경이나 지원 종료가 확인되면 즉시 재확인한다. 선택표의 checkedAt은 기록된 검증의 시간대 포함 시각이며 쉬었던 기간만으로 만료되지 않는다. 오늘의 실제 목록과 기존 모델·강도가 호환되면 기존 선택과 검증 근거를 유지한다. 과거 자료에 오늘 시각을 붙여 새 검증으로 만들지 않는다.

유망한 새 후보에만 현재 계정·클라이언트 버전·지원 기능과 요금/계정 사용량 근거 확인→같은 revision의 대표 구현·리뷰 과제(권한/일관성 실패 탐지 포함) 평가→증거를 티켓에 기록하고 검증된 선택표 갱신→새 작업에 적용한다. 이전 선택과 실패·교체 이유도 티켓에 보존한다. 목록 조회를 매일 성능 평가로 확대하거나 후보를 자동 승격하지 않는다. 목록이 바뀌었다는 이유만으로 품질·비용 평가를 통과 처리하거나 CLI를 자동 업데이트하지 않는다.

배정 **전에** `node scripts/agent-models.mjs assign --client <surface> --tier <grade> --effort <level> --role <role> --reason <선택근거> --snapshot <current.json>`을 실행한다. [실행 경로와 snapshot 형식](agent-model-execution.md)을 따른다. 명령은 선택 모델/추론 강도와 명시 실행 인자를 출력하며 모델/강도 누락·미지원·차단·다른 현지 날짜/미래의 조회·잘못된 시각/시간대·설정 drift·문맥 변경을 거부한다. 초기 후보 검증에는 `--evaluate`를 써 미검증 표시로 제한된 평가만 한다. 실패를 부모의 고성능 상속으로 숨기지 않고 해당 배정을 멈춰 증거를 갱신한다. 역할·승인 범위·실제 모델/강도·확인 시각과 모델/강도 상향·하향 이력은 [티켓 인계 필드](../tickets/README.md#인계와-작업-배정)에 남긴다. 실제 실행/재개 후 선택과 actual 모델을 대조한다.

재개도 같은 preflight를 수행한다. 기존 세션에 결합된 모델·강도가 같으면 지원되는 followup/resume으로 이어갈 수 있다. 둘 중 하나가 바뀌면 현재 continuation API가 그 값을 명시 적용하는지 확인한다. 지원하지 않거나 적용을 확인할 수 없으면 새 서브세션에 티켓·base·완료 결과·남은 범위만 좁게 인계한다. preflight 성공만으로 기존 세션의 모델·강도가 바뀌었다고 보고하지 않는다. 클라이언트별 실행 제한과 관찰 범위는 [모델 실행](agent-model-execution.md)을 따른다.

선택표 변경 후 `node scripts/agent-models.mjs sync`로 얇은 native 연결 설정을 맞춘다. `npm run check:docs`는 schema·지원 강도·정본/native drift와 오류 경로를 검사하며 단순 날짜 경과로 CI를 깨지 않는다. 최신성은 배정 명령이 강제한다. 저장소 설정은 개인 전역 설정이나 권한을 바꾸지 않는다.

## 구현과 지침을 함께 발전시키기

이 저장소는 도메인 앱을 시작하는 템플릿이다. 문서의 소유와 변경 권한은 [ADR-0008](../adr/0008-document-ownership.md)을 따른다. PRD·ADR은 사람이 소유하고, 티켓·구현·가이드·스킬은 에이전트가 소유한다. 가이드는 에이전트가 일관되게 작업하기 위한 수단이며 구현에서 얻은 판단을 다시 반영해 발전시킨다.

변경할 때는 관련 PRD·ADR과 가이드·스킬을 함께 확인한다. 충돌이 있으면 다음과 같이 처리한다.

| 판단 | 처리 |
| --- | --- |
| 기준이 적절하고 구현이 잘못됨 | 구현을 기준에 맞게 수정하고 재발을 확인할 검증 보완 |
| 가이드·스킬의 방법을 바꾸는 것이 적절함 | 에이전트가 담당 가이드와 관련 스킬·구현·테스트를 같은 PR에서 갱신 |
| PRD·ADR의 범위·결정을 벗어나야 함 | 작업을 멈추고 이유·대안·영향을 담은 PRD 변경안 또는 ADR 초안(상태 `제안`)으로 사람의 승인을 받음. 승인 전에는 이탈하는 구현을 머지하지 않음 |
| 특정 조건에서만 다른 동작이 필요함 | 적용 범위·이유·유지할 공통 기준·재검토 조건을 예외로 기록. PRD·ADR과 충돌하면 위 행을 따름 |

어느 쪽인지 애매하면 ADR-0008의 분류 기준(제품 의미→PRD, 되돌리기 비싼 결정→ADR, 방법→가이드)으로 판단한다. 같은 예외가 여러 곳에서 반복되면 예외를 쌓지 않고 기준 자체를 재검토한다. 반복 결함은 원인에 맞는 가이드와 재현 가능한 회귀 검사로 반영한다.

기존 문장을 남긴 채 상충하는 최신 규칙을 덧붙이지 않는다. 적용되지 않는 예시·링크·스킬 지침은 수정하거나 제거하고 과거 검증 기록은 당시의 증거로 구분한다.

완료 기준은 변경 위치 하나가 동작하는 데 그치지 않는다. 영향받는 공통 코드·웹/HTTP·MCP/제품 스킬·문서·검증이 같은 의미를 갖는지 확인한다. 관련 없는 영역까지 일괄 수정할 필요는 없다. 단계적으로 옮겨야 하면 임시 차이·남은 소비자·담당 작업·종료 조건을 명시하고 전환 완료로 보고하지 않는다.

## 변경 단위와 PR·리뷰

### 작게 나누기

- 티켓의 각 단계는 시작할 때 PR 분할 계획을 티켓에 먼저 적는다. PR 하나에는 실제로 동작하는 기능 한 조각 또는 결정 하나만 담는다. DB만, API만, 화면만처럼 계층 단위로 나누지 않는다. 분할 계획의 완료 조건에는 "이 PR까지 머지하면 무엇을 직접 확인할 수 있는가"를 적는다(예: 일회성 할 일을 웹과 MCP에서 만들고 완료할 수 있음). 공통 기반은 그것을 처음 쓰는 기능 PR에 함께 넣는다.
- PR 크기는 lockfile·자동 생성 파일을 빼고 약 400줄, 30분 안에 리뷰할 수 있는 정도를 기준으로 한다. 넘으면 계층이 아니라 기능을 더 좁혀 나누고(예: 할 일 만들기 → 완료하기), 그래도 넘으면 PR 설명에 이유를 적는다.
- 되돌리기 비싼 선택이 구현 전에 필요하면(기술 검증 결과, 공개 계약, schema 정본 등) 먼저 짧은 PR이나 티켓 메모로 확정한다. PRD·ADR에 해당하면 위 승인 절차를 따른다.
- 앞 PR의 코드나 문서에 실제로 의존하는 PR만 앞 PR의 브랜치 위에 쌓는다. 앞 PR이 바뀌면 뒤 PR을 다시 맞춘다. 티켓 기록 표의 몇 줄처럼 작은 충돌만 예상되면 쌓지 말고 각자 `main`에서 브랜치를 만든 뒤, 나중에 머지하는 PR에서 충돌을 해결한다.
- 쌓은 PR은 리뷰가 끝나는 대로 아래부터 바로 머지해 쌓인 수를 적게 유지한다. 여러 개를 모아 두었다가 한꺼번에 머지하지 않는다. 쌓인 PR마다 base 변경·rebase·CI 재실행이 필요해서, 몰아서 머지하면 그 비용과 충돌이 한꺼번에 생긴다.
- 아래 PR을 머지하기 전에 바로 위 PR의 base를 `main`으로 바꾼다(`gh pr edit <위 PR> --base main`). base 브랜치가 먼저 지워지면 GitHub가 위 PR을 닫는다. squash 머지 뒤에는 위 PR에 아래 PR의 원래 커밋이 남아 충돌하므로, 위 PR 브랜치에서 자기 커밋만 `main` 위로 옮기고(`git rebase --onto origin/main <아래 PR의 머지 전 head>`) 강제 푸시(`--force-with-lease`)한 뒤 머지한다. 아래 PR의 머지 전 head는 `gh pr view <아래 PR> --json headRefOid`로 확인한다.

### 브랜치와 PR

- `main`에 직접 푸시하지 않는다. 작업마다 브랜치를 만들고 PR을 연다. 브랜치 이름은 `<종류>/<짧은-설명>`(예: `feat/task-complete`, `docs/adr-0009`)으로 한다.
- PR 설명은 [PR 템플릿](../../.github/pull_request_template.md)을 따른다. 관련 티켓·PRD/ADR, 변경 내용, 검증 명령과 결과, 검증하지 못한 항목, 리뷰어가 볼 부분을 적는다.
- 커밋 메시지는 `feat:`·`fix:`·`docs:`·`refactor:`·`test:`·`chore:` 접두어를 쓴다. 머지는 squash를 기본으로 한다.
- 세션별 작업 공간·변경 담당은 [세션 배정과 인계](#세션-배정과-인계)를 따른다.

### 리뷰

- 모든 PR은 머지 전에 리뷰를 받는다. 본 세션은 PR이 준비되면 구현 대화 맥락이 없는 별도 새 세션에 리뷰를 맡긴다. 사람이 따로 요청하지 않아도 매 PR에 한다. 서브세션을 띄울 수 없는 환경이면 머지하지 말고, 사람에게 새 세션에서 `PR #N 리뷰해줘`를 요청해 달라고 알린다.
- 리뷰어에게는 PR 번호·정확한 head commit·base와 diff·관련 티켓·PRD/ADR·지침의 위치만 넘긴다. 구현 논리나 예상 결론을 주입하지 않는다. 리뷰 결과는 검사한 head와 함께 PR 코멘트로 남긴다. 이후 코드나 문서가 바뀌면 새 head로 변경 범위의 독립 리뷰와 필요한 검증을 다시 받는다.
- 다른 개발 에이전트(예: Claude Code가 만든 PR을 Codex가)의 교차 리뷰는 사람이 요청할 때만 한다.
- 리뷰어는 결함과 함께 PRD·ADR 이탈 여부를 확인한다. 점검 기준은 해당 가이드를 따른다: HTTP/MCP 동등성·데이터 수명·실패와 재시도(이 문서의 기능 계약), 권한·입력·비신뢰 콘텐츠([보안 가이드](../security/guide.md)), 화면([디자인 가이드](../design/guide.md)), 검색([검색 가이드](../architecture/search.md)), 플러그인([배포 방법](../deployment/release.md)).
- 리뷰 결론은 셋 중 하나로 남긴다: `머지 가능`, `수정 필요`(발견 사항과 근거), `사람 승인 필요`(실제 사용자 결정·승인 경계 또는 PRD·ADR 변경·이탈).
- 기술 리뷰 이견은 먼저 해당 head에서 문제를 재현하고 증거·계약·영향을 대조한다. 작성자는 수정 또는 반영하지 않는 근거를 답하고 독립 리뷰어가 결론을 갱신한다. 해소되지 않으면 구현 맥락이 없는 추가 독립 리뷰로 확인한다. 작성자 혼자 발견 사항을 기각하고 머지하지 않으며, 정확한 머지 head의 독립 `머지 가능` 결론은 여전히 필요하다.
- 미해결 발견 사항·재현 근거·처리 결과는 PR에 남기고 추가 독립 리뷰도 그 쟁점을 검토한다. 다른 리뷰의 일반적인 `머지 가능` 문구만으로 알려진 차단 사항을 무시하지 않는다. 수정 또는 근거 있는 해소를 독립 리뷰에서 확인한 뒤 머지한다.
- `사람 승인 필요`는 실제 미정인 사용자 결정, 실행 승인 경계, PRD·ADR 변경·이탈에 적용한다. 기술적 의견 차이만으로 사람에게 승인을 넘기지 않는다. 사용자 결정이 필요한 부분과 그 결정에 의존하지 않는 검증·수정을 구분한다.

### 머지

머지·리뷰 조건의 정본은 이 절과 위 "리뷰" 절이다. 에이전트의 머지 권한은 [ADR-0010](../adr/0010-merge-authority.md)이 정하고, 다른 문서는 이 절을 링크한다. 다음을 모두 만족하면 에이전트가 머지한다.

- PRD·ADR을 바꾸지 않고 벗어나지도 않는다.
- 자동 검사(CI)가 통과했다. `main`은 CI의 `check`·`integration` job을 필수 상태 검사로 걸어 두므로, 실패했거나 실행되지 않은 PR은 관리자도 머지할 수 없다. 검사를 건너뛰거나 보호를 잠시 풀어 머지하지 않는다.
- 머지할 정확한 head에 대해 구현한 세션과 분리된 리뷰의 결론이 `머지 가능`이다.
- 필수 검증의 증거 또는 검증하지 못한 이유가 티켓에 기록되어 있다.

필수 검사는 PR 브랜치가 최신 `main`을 포함할 것도 요구한다(strict). 뒤처진 PR은 `main`을 반영해 CI를 다시 통과시킨 뒤 머지한다. 쌓은 PR은 위 "작게 나누기"의 rebase 절차가 이 조건을 함께 맞춘다. CI 파일이 없는 브랜치(필수 검사 등록 이전에 갈라진 브랜치 등)는 검사가 생기지 않아 머지할 수 없으므로 `main`을 반영해 CI가 실행되게 한다.

필수 검사 목록은 CI job과 함께 바꾸며 시점은 다음과 같다.

- job 추가: 그 job을 도입한 PR을 머지한 직후에 목록에 넣는다. 머지 전에 넣으면 그 job이 없는 다른 PR(쌓은 PR의 아래쪽 포함)이 모두 막힌다.
- job 이름 변경·삭제: 그 PR의 CI가 통과한 뒤 머지 직전에 목록을 바꾸고 바로 머지한다. 다른 열린 PR은 `main`을 반영해 바뀐 job으로 다시 검사한다.
- 머지하려고 필수 검사를 잠시 줄이거나 빼지 않는다(위 머지 조건).

필수 검사 변경은 저장소 관리자 권한이 필요하며 사람이 승인한 뒤 에이전트가 GitHub API로 바꾸거나 사람이 설정한다. 바꾼 뒤 보호 설정 조회 결과를 해당 티켓에 남긴다. 새 프로젝트의 같은 설정은 [Template-02](../tickets/template-02-implementation-base.md) T02-6의 초기화 절차에 넣는다.

PRD·ADR을 바꾸는 PR은 사람이 승인한다. 머지는 배포가 아니다. 운영 배포·운영 DB 적용·비용이 드는 작업은 ADR-0008의 실행 예외에 따라 사람이 지시한 범위에서만 한다.

| 위치 | 주제마다 `experiments/<주제>/` 하나(예: `t02-1`). 폴더마다 자체 `package.json`·Supabase 설정을 두고 다른 실험·사용자의 로컬 프로젝트와 겹치지 않는 포트를 쓴다 |
| README | 폴더마다 목적, 필요한 도구, 준비·실행·정리 명령, 결과를 기록한 티켓 링크를 둔다. 목록은 [`experiments/README.md`](../../experiments/README.md)에 추가한다 |
| 앱과 분리 | 앱 코드·테스트·배포는 `experiments/`를 가져오지 않는다. 채택한 방식은 앱 코드에 새로 구현하고 앱의 테스트로 다시 검증한다 |
| 환경 | 로컬 또는 사람이 승인한 격리 환경만 쓴다. 운영 프로젝트·운영 데이터와 기존 프로젝트를 쓰지 않는다. 호스팅에서만 드러나는 동작(Edge 배포, 실서버 풀러, 경로 삽입형 metadata 등)은 실험이 아니라, 사람이 지시한 운영 배포 뒤의 동작 확인으로 본다. 이 경우 그 동작이 첫 운영 배포에서 처음 확인된다는 위험을 해당 티켓에 적는다. 확인 결과 설계를 바꿔야 하면 로컬이나 사람이 승인한 격리 환경에서 다시 실험한다 |
| 비밀값 | `.env*`·서명 키·생성된 설정은 각 폴더의 `.gitignore`로 제외한다. 시험 계정 값도 이 파일에만 둔다 |
| 결과 | 실행 환경·명령·결과·채택/기각 판단은 해당 티켓에 남긴다. 실험 PR은 결과 기록과 함께 머지한다 |
| 수명 | 실험은 지우지 않고 계속 보존한다. 결과가 더 이상 맞지 않으면(예: 버전 변경으로 다른 방식 채택) [`experiments/README.md`](../../experiments/README.md) 목록의 상태를 `대체됨`으로 바꾸고 대체한 실험을 링크한다. 템플릿으로 만든 새 프로젝트도 실험 폴더를 유지한다 |

## 최소 기반과 완결된 기능

첫 기능이 사용하는 도메인·저장·HTTP/MCP·화면·테스트를 함께 연결한다. 공통 기반에는 즉시 사용할 기능과 종료 조건을 적는다. 실제 두 번째 사용처에서 공통성이 확인되면 확장한다. 모든 DB, 모든 API, 모든 화면을 각각 먼저 완성하는 방식은 기본으로 삼지 않는다.

공통 기반의 첫 소비자는 할 일·기록·검색 기능이다(이 템플릿에서는 [Template-01](../tickets/template-01-task-record-search.md)). 기반만 구현했거나 모의 화면만 연결한 상태를 사용자 기능 완료로 보고하지 않는다.

## 기능 계약과 교차 검증

인증·권한·입력·외부 통신·데이터 수명 변경에는 [보안 가이드](../security/guide.md)를 적용한다. 기능 티켓에 보호 대상·신뢰 경계·거부 테스트와 미적용 항목의 이유를 기록한다. AGENTS.md와 개발 스킬의 작업별 문서 연결을 유지한다.

각 기능 티켓에서 아래 항목을 관리한다. 실제 경로·도구 이름·필드·오류는 해당 티켓의 계약에 한 번 정의한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 웹/MCP 동등성 | 지원 행위, 전체 편집 필드, 단건·페이지 탐색, 동일한 권한과 부수효과 |
| 데이터 수명 | 정본, 참조, 삭제·정정 영향, 파생 데이터 갱신 |
| 실패와 재시도 | 부분 실패, 응답 유실, 중복 요청, 충돌, 오래된 비동기 결과 |
| 에이전트 사용 | 도구 schema·설명·실제 호출 일치, 제품 스킬의 필요한 안내 |
| 플러그인 제공 | Claude·Codex 각 manifest·연결 설정과 공유 스킬의 통합 패키지, 클라이언트별 설치·업데이트·서버 호환성과 실제 행동 |

웹 생성→MCP 조회·변경→웹 재조회와 반대 방향을 해당 범위에서 검증한다. 미지원 기능은 표기하며 공통 유스케이스를 쓴다는 이유만으로 동등성을 통과 처리하지 않는다.

필드·필터를 바꾸면 영향받는 HTTP 입출력·MCP `tools/list` schema·웹 입력/표시·저장소 쿼리·제품 스킬을 티켓에서 대조한다. 반복 회차처럼 별도 계산·조회·완료 분기도 포함한다. 가능한 schema는 공유 계약 정본에서 파생하고 수동 동기화 대상은 비교 검사로 확인한다. schema가 같아도 실제 저장소 분기의 필터 전달이 보장되지는 않으므로 변경한 행위·분기를 실제 진입점과 DB에서 검증한다.

### 기능별 회귀 검증

화면의 복귀·초안 규칙은 [디자인 가이드](../design/guide.md#화면-완료-체크리스트)가 정본이다. 목록·상세·편집·필터를 변경하는 기능은 첫 페이지 동작에 더해 추가 페이지→상세→편집 저장/취소·삭제→목록 복귀를 완료 조건에 넣는다. 변경 위험에 따라 필터·펼친 범위·스크롤·초점, 저장 실패/충돌의 초안, 브라우저 뒤로 가기·새로고침, 상세에 머무는 동안의 동시 추가, 필터 전환/화면 이탈 뒤 늦은 응답을 검사한다. 대상이 삭제되거나 조건에서 빠지면 유효한 위치로 돌아가고 복원 조회가 끝나는지도 확인한다. 필요한 시나리오는 관련 모바일·데스크톱 E2E에 남긴다.

## 검증 환경과 증거

세션 시작과 환경 전환 시 checkout·commit·미커밋 변경과 필요한 런타임·연결 도구를 확인한다. 로컬 앱의 접속 대상이 로컬 DB라고 가정하지 않는다. 일반 개발 데이터, 초기화 가능한 격리 테스트, 운영 데이터를 구분한다. 운영 DB를 격리 테스트 대신 사용하지 않는다.

| 변경 대상 | 검증 위치 |
| --- | --- |
| 도메인 판단 | DB 없는 단위 테스트 |
| 저장·RLS·원자성·경쟁 | 실제 격리 DB 통합 테스트 |
| HTTP/MCP | 인증·입출력·오류 계약과 실제 호출 |
| 웹 흐름 | 관련 브라우저 E2E, 모바일·데스크톱 상태와 조작 |
| 검색 | 실제 모델의 관련/무관 질문 평가, 원문 접근, 색인 지연·실패 구분 |
| 제품 스킬 | 자동 계약 검사와 별도로 Claude·Codex 각 클라이언트에서 행동 확인 |
| 문서 | UTF-8 BOM 없음·LF, 링크, 공백, 문서 간 계약 일치, Claude 스킬 연결 파일과 정본 frontmatter 일치 |

### 공유 환경과 테스트 자료

실행 전에 테스트 자료의 실행별 식별자·생성 범위·정리 대상과 담당을 정한다. 목록 개수·검색 범위 등은 이전 실행의 자료와 다른 검사가 만든 자료가 섞이지 않도록 격리한다. 정리는 해당 실행이 만든 자료만 대상으로 하며, 실패 분석에 필요한 증거를 먼저 보존한다.

같은 로컬 환경의 DB·HTTP·MCP·E2E와 setup·migration·서버 시작/종료는 한 담당이 순차 관리한다. 검증 동안 코드·설정을 고정하고 hot reload, 다른 통합 테스트, 초기화나 서버 정리가 끼어들지 않게 한다. 변경이 필요하면 진행 검증을 끝내거나 중단하고 revision·환경을 다시 기록한 뒤 시작한다. 적용된 migration은 다시 쓰지 않고 후속 migration으로 변경한다.

공유 환경에서는 `test:all`을 동시에 실행하지 않는다. 별도 worktree만으로 프로젝트·포트·계정·DB·함수 서버와 정리 대상이 분리되지는 않는다. 각 환경의 설정·자료·실행 파일·서비스·정리 범위까지 서로 영향을 주지 않도록 격리한 경우에만 환경별 동시 실행을 허용한다. 격리 여부와 제약은 해당 티켓에 남긴다.

### 반복 초기화 검증

초기화·설정 생성 절차를 바꾸면 같은 조건으로 두 번 실행한다. 두 번째 실행에서 생성 값·키·비밀번호와 사용자 설정·주석이 보존되는지, 내용이 같은 파일의 byte·수정 시각이 유지되는지 확인한다. 값 출력 대신 비교 결과를 남긴다. 실제 값 변경은 저장되어야 하며, 실행 중 서비스의 파일 감시 재시작·인증·요청 처리에 불필요한 영향이 없는지도 검증한다. 실행할 수 없는 항목은 환경 제약과 함께 인계한다.

### 실패 분석과 재실행

실패 직후 trace·테스트 결과·관련 서비스 로그를 덮어쓰지 않는 실행별 위치에 보존하고, 실패 시각·검증 revision·미커밋 변경·명령·비밀값을 제외한 환경/데이터 조건을 기록한다. Playwright의 다음 실행이나 서버 시작이 이전 결과·로그를 덮어쓰기 전에 복사하거나 별도 artifact로 남긴다.

그 증거로 구현 결함, fixture/기대값 오류, 환경 문제, 실행 방식의 간섭 중 원인을 분류한다. 원인을 확인할 좁은 검증을 수행하고 수정·환경 조정의 이유를 기록한 뒤 관련 검사를 재실행한다. timeout·재시도 횟수를 늘리거나 재실행이 통과한 것만으로 종결하지 않는다. 원인상 제한 시간·재시도 변경이 타당하면 근거와 실패를 감지할 조건을 함께 남긴다. 결론을 못 내리면 미확인 원인과 남은 검증을 표시한다.

### 문서 검사

문서·스킬·설정 파일을 바꾸면 저장소 루트에서 다음을 실행하고 결과를 PR과 티켓에 남긴다. Node 22 이상에서 `npm ci`로 lockfile의 검사 의존성을 준비한다. 기본 텍스트/링크 검사기는 단독 실행할 수 있지만 모델 설정 검사는 고정된 TOML parser·편집기를 사용한다.

| 명령 | 검사 |
| --- | --- |
| `node scripts/check-docs.mjs` | Git이 추적하거나 무시하지 않는 텍스트 파일의 UTF-8 유효성·BOM 없음·LF·줄 끝 공백·마지막 줄바꿈, 마크다운 내부 상대 링크(코드 블록·인라인 코드 제외)와 HTML의 href·src 상대 경로(script·style·주석 제외. 둘 다 앵커는 미검사), 개발 스킬 정본과 Claude 연결 파일의 name·description 일치, 일반 앱 티켓 상위/하위 ID 중복(템플릿 이력 제외) |
| `node scripts/agent-models.mjs check` | 모델 선택표 schema·지원 강도와 양쪽 native 설정 drift, 실제 TOML 문법·parsed defaults(날짜 최신성은 배정 시 검사) |
| `node --test "scripts/*.test.mjs"` | 검사기 자체의 시험. 정상 저장소 통과와 깨진 링크(마크다운·HTML)·CRLF·BOM·UTF-8이 아닌 바이트·줄 끝 공백·frontmatter 불일치 검출 |
| `git diff --check` | 변경분의 공백 오류 |

문서 변경의 검증 근거는 저장소 밖 검사기 대신 이 명령의 결과로 남긴다. 실패 메시지는 `파일:줄: 문제` 형식이다. 변경 문서의 내부 앵커는 대상 제목·HTML id를 직접 확인한다. 검사기는 앵커 존재를 확인하지 않는다.

### 실행 검증

필요한 도구는 Node 22 이상과 Docker다. Deno와 Supabase CLI는 `npm ci`가 `package.json`에 고정한 버전으로 설치하며 `npm run`이 그 버전을 쓴다. 명령의 정본은 `package.json`의 `scripts`와 [CI](../../.github/workflows/ci.yml)다.

| 명령 | 하는 일 |
| --- | --- |
| `npm ci` | 잠금 파일대로 의존성 설치 |
| `npm run setup:local` | 서명 키 생성(처음 한 번), 로컬 Supabase 시작, `.env.local`과 개발용 사용자 A·B 준비. 다시 실행해도 키와 비밀번호를 유지하고 `.env.local`·`supabase/functions/.env`의 사용자 추가 값·dotenv 구문·주석을 보존한다. 생성 스크립트가 소유한 키만 갱신한다. `supabase/.env`에 Google OAuth 클라이언트 값이 있으면 로컬 Google 로그인도 켠다(`.env.example` 참고, 바꾼 뒤에는 `npm run stop:local` 후 다시 실행) |
| `npm run dev` | 웹 개발 서버(`http://127.0.0.1:55480`) |
| `npm run check:boundaries` | 의존 경계: contracts는 zod만, core는 contracts·core·zod만(Deno API·네트워크·HTTP 타입 금지), 웹은 서버 코드를 `@contracts`로만 가져오고 제품 데이터에 supabase-js `.from`/`.rpc`를 쓰지 않음 |
| `npm run check:deno` | 서버 코드의 Deno 타입·lint·형식 검사 |
| `npm run test:core` | DB 없는 contracts·core 테스트 |
| `npm run test:web` | 웹 단위 테스트(Vitest) |
| `npm run build` | 웹 타입 검사와 정적 빌드 |
| `npm run test:db` | 격리 로컬 DB 테스트: 사용자 격리, 직접 쓰기 차단, 연결 재사용 시 문맥 해제, 원본·큐 원자성, contracts와 DB 한도 parity, 유스케이스 부분 실패 롤백 |
| `npm run serve:functions` | 로컬 Edge Functions 실행(`/functions/v1/api`, `/functions/v1/mcp`). HTTP·MCP 테스트 전에 다른 터미널에서 띄운다 |
| `npm run test:http` | 실제 진입점과 로그인 토큰으로 HTTP 계약 테스트: 인증·입력 오류, 격리, 완료·동시 완료·재시도, 반복 회차, 커서 |
| `npm run test:mcp` | 실제 OAuth 흐름(동적 등록·PKCE·동의 API·코드 교환)으로 받은 MCP 토큰과 공식 MCP 클라이언트로 도구 계약 검사: 토큰 audience 구분, `tools/list` schema, 웹 작성→MCP 완료→웹 확인, HTTP와 같은 결과·오류, 제품 스킬의 도구 이름 |
| `npm run test:e2e` | Playwright(데스크톱·모바일 viewport): 웹 작성→브라우저 동의 화면 승인으로 MCP 연결→MCP 완료→웹 확인, MCP 작성→웹 편집→MCP 확인, 다른 사용자의 URL 접근 거부. 웹 개발 서버는 자동으로 띄운다. 처음 한 번 `npx playwright install chromium` |
| `npm run test:all` | 로컬 통합 테스트를 한 번에(정적 검사·웹 빌드 제외): 로컬 Supabase 준비, Edge Functions가 없으면 띄우고 끝나면 정리, core·DB·HTTP·MCP·E2E를 차례로 실행하고 결과 요약 |
| `npm run stop:local` | 로컬 Supabase 정지(데이터 유지) |

로컬 Supabase 포트는 55420~55429, 웹은 55480, Edge inspector는 8483이다. 다른 로컬 프로젝트·실험(55320~55329)과 겹치지 않는다. CI는 운영 secret 없이 `check` job(문서·공백·Deno·core·웹)과 `integration` job(러너 안의 로컬 Supabase로 DB·HTTP·MCP·E2E 테스트)을 실행한다. 새 검사는 추가되는 단계에서 이 표와 CI에 넣는다.

환경상 실행할 수 없는 검사는 대상 commit·명령·데이터 조건·실행 가능한 격리 환경을 기록해 인계한다. CI에서 수행하는 경우 해당 revision의 결과까지 확인한다.

## 변경과 완료 기록

영향받는 계약·도구 설명·제품 스킬·스키마 색인을 함께 갱신한다. 적용된 migration 이력과 무관한 사용자 변경을 보존한다. 비밀값은 문서·로그·버전 관리에 남기지 않는다.

티켓에는 실제 명령·결과·검증 revision·남은 검사를 남긴다. 티켓 머리말·완료 체크박스·현재 단계 표와 [START-HERE의 현재 상태](../START-HERE.md#현재-상태)는 현재 요약이다. 다음 실제 작업에서 관련 최종 증거를 확인한 기회에 현재 결과와 다음 작업을 맞춘다. 요약 갱신만을 위해 머지 후 상태 전용 PR을 반복하지 않는다.

제출 단계의 명령·실패·조사·배정/인계 기록은 당시의 변경하지 않는 증거로 보존하고 제출 시점 snapshot임을 표시한다. 해당 PR 제출 후의 최종 head·독립 리뷰·필수 CI·머지 결과는 PR 최종 완료 코멘트와 checks가 소유한다. 본 세션이 증거 링크와 실제 결과를 그곳에 남기며, 제출 시점 티켓에서 아직 남은 리뷰·CI·머지를 미리 완료로 표시하지 않는다. 다음 실제 작업의 현재 요약에는 그 외부 증거를 연결하되 과거 실행 기록을 최신 사실처럼 다시 쓰지 않는다.

구현, 자동 검증, 독립 리뷰와 머지, 운영 배포, 실제 에이전트 클라이언트 확인은 각각 기록한다. 서버·DB·웹·플러그인의 배포가 동시에 완료된다고 가정하지 않는다.

검증한 revision의 공개는 [배포 방법](../deployment/release.md), 공개 후 점검과 장애 처리는 [운영 방법](../operations/runbook.md)을 따른다. 실행 기반을 만들 때 문서에 실제 명령·설정·조회 위치를 채우고 재현한 증거를 남긴다.
