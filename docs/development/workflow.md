# 개발과 검증 방법

## 작업의 출발점

[제품 컨셉](../product/concept.md)과 [코드 설계 원칙](../architecture/principles.md)을 읽고 구체적인 사용자 시나리오 하나를 선택한다. 관련 티켓에는 변경 데이터, 유지할 불변 조건, HTTP/MCP 기능, 필요한 화면과 완료 조건을 적는다. 미정인 업무·권한·저장 계약은 구현 전에 확정한다.

설계는 검토 가능한 문서와 구현 인계로 마친다. 구현 시작은 명시적으로 구분한다. 제안·확정·구현·검증·배포 상태를 혼동하지 않는다.

웹 화면 설계·수정 전에는 [디자인 가이드](../design/guide.md)와 그에 연결된 시각 규격·상호작용을 읽는다. 티켓에 소비할 공통 패턴과 상태, 예외, viewport·키보드·초안 보존 검증을 명시한다. 공통 UI 변경은 실제 소비 화면을 함께 검사하고 여러 화면에 영향을 주면 전체 브라우저 E2E를 수행한다.

## 최소 기반과 완결된 기능

첫 기능이 사용하는 도메인·저장·HTTP/MCP·화면·테스트를 함께 연결한다. 공통 기반에는 즉시 사용할 기능과 종료 조건을 적는다. 실제 두 번째 사용처에서 공통성이 확인되면 확장한다. 모든 DB, 모든 API, 모든 화면을 각각 먼저 완성하는 방식은 기본으로 삼지 않는다.

첫 소비자는 [할 일·기록·검색 티켓](../tickets/template-01-task-record-search.md)이다. 기반만 구현했거나 모의 화면만 연결한 상태를 사용자 기능 완료로 보고하지 않는다.

## 기능 계약과 교차 검증

인증·권한·입력·외부 통신·데이터 수명 변경에는 [보안 가이드](../security/guide.md)를 적용한다. 기능 티켓에 보호 대상·신뢰 경계·거부 테스트와 미적용 항목의 이유를 기록한다. 첫 AGENTS.md에도 디자인 및 보안 가이드의 작업별 진입점을 연결한다.

각 기능 티켓에서 아래 항목을 관리한다. 실제 경로·도구 이름·필드·오류는 해당 티켓의 계약에 한 번 정의한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 웹/MCP 동등성 | 지원 행위, 전체 편집 필드, 단건·페이지 탐색, 동일한 권한과 부수효과 |
| 데이터 수명 | 정본, 참조, 삭제·정정 영향, 파생 데이터 갱신 |
| 실패와 재시도 | 부분 실패, 응답 유실, 중복 요청, 충돌, 오래된 비동기 결과 |
| 에이전트 사용 | 도구 schema·설명·실제 호출 일치, 제품 스킬의 필요한 안내 |
| 플러그인 제공 | manifest·연결 설정·스킬의 통합 패키지, 설치·업데이트·서버 호환성과 실제 행동 |

웹 생성→MCP 조회·변경→웹 재조회와 반대 방향을 해당 범위에서 검증한다. 미지원 기능은 표기하며 공통 유스케이스를 쓴다는 이유만으로 동등성을 통과 처리하지 않는다.

## 검증 환경과 증거

세션 시작과 환경 전환 시 checkout·commit·미커밋 변경과 필요한 런타임·연결 도구를 확인한다. 로컬 앱의 접속 대상이 로컬 DB라고 가정하지 않는다. 일반 개발 데이터, 초기화 가능한 격리 테스트, 운영 데이터를 구분한다. 운영 DB를 격리 테스트 대신 사용하지 않는다.

| 변경 대상 | 검증 위치 |
| --- | --- |
| 도메인 판단 | DB 없는 단위 테스트 |
| 저장·RLS·원자성·경쟁 | 실제 격리 DB 통합 테스트 |
| HTTP/MCP | 인증·입출력·오류 계약과 실제 호출 |
| 웹 흐름 | 관련 브라우저 E2E, 모바일·데스크톱 상태와 조작 |
| 검색 | 실제 모델의 관련/무관 질문 평가, 원문 접근, 색인 지연·실패 구분 |
| 제품 스킬 | 자동 계약 검사와 별도로 실제 지원 클라이언트에서 행동 확인 |
| 문서 | UTF-8 BOM 없음·LF, 링크, 공백, 문서 간 계약 일치 |

검증 명령은 실행 스크립트가 생길 때 확정한다. 환경상 실행할 수 없는 검사는 대상 commit·명령·데이터 조건·실행 가능한 격리 환경을 기록해 인계한다. CI에서 수행하는 경우 해당 revision의 결과까지 확인한다.

## 변경과 완료 기록

영향받는 계약·도구 설명·제품 스킬·스키마 색인을 함께 갱신한다. 적용된 migration 이력과 무관한 사용자 변경을 보존한다. 비밀값은 문서·로그·버전 관리에 남기지 않는다.

티켓에는 실제 명령·결과·검증 revision·남은 검사를 남긴다. 구현 완료, 자동 검사 통과, 운영 배포, 실제 에이전트 클라이언트 확인은 각각 기록한다. 서버·DB·웹·플러그인의 배포가 동시에 완료된다고 가정하지 않는다.

검증한 revision의 공개는 [배포 방법](../deployment/release.md), 공개 후 점검과 장애 처리는 [운영 방법](../operations/runbook.md)을 따른다. 실행 기반을 만들 때 문서에 실제 명령·설정·조회 위치를 채우고 재현한 증거를 남긴다.
