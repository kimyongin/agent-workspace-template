## 목표와 기준 문서

이 티켓은 [PRD](../product/concept.md)의 템플릿 완성 범위를 구현하는 순서와 완료 기준을 소유한다. 목적·필수 기본 기능·기본 예제 엔터티(`Entity`)·지원 클라이언트는 PRD와 [ADR](../adr/README.md)이 정본이며 이 티켓에 복제하지 않는다. 작업 중 PRD·ADR을 벗어나야 하면 [ADR-0008](../adr/0008-document-ownership.md)에 따라 멈추고 사람의 승인을 받는다.

T02-4는 PRD의 중립적인 기본 앱을 구현하고, T02-5는 별도 복사본에서 단일 엔터티를 작은 실제 도메인으로 바꾸어 재사용성을 검증한다.

일상적인 구현 선택은 에이전트가 직접 해결한다. 실제 서비스 생성·운영 공개·비용이 발생하는 작업은 ADR-0008의 실행 예외에 따라 사람이 요청·승인한 범위에서만 진행한다.

## 현재 상태와 기존 티켓 관계

현재 저장소에는 설계·개발·디자인·보안·배포·운영 문서와 두 종류의 스킬이 있다. 실행 코드, DB migration, CI, 설치 가능한 플러그인 연결 설정은 아직 없다. [제품 스킬](../../plugins/workspace/skills/workspace/SKILL.md)은 초안이며 실제 도구 계약과 실클라이언트 검증이 필요하다.

이 티켓은 전체 구현 순서와 템플릿 완성 기준을 소유한다. [Template-01](template-01-task-record-search.md)의 S1a는 T02-2, S1b는 T02-3에서 이어서 구현한다. 기존 상세 계약·실패 경로·검증 조건은 유지하되 중복된 새 구현을 만들지 않는다. Template-01의 후속 항목인 사용자 원칙은 T02-3에 포함한다. 그 티켓의 운영 출시 게이트는 T02-6에서 완료하며 첫 기능 착수의 선행 조건으로 취급하지 않는다.

2026-10-01 저장소 종합 검토(기준 `bd7a644`)의 개선 항목은 별도 티켓을 만들지 않고 해당 단계에 넣었다. 문서 불일치·공유 schema·핵심 기술 실험·상태 서술·문서 검사는 T02-1, 문서 검사의 CI 실행은 T02-2, 제품 스킬 이름·라이선스·템플릿 저장소 설정은 T02-6이 담당한다.

기존 문서의 ‘스켈레톤’은 구현형 템플릿의 출발 상태로 해석한다. 범용 Entity/Item 저장소를 선행 구축하지 않는 원칙은 유지한다. 도메인별 타입·테이블·유스케이스를 두면서 반복되는 배선과 표현을 재사용한다.

## 유지할 기준과 정리할 내용

- HTTP와 MCP는 같은 유스케이스를 실행하고 권한·결과·필드·오류·재시도 의미를 맞춘다.
- 업무 규칙과 인프라를 분리하고 실제 DB에서 사용자 격리·트랜잭션·경쟁을 검증한다.
- 스킬의 안내와 서버의 권한·일관성 보장을 구분한다.
- 제목+요약 단일 벡터, 본문 키워드 검색과 원문 읽기를 기본 검색 방식으로 유지한다.
- GitHub Pages·Supabase·Google OAuth·Pinecone Inference·pgvector를 기본 기술 선택으로 유지한다.
- 상세 디자인·보안·운영 기준은 유지한다. 중복 설명과 누적된 과거 검증 서술만 담당 문서·이력으로 정리한다.
- 개발 스킬에서 아키텍처·검색·인증의 상세 설명을 줄이고 담당 문서 링크로 연결한다. 작업 선택·실행 순서·검증·인계 절차는 남긴다.
- 변경한 구현과 원칙·가이드·제품/개발 스킬을 함께 맞춘다.

## T02-1 — 계약과 문서 정리

### 작업

1. PRD(2026-10-01 정리 완료)와 다른 문서의 불일치를 정리한다.
   - Template-01 구현 순서 3번이 사용자 원칙을 후속 기능으로 두는 부분을 PRD에 맞춰 고친다.
   - 폴더 구조·아키텍처 등에서 사용자 데이터 개념을 가리키는 "판단 기준"을 "사용자 원칙(principles)"으로 통일한다. 개발용 코드 설계 원칙과의 구분은 유지한다.
   - 폴더 구조의 "범용 Entity/Item 저장소를 만들지 않는다"와 확정한 예제 `Entity`의 차이를 명시한다. 예제는 명시적인 컬럼을 가진 단일 테이블이며 금지 대상은 동적 키–값·범용 payload 저장소다. 예제 이름은 PRD를 따른다.
   - 폴더 구조의 "다음 작업"을 이 티켓으로 갱신한다.
2. 할 일·기록·원칙·태그·검색의 웹/HTTP/MCP 행위·필드·목록/상세·페이지 탐색·오류 계약표를 만든다. 수정·삭제·완료·원칙의 적용/비활성 의미와 관계 삭제 영향을 정한다.
3. 도메인 변경 계약을 정한다. 모델/검증, DB migration, DTO, HTTP/MCP, 폼/목록/상세, 검색 표현과 원문 링크, 제품 스킬 중 바꿀 위치와 공통으로 유지할 위치를 표시한다.
4. 새 엔터티 속성의 타입·필수값·검증·표시 이름이 각 접점에서 어긋나지 않도록 공유할 정의와 변환 경계를 결정한다. 브라우저가 서버·DB 내부 모듈을 가져오게 하지 않는다. HTTP 입력 검증·MCP 입력 schema·웹 폼이 함께 쓰는 schema 정의 하나를 정본으로 정하고, 손으로 맞출 위치(DB migration·제품 스킬 등)와 그 불일치를 잡는 검사를 기록한다. 생성 스크립트·공통 배선 도구는 여기서 만들지 않고 T02-5에서 반복이 확인된 범위에 한해 도입한다.
5. PRD의 단일 예제 엔터티의 id·prop1·prop2 등의 타입·필수값·검증과 목록·상세·편집 계약을 정한다. 별도로 T02-5에서 속성 변경을 시험할 작은 실제 도메인 하나를 선택한다. 전환 시험도 단일 엔터티를 기준으로 하며 두 번째 테이블이나 완성된 도메인 서비스 구축을 요구하지 않는다.
6. 런타임·웹 프레임워크·SQL 드라이버를 조사·선정해 근거와 버전을 기록한다. 지원 클라이언트인 Claude·Codex 각각의 플러그인 manifest·MCP 연결/앱 참조·스킬 포함 형식을 공식 자료로 확인하고, 공유 스킬을 양쪽 패키지에 넣는 방식을 정한다. Google 로그인과 MCP OAuth를 별도 계약으로 정하고 두 클라이언트의 OAuth 지원 차이를 기록한다.
7. 개발 스킬의 중복 설명을 담당 문서 링크로 대체한다. 제품 스킬의 공통 흐름과 도메인 참고 자료 확장 위치를 구분한다. 개발 스킬의 name·description을 바꾸면 Claude 연결 파일(`.claude/skills/develop-agent-app/SKILL.md`)도 맞춘다. 여러 문서에 반복된 같은 경고 문장은 담당 정본 한 곳에 두고 링크로 바꾸되, 디자인·보안·운영의 보호 기준과 검증 항목은 줄이지 않는다.
8. Template-01의 체크 항목을 후속 단계에 매핑한다. 과거 검증 기록은 보존 가능한 이력으로 정리하고 현재 상태와 다음 행동이 먼저 보이게 한다. 저장소의 구현 상태 서술은 START-HERE의 "현재 상태"와 각 티켓에만 두고, 다른 문서에 흩어진 "설계 단계·구현 전" 같은 상태 문구는 제거하거나 START-HERE 링크로 바꾼다.
9. 핵심 기술 가정을 작은 격리 실험으로 먼저 확인하고 결과로 6번의 선정을 확정한다.
   - Edge Function의 직접 Postgres 트랜잭션: 채택 후보 드라이버와 연결 풀에서 검증된 Actor 문맥의 트랜잭션 한정 전달, 연결 재사용 시 문맥 해제, 원본 저장과 `pgmq.send`의 함께 롤백. 성립하지 않으면 업무 규칙 없이 원본 저장과 큐 등록만 하는 SQL 함수를 사용자 JWT로 호출하는 대안을 평가하고 아키텍처를 갱신한다.
   - Claude·Codex의 MCP OAuth: 각 클라이언트의 원격 MCP 인증 요구(클라이언트 등록 방식·metadata·scope·callback)와 Supabase Auth로 구성 가능한 범위를 확인하고, 최소 도구 하나로 양쪽의 인증·호출을 시험한다.
   - 임베딩: 후보 모델의 소규모 한국어 관련/무관 질의 평가. 위 두 항목보다 뒤에 수행해도 된다.
   - 실험에는 격리 Supabase 프로젝트·클라이언트 연결이 필요하다. 서비스 생성과 비용은 사용자가 요청·승인한 범위에서 진행하고, 운영 프로젝트·운영 데이터를 사용하지 않는다.
10. 문서 검사 스크립트를 `scripts/`에 추가한다. UTF-8 BOM 없음·LF·줄 끝 공백·내부 상대 링크·개발 스킬 정본과 Claude 연결 파일의 name·description 일치를 검사하고, 로컬 실행 방법을 개발 방법 문서에 적는다. 이후 문서 변경 기록은 저장소 밖 검사기 대신 이 명령의 결과를 근거로 남긴다.

### 완료 조건

- [ ] 기본 기능·첫 버전 범위·후속 기능이 구분되고 원칙/RAG가 선택 기능으로 빠지지 않는다.
- [ ] 반복 일정·공유·첨부·실시간 갱신은 첫 버전 포함 여부를 명시한다. 미합의 범위를 자동 추가하지 않는다.
- [ ] 데이터 수명·권한·경쟁·재시도와 도메인 변경 계약을 다음 단계가 구현할 수 있다.
- [ ] 일상적인 파일명·배치·라이브러리 선택을 불필요하게 사용자에게 되묻지 않는다. 실제 미정인 업무 의미만 결정 요청으로 분리한다.
- [ ] 링크·인코딩·문서 간 역할을 확인하고 기존 보호·검증 기준이 사라지지 않는다.
- [ ] 사용자 원칙의 위치·용어와 예제 `Entity`의 설명이 제품 컨셉·폴더 구조·Template-01·이 티켓에서 일치한다.
- [ ] 공유 schema 정본, 파생 대상, 수동 동기화 대상과 그 검사가 기록되고, T02-5에서 비교할 예상 변경 파일 목록이 있다.
- [ ] 트랜잭션·MCP OAuth 실험의 revision·환경·명령·결과·채택/기각 판단이 기록되고 바뀐 기술 선택이 관련 문서와 개발 스킬에 반영된다. 실행하지 못한 실험은 차단 원인과 함께 미완료로 남긴다.
- [ ] 티켓과 START-HERE 밖에 저장소 구현 상태 서술이 남지 않는다.
- [ ] 깨끗한 checkout에서 문서 검사 명령 하나로 검사가 재현되고, 의도적으로 깨뜨린 링크·CRLF·BOM·frontmatter 불일치를 각각 검출한다.

## T02-2 — 실행 기반과 할 일·기록

### 작업

- 실제 package/config, 잠금 파일, 실행·타입/빌드·테스트 명령, 환경변수 예시와 최소 CI를 만든다. 최소 CI는 push·PR에서 T02-1의 문서 검사와 `git diff --check`도 실행하며 운영 secret을 사용하지 않는다.
- 최소 CI를 `main` 브랜치 보호의 필수 상태 검사(required status check)로 등록한다. 2026-10-01 기준 `main` 보호는 PR 필수·관리자 포함·선형 이력만 설정되어 있고 필수 검사는 없다. GitHub는 최근 실행된 검사 이름만 선택할 수 있으므로 CI가 한 번 실행된 뒤 job 이름으로 등록하고, PR 브랜치가 최신 `main`을 포함해야 하는지(strict)도 정한다. 저장소 관리자 권한이 필요하며 사용자 승인 후 에이전트가 GitHub API로 등록하거나 사람이 설정한다. 등록 후 보호 설정 조회 결과를 티켓에 남긴다. CI의 job 이름을 바꾸면 필수 검사 설정도 함께 바꾼다. 새 프로젝트에서 같은 설정을 하는 단계는 T02-6의 초기화 절차에 넣는다.
- 격리 DB migration, 사용자 인증·Actor·DB 권한 문맥, HTTP/MCP 조립을 구현한다.
- Template-01 S1a의 할 일 생성·조회·완료 결과 저장·직접 기록 작성·조회와 필요한 웹 화면을 연결한다.
- [T02-1 계약](template-02-t02-1-contracts.md)의 반복 할 일(회차 계산·회차 기록·중단·재개)을 웹·HTTP·MCP에 연결한다. 회차 계산은 DB 없는 core 테스트로 매일·매주·매월, 그 달에 없는 날짜, 시간대 경계, 중단 기간, 규칙 수정을 검증한다.
- T02-1 계약의 기본 수정·삭제·목록 탐색을 연결한다. 후속 작업이 있으면 명시하고 전체 완료로 표시하지 않는다.
- 완료와 기록 저장, 필요한 색인 작업 등록의 원자성·충돌·멱등성을 구현한다.

## T02-3 — 사용자 원칙·RAG·지식 연결

### 작업

- 사용자 원칙의 관리·조회·현재 유효 상태·적용 조건을 웹과 MCP에 구현한다. 과거 판단 기록과 현재 원칙을 혼동하지 않도록 연결/정정 정책을 적용한다.
- 할 일·기록·원칙과 도메인 대상을 연결하는 최소 계약을 구현한다. 대상 존재·소유권·삭제 시 처리·상세 링크를 보장한다. 범용 관계 엔진을 선행 구축하지 않는다.
- 원칙 탐색 경로를 명시한다. 벡터 검색 대상과 별도 원칙 조회 범위를 정하고, 에이전트가 현재 적용할 원칙을 빠짐없이 찾을 수 있는 경로를 제공한다.
- Template-01 S1b의 pgmq·worker·임베딩·pgvector·키워드/의미 검색·원문 조회를 구현한다.
- 실제 한국어 자료로 후보 모델·차원·입력 예산·검색 임계값을 검증해 확정한다. 모델 설정과 제목/요약 상한 후보를 미검증 확정값으로 취급하지 않는다.
- 제품 스킬을 실제 도구 계약에 맞추고 원칙 확인→관련 활동 검색→원문 확인→조건 비교→요청한 실행→결과 축적을 연결한다.

- [ ] 저장 금지 요청, 가정과 실제 결정, 오래된 원칙과 새 지시, 검색 실패 사례에서 제품 스킬의 동작을 확인한다.

## T02-4 — 단일 예제 엔터티·화면·플러그인

### 작업

- T02-1에서 확정한 단일 예제 엔터티(id·prop1·prop2 등)의 명시적인 컬럼·검증·기본 CRUD를 DB부터 웹/MCP까지 구현한다. 엔터티 목록·상세·생성·편집을 제공하고 특정 도메인 업무나 메인/서브 구조를 기본 예제에 추가하지 않는다.
- 엔터티 상세에서 관련 할 일·기록·원칙을 보고 이동하게 한다. 에이전트에도 같은 연결을 조회할 수 있게 한다.
- 실제 디자인 토큰과 공통 목록·상세·폼·모달·검색·상태 표현을 구현한다. 브랜드·앱 이름·메뉴·도메인 표시를 바꾸는 위치를 모은다.
- 제품 스킬에 기본 예제의 속성과 관련 지식을 읽는 방법을 연결하고, 새 앱에서 도메인 용어·원문 해석·업무 규칙 안내를 추가할 위치를 마련한다.
- Claude·Codex 각각의 실제 manifest·MCP 연결을 만들고 같은 제품 스킬을 패키징한다. 클라이언트별 식별자·버전·연결 대상을 설정하고 제품 스킬을 클라이언트별로 복제하지 않는다. 개발 스킬을 제품 패키지에 포함하지 않는다.
- 샘플 데이터와 제거/교체 절차를 제공한다. 예제 데이터는 개발/격리 환경에만 명시적으로 넣는다.

### 완료 조건

- [ ] 기본 예제가 테이블 하나의 명시적인 속성으로 구현되고, 주요 화면과 웹/MCP 엔터티 작업이 실제 데이터로 동작한다.
- [ ] 모바일·데스크톱, 긴 원문·빈 상태·오류·초안 보존·목록 복귀를 디자인 가이드에 따라 확인한다.
- [ ] Claude와 Codex 각각에서 플러그인 설치·연결·스킬의 원문 확인 행동을 검증한다. 한쪽 결과로 다른 쪽을 통과 처리하지 않는다. Claude는 Claude Code, claude.ai 웹·데스크톱(개인 계정 플러그인 업로드), 모바일(커넥터와 스킬 동작 여부)을 각각 기록한다([표면별 제공 방식](template-02-t02-1-contracts.md#플러그인-형식-claudecodex)).
- [ ] 브랜드 변경과 예제 엔터티 교체 위치가 문서화되고 불필요한 공통 기능 수정이 없다.

## T02-5 — 예제 엔터티의 도메인 전환 검증

### 작업

- 별도 격리 checkout/프로젝트에서 중립적인 예제 엔터티를 작은 실제 도메인 하나로 교체한다. id는 식별자로 유지하고 prop1·prop2 등의 이름·타입·검증을 바꾼다. 단일 테이블로 검증하며 기본 템플릿에는 중립적인 예제를 유지한다.
- 엔터티 속성·작은 업무 규칙·목록/폼/상세·브랜드·제품 스킬을 바꿔 동일한 지식 활용 흐름을 실행한다.
- 실제 변경 파일·반복 수정·공통 기반 변경과 이유를 기록한다. 예상한 변경 위치와 비교한다.
- 반복성이 확인된 배선에 한해 작은 생성 스크립트나 공통 함수를 도입한다. 모든 도메인을 해석하는 메타데이터 엔진은 만들지 않는다.

### 완료 조건

- [ ] 도메인으로 바꾼 검증용 앱에서도 인증·할 일·기록·원칙·검색의 동작이 유지된다.
- [ ] 새 필드와 검증이 DB·웹·HTTP·MCP에서 일치하고 연결된 지식/원문 조회가 가능하다.
- [ ] 도메인 교체 때문에 공통 기반을 수정한 부분은 원인과 해결 또는 남은 한계를 명시한다.
- [ ] 모델·화면·설정·스킬 중심의 변경으로 새 앱을 만들 수 있다는 실제 diff와 실행 증거가 있다.

- 초기화 절차에 템플릿 기록의 정리를 넣는다([Template-03 T03-5](template-03-docs-for-people.md#t03-5--템플릿-기록과-새-앱-문서-분리-방침)의 분류를 따른다). 템플릿 티켓(`template-NN-…`)과 `experiments/`는 보존한다. START-HERE의 현재 상태·다음 단계와 읽는 순서 표의 템플릿 티켓 행, 폴더 구조의 "다음 작업" 절, 아키텍처 첫 문단의 "구현 순서는 Template-02"는 새 앱 기준으로 바꾼다. 새 앱의 PRD를 쓸 때 PRD의 Template-02 문장도 바꾸도록 사람에게 안내한다.
- 프로젝트 안내 페이지(`docs/overview.html`)를 웹 배포와 함께 공개할지 정하고, 공개하지 않으면 README에 내려받아 브라우저로 여는 방법을 적는다. GitHub 저장소 화면에서는 HTML이 원문 코드로 보인다([Template-03 T03-4](template-03-docs-for-people.md#t03-4--overview-유지-장치)).
- 신규 프로젝트 안내에 외부 서비스별 비용이 생기는 지점(Supabase·Pinecone·GitHub Pages)과, 비용이 드는 작업은 사람이 지시한다는 점을 적는다. 금액은 쓰지 않고 [운영 방법](../operations/runbook.md)의 비용·한도 점검으로 연결한다.
