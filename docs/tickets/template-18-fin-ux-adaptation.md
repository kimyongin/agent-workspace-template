## 목표와 승인 범위

사용자는 템플릿의 원본인 fin의 UX를 조사해 적용할 내용을 정리하도록 요청했고, 2026-10-04 “좋아. 티켓 정리해서 개발해줘”로 구현을 승인했다. 금융 도메인을 걷어내고 단순 엔터티를 유지한다는 조건을 유지한다. 조사 기록의 제안/미정 표현은 당시 상태이며 아래 확정 범위가 구현 기준이다. 운영 배포는 이번 요청에 포함하지 않는다.

## 확정 범위와 구현 티켓

- 모든 폭에서 엔터티 / 활동 / 원칙 / 검색 하단 탐색과 더보기(태그 관리 / 사용 가이드 / 로그아웃)를 제공한다. 첫 경로와 기존 상세 URL은 유지한다.
- 활동은 기존 할 일/기록 경로의 로컬 링크로 연결한다. 기록만 날짜별로 묶고 접힘·목록 복귀를 보존한다.
- 필터는 상시 표시하며 간격과 구획을 정돈한다. 작성은 종류(필요한 경우) → 제목·요약·본문 → 연결·태그·일정 순서다.
- 명시적 보기/편집, 문서형 상세, 엔터티 문맥 작성, 태그 사전의 한 영역 편집, 중립적 첫 사용 안내를 구현한다.
- 기존 상세 페이지를 유지한다. route 기반 읽기 overlay는 후속 검토이며 이번 완료 조건에 포함하지 않는다.
- Entity 속성·검증과 서버/DB/MCP/검색 계약은 변경하지 않는다. 태그 필터는 단일 선택이다.

## 조사 범위와 근거의 한계

- 배포 화면: [fin](https://kimyongin.github.io/fin/), [template](https://kimyongin.github.io/agent-workspace-template/). 기존 로그인 상태로 읽기·탐색하고 템플릿의 빈 작성창을 열고 닫았다. 저장·수정·삭제·연결 변경은 하지 않았다.
- fin 실제 관찰: 자산 목록, 활동의 할 일과 날짜별 기록, 기록 읽기 모달, 보조 메뉴, 첫 사용 가이드, 원칙 화면 진입. 금융 데이터 값·개인 기록 내용은 이 조사 문서에 옮기지 않는다.
- template 실제 관찰: 할 일의 빈 상태·필터, 상단 탐색, 할 일 작성창. 390×844에서 메뉴·로그아웃이 여러 줄을 차지하고 목록 앞에 큰 필터 구획이 있는 것을 확인했다. 넓은 화면의 상단 메뉴 배치도 관찰했다.
- fin 좁은 화면에서는 검색·기간·태그가 기록보다 앞서 긴 세로 구획을 차지했다. fin의 넓은 화면은 이번 브라우저 캡처에서 viewport 전환을 확정하지 못해 코드 근거와 구분한다. 모든 viewport·키보드·실기기·스크린리더를 검수한 결과가 아니다.
- 로컬 fin은 위 branch의 코드다. 미커밋 변경은 `.claude/settings.local.json`, `docs/tickets/README.md`에 있으며 보존했다. 배포 source와 로컬 commit의 동일성을 확인하지 않았으므로 화면 관찰과 코드 근거를 각각 기록한다.
- 본 세션이 조사·설계 문서를 직접 작성했다. 별도 구현/리뷰 세션과 모델 평가를 수행하지 않았으며 backend effort·실청구액을 관찰하지 않았다.

## 제안하는 사용자 흐름

### fin 정본 가이드 추가 대조

첫 조사에서는 template 디자인 정본과 fin 구현 코드를 읽었으나 fin의 디자인 정본을 직접 읽지 않았다. 사용자 후속 질문을 받고 fin의 `docs/design/modal-guidelines.md`, `component-system.md`, `list-interaction-guidelines.md`, 설계 문서 지도와 `docs/tickets/ui-35-list-reading-and-mobile-interaction.md`의 최신 문서 표현/예외를 추가 확인했다. 코드·화면 조사만으로 정본 검토까지 마쳤다고 보지 않는다.

- fin의 모달 계층은 페이지→대상 모달→짧은 확인의 최대 2단계다. 일반 편집·태그 관리·대상 탐색을 2차에 넣지 않고 최상위만 활성화하며 초안·스크롤·초점을 보존한다. template의 기존 상호작용 가이드와 일치하므로 유지한다.
- 일반 등록/편집은 640px 미만 전체 화면, 넓은 화면 중앙이며 헤더/본문/footer 중 본문만 스크롤한다. fin은 일반 최대42rem·확인32rem, template는 일반40rem·현재 확인28rem이다. 용도별 배치는 가져오되 폭 수치와 색은 template 정본을 유지한다. 드로어/표 편집 예외는 일괄 채택하지 않는다.
- fin의 일반 대상 상세는 바로 편집·한 초안·단일 저장이 기본이다. 할 일/기록에는 이후 목록 가이드의 명시적 보기/편집과 2026-10-01 문서형 읽기 예외가 우선한다. 모든 대상을 읽기/편집 모드로 획일화하거나 오래된 직접 편집 규칙으로 활동 읽기를 없애지 않는다.
- 읽기 전용 짧은 값의 정렬·크기·선택/복사는 공통 폼에서 유지한다. fin의 잠금 아이콘/입력 상자는 할 일·기록의 문서형 읽기에 적용하지 않는 명시 예외이며 template에도 모든 읽기 값을 입력칸으로 표현하는 변경을 제안하지 않는다.
- 보기·편집은 제목 끝 기준선에 이어지는 하나의 묶음이다. 공간이 부족하면 묶음 전체가 다음 줄로 가고 각 조작의44px 영역은 정상 레이아웃에서 확보한다. 실제 이동은 링크, 모달 실행은 버튼이다. 이 구체적인 기준은 목록 조작 구현에 반영한다.
- 한 대상의 태그·본문·일정은 한 저장에 포함하고 별도 blur 저장이나 속성별 모달을 만들지 않는다. fin의 금융 변경 메모/태그를 받는 저장 확인은 승인된 도메인 예외이므로 template 일반 저장에 도입하지 않는다.
- 연결 선택은 같은 폼/영역에서 처리하고 태그 사전 관리는 별도 1차 진입으로 유지한다. fin 활동의 연결/태그를 접지 않는 특정 예외를 모든 폼에 일반화하지 않는다. template에서 선택 영역을 접을 때는 값·오류 표시와 오류 시 펼침을 보장한다.

따라서 아래의 문서형 읽기·같은 대상의 단일 편집·확인 전용 2차·URL 보존 제안은 유지한다. 엔터티의 바로 편집 가능 상세를 채택할지는 구현 전 비교 대상으로 남기며 서버의 단일 저장/권한 계약을 바꾸지 않는다. fin 티켓의 과거 검증 수치는 template의 검증 성공으로 전용하지 않는다.

### 탐색과 활동

주요 메뉴는 `엔터티 / 활동 / 원칙 / 검색`, 보조 메뉴는 `태그 관리 / 사용 가이드 / 로그아웃`으로 제안한다. 엔터티 명칭은 현재 그대로 유지하고 새 앱에서 바꾼다. 기존 첫 진입은 할 일로 유지하며 엔터티를 먼저 보여주는 변경은 이번 안에 넣지 않는다.

작은 화면은 4개 주요 링크와 더보기로 하단 탐색을 제안한다. fin 정본은 넓은 화면도 하단 고정이다. template에서 같은 모든 폭 하단을 쓰는 안과 넓은 화면의 상단 탐색 안을 비교하며 아직 채택하지 않았다. 현재 위치는 route에서 결정하고 실제 이동은 링크를 사용한다. 하단 높이·safe-area만큼 본문 여백을 두고 키보드/200% 확대에서 본문·액션이 가려지지 않게 한다. fin의 친구/포트폴리오 전환 슬롯은 만들지 않는다.

활동은 할 일/기록의 공통 진입점이다. 우선 `/tasks`, `/records`를 유지한 두 로컬 탐색 링크로 구성한다. 완료된 할 일을 기록과 하나의 데이터로 합치지 않고, 기록 작성도 할 일 없이 가능하다. 작은 화면에서 두 긴 목록을 동시에 쌓기보다 하나씩 읽게 한다. 할 일 완료 후 생성한 결과 기록을 열고, 돌아갈 때 기존 할 일 조건·페이지·스크롤·초점을 복원한다.

### 목록과 상세

기록은 기존 `occurred_at` 안정 정렬과 페이지 경계를 유지하고 업무 시간대에 따라 날짜별로 묶는다. 같은 날짜의 다음 페이지는 기존 그룹에 합치며 ID로 중복을 제거한다. 접힘 상태를 상세 왕복/더 보기로 초기화하지 않는다. 날짜 제목에 전체 건수처럼 보이는 미확정 개수를 표시하지 않는다. 검색 결과는 현재 관련도/검색 순서를 유지하고 날짜 그룹을 강제하지 않는다.

목록은 제목·짧은 요약·날짜/상태·읽기 태그를 순서대로 보여준다. 제목은 선택·복사할 수 있고 명시적인 상세 링크가 있다. 편집 가능 대상에는 가까운 편집 조작을 제공한다. 기존 완료·중단·재개 규칙을 그대로 따르고 삭제는 보조 위치에서 실제 영향 확인을 거친다.

읽기는 제목→요약→필요 메타데이터→본문→관련 대상 순서의 문서로 만든다. 긴 본문 앞에 비어 있는 연결 섹션을 여러 개 쌓지 않고 관련 정보는 본문 뒤에서 확인하게 한다. 엔터티는 짧은 속성표와 관련 할 일·기록·원칙으로 구성한다. DB 버전 같은 구현 정보의 일상 노출은 줄이고 충돌 안내에 필요한 의미는 유지한다.

첫 적용은 기존 상세 URL/페이지를 보존한다. fin식 읽기/편집 모달 전환은 후속 단계에서 목록 진입 시 overlay, 직접 URL 진입/새로고침 시 독립 상세를 제공하는 방식으로 검토한다. 같은 대상의 모달 두 개를 겹치지 않고 삭제/변경 버리기만 2차 확인을 허용한다. 읽기→편집→취소/저장은 진입한 읽기로, 목록에서 바로 편집→취소/저장은 목록으로 복귀한다.

### 필터와 작성

fin 정본은 모든 필터를 상시 표시하고 상세 필터 접기를 허용하지 않는다. 먼저 같은 구획의 배치/여백을 정돈하는 안을 검토한다. template의 별도 개선 후보는 대표 검색/필수 조건을 기본 구획에 두고 나머지를 `상세 조건`에 두는 것이다. 접기를 채택한다면 적용된 조건 수/이름·전체 해제를 접힌 상태에서도 보여줘야 한다. 아직 채택하지 않았으며 fin에서 가져온 규칙으로 표시하지 않는다. 잘못된 날짜는 오류를 표시하며 무시하지 않는다. 모든 목록에 검색을 신규 구현하지 않고 기존 목록 API와 SearchPage의 기능을 구분한다.

작성은 제목·요약·본문을 먼저 읽고, 연결 엔터티·태그·일정 등 보조 입력을 뒤에 둔다. 반복 종류를 먼저 골라야 하는 할 일은 종류 선택을 유지한다. 필수값·길이·반복 규칙을 fin의 규칙으로 바꾸지 않는다. 실패하면 초안을 유지하고 변경 버리기/닫기/뒤로가기의 공통 보호를 확인한다.

엔터티 상세의 `관련 할 일 추가 / 기록 작성`은 기존 `entity_id`를 초안에 미리 채우는 UI 진입으로 제안한다. 엔터티 자체를 수정하거나 새 관계 테이블을 만들지 않는다. 생성 성공 후 관련 목록을 갱신하고 실패/취소는 엔터티 상세와 초안을 보존한다.

### 첫 사용과 연결

사용 가이드는 `엔터티 하나 만들기 → 할 일 또는 기록 작성 → 제품 플러그인 연결 → 검색/원문 읽기 → 명시한 결과 저장 후 웹 확인`으로 구성한다. 첫 엔터티 없이도 할 일/기록을 만들 수 있다는 점을 안내한다. 빈 목록에서 허용된 첫 행동과 가이드로 이동할 수 있게 한다.

Claude/Codex의 MCP 연결과 제품 스킬 패키지를 함께 안내한다. 주소·패키지 링크는 새 앱의 공개 설정에서 만들고 fin의 주소/브랜드를 복사하지 않는다. OAuth 연결과 스킬 설치를 완료 상태 하나로 오인하지 않게 한다. URL 복사 성공/실패를 텍스트로 알리고 클립보드 실패 시 선택·복사 가능한 주소를 남긴다. 실제 클라이언트 지원 문구는 구현 시 공식 문서와 해당 앱의 검증 이력으로 다시 확인한다.

## 유지할 데이터·API·권한 계약

- Entity는 테이블 하나와 `id`, `prop1`(문자), `prop2`(nullable 정수), `prop3`(nullable 날짜), `prop4`(`a/b/c`)를 그대로 쓴다. 이름·필수값·검증 변경은 이 UX 조사에 포함하지 않는다.
- 기존 할 일·기록·원칙·태그·엔터티 연결과 HTTP/MCP 공통 유스케이스를 유지한다. 첫 적용에 migration·새 API·MCP tool은 필요하지 않다.
- 목록 필터의 단일 `tag_id`, 검색 모드/기간/상태, cursor, 멱등 request ID, `expected_version`을 유지한다. fin의 다중 태그 AND/OR·자동 검색450ms·최근30일 기본 기간은 채택하지 않는다. 도입하려면 별도 서버 계약/영향 설계가 필요하다.
- 원본 저장 성공과 색인 완료를 구분한다. 안내 화면을 위해 검색/임베딩을 자동 실행하거나 운영 시험 기록을 만들지 않는다.
- 금융 자산·계좌·보유·배분·시세·수익률·거래·스프레드시트 편집·금융 변경 전후 원장을 넣지 않는다. fin의 공유·친구·방문자·별도 보기 비밀번호·프로필 전환도 소유자 한정 ADR과 다른 기능이므로 제외한다.
- 원칙 이력·당시 원칙 snapshot·제품 피드백 수집은 화면 참고만으로 신규 기능화하지 않는다. 현재 원칙 연결과 당시 판단 본문의 의미를 유지한다.

## 구현 순서와 인계

아래는 제안 분할이며 구현 승인은 아직 받은 것으로 취급하지 않는다. 한 PR에서 공통 기반만 만들고 소비 화면을 다음 PR로 넘기지 않는다. 기존 디자인 규격과 충돌하는 보편적 패턴은 해당 가이드·소비 화면·회귀 검증을 함께 갱신한다.

| 순서 | 작은 PR 범위 | 머지 후 직접 확인할 결과 | 주요 변경 후보 |
| --- | --- | --- | --- |
| 1 | 탐색 재구성·활동의 할 일/기록 링크 | 모바일 주요 메뉴가 여러 줄의 상단 영역을 차지하지 않고 할 일과 기록을 오갈 수 있음 | App, 공통 탐색, CSS, 활동 페이지 |
| 2 | 기록 날짜 그룹·명시적 보기/편집 | 기록을 날짜별로 접고 읽고 편집한 뒤 같은 문맥으로 복귀 | RecordsPage, 공통 Timeline, 상세 진입/복귀 |
| 3 | 필터 구획·작성 순서 | 작은 화면에서 목록/필수 입력을 먼저 보고 선택 조건과 오류를 놓치지 않음 | 대표 할 일/검색 화면, Field/ContentForm, 후속 소비 화면 |
| 4 | 문서형 상세·엔터티 문맥 작성 | 본문부터 읽고 엔터티가 미리 연결된 할 일/기록을 생성 | 상세 페이지, 공통 읽기 표현, 기능 폼 |
| 5 | 첫 사용·플러그인 안내 | 새 사용자가 예제 데이터부터 에이전트 원문 읽기/저장 확인까지 따라갈 수 있음 | 가이드 route, 빈 상태, 공개 연결 설정 |
| 6 | 필요할 때 route 기반 상세 overlay | URL 직접 진입·새로고침·뒤로가기와 모달 읽기/편집 모두 일관됨 | 상세 route/Modal, list-state/return, 영향받는 E2E |

1~5를 우선 제안하며 6은 라우팅 변경 비용이 크므로 문서형 상세 적용 후 필요성을 다시 판단한다. 기본 API에 없는 기간 필터/복합 태그/상태를 UI만으로 새로 약속하지 않는다.

구현 담당은 각 PR의 기능 파일·공통 표현·해당 회귀를 소유하고 본 세션은 계약·분할·통합·독립 리뷰를 조정한다. 별도 작업 공간과 정확한 base/head로 인계한다. 실제 모델 배정은 구현 시작일 preflight로 결정하며 이 조사에 새 모델 평가를 포함하지 않는다.

## 구현 검증 조건

- 관련 화면을 360/390/768/1024/1440px, 긴 한국어, 200% 확대에서 확인한다. 하단 탐색/모달 footer가 마지막 항목·키보드 초점을 가리지 않게 한다.
- 탐색/보조 메뉴/날짜 접기/보기/편집/저장/취소/삭제 확인을 키보드로 조작한다. 초점 반환·dialog 활성 경계·live 상태를 확인한다.
- 최초 로딩/빈 목록/조건 결과 없음/오류, 더 보기 실패에서 기존 결과 유지, 날짜 그룹의 페이지 합침/중복/접힘 유지, 대상 삭제 후 복귀를 검증한다.
- 기존 필터·cursor·scroll·focus·검색 원문 복귀 및 HTTP/MCP 저장 의미를 회귀한다. 첫 적용은 웹 표현이며 DB/API 계약 변경이 생기면 별도 계약 검증을 추가한다.
- 공통 탐색·여러 화면 DOM/동작 변경은 [변경 영향별 CI](../development/workflow.md#변경-영향별-ci)에 따라 전체 E2E를 수행한다. 실제 앱 UX 변경을 표시 문구만의 경량 검사로 취급하지 않는다.
- 실기기/스크린리더는 이번 조사에서 검증하지 않았다. 이전 사용자 이관/제외 결정을 새 필수 작업으로 바꾸지 않는다.
