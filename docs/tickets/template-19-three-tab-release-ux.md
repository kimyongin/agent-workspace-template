# Template-19 — 세 탭 구조와 출시 UX 정리

작성: 2026-10-04
상태: 진행 중
검토 기준: main `399b82b744f3ea9471dc335ccf5b13c972c16e93`

## 목표와 승인 범위

사용자는 엔터티/활동/원칙 세 탭, 각 탭의 등록·검색·목록·보기/편집, 하단 메뉴의 가이드/설정, 설정의 프로필 아이콘 선택과 하단 로그인 표시를 요청했다. 2026-10-04 사용자의 “좋아. 티켓 정리하고 개발해줘”로 제안과 구현을 승인했다. 키워드 기본+자동 검색 옵션, 중앙/전체 화면 상세, 고정 아이콘+계정 metadata, 인증 후 브랜드 헤더 제거를 기본값으로 확정했다. 원칙의 예외 흐름은 Template-20을 따른다. 운영 배포는 포함하지 않는다.

단순 Entity의 prop1~4, 사용자 소유권, HTTP/MCP 공통 업무, 제목+요약 단일 벡터 검색을 유지한다. 후속 사용자 설명의 현재 원칙 하나·태그 사전 분리·메모와 CRUD 변경 기록은 [Template-20](template-20-current-principle-change-records.md)을 먼저 따른다. fin의 친구·공유·금융 기능은 가져오지 않는다. 설계 당시 PRD/ADR을 변경하지 않았으며, 이후 사용자 구현 승인으로 제품 의미를 PRD에 반영했다. 아래 설계 당시 실행 기록과 현재 구현 상태는 구분한다.

기준 문서: [PRD](../product/concept.md), [ADR-0004](../adr/0004-summary-single-vector-search.md), [코드 원칙](../architecture/principles.md), [검색](../architecture/search.md), [디자인](../design/guide.md), [시각 규격](../design/visual-spec.md), [상호작용](../design/ui-patterns.md), [보안](../security/guide.md), [개발 방법](../development/workflow.md).

선행 [Template-18](template-18-fin-ux-adaptation.md)은 PR #91/#92/#93으로 개발·리뷰·필수 CI·머지를 완료했다. 마지막 [PR #93 완료 기록](https://github.com/kimyongin/agent-workspace-template/pull/93#issuecomment-5977999865)이 제출 이후 최종 결과를 소유한다. 운영 배포는 하지 않았다.

## 제안하는 사용자 흐름

### 1. 세 탭과 하단 탐색

하단 순서: `[프로필] [엔터티] [활동] [원칙] [메뉴]`. 모바일·데스크톱 모두 같은 순서다. 프로필/메뉴의 조작 영역은 44×44px 이상, 가운데 세 항목은 동일 폭이다. 세 주요 항목은 아이콘과 글자, 현재 위치 표시를 갖는다. 양끝 아이콘은 접근성 이름을 제공한다.

- 프로필은 로그인된 내 계정을 표시한다. 누르면 이름/이메일·로그인 상태·설정 바로가기를 보여주는 작은 팝오버를 연다. 친구 목록·계정 전환을 만들지 않는다. 아이콘 자체를 인증 증거로 사용하지 않는다.
- 메뉴는 가이드·설정으로 이동한다. 태그 관리는 설정의 자료 관리에서 기존 전용 페이지로 연결한다. 로그아웃은 설정의 계정 영역에 둔다.
- 팝오버는 동시에 하나만 연다. 선택·바깥 클릭·Escape로 닫고 진입 버튼으로 초점을 돌린다. 편집 중 로그아웃/탭 이동은 기존 초안 보호를 유지한다.
- 로그인 상태 조회 중에는 로그인 완료 아이콘을 미리 그리지 않는다. 세션 만료 시 사용자 계정 표시와 계정별 캐시를 정리한다. 인증과 업무 권한은 기존 서버 검증을 유지한다.
- 상단의 반복되는 앱 브랜드 헤더는 인증 후 작업 화면에서 제거하고 각 탭 제목이 페이지 문맥을 담당하는 것을 권한다. 로그인·OAuth 동의는 독립 제목을 유지한다.

### 2. 모든 탭의 공통 골격

순서: `제목 + 등록 버튼 → 검색 입력/실행/지우기 → 기본 조건 + 추가 조건 → 적용 조건 → 목록 → 더 보기`.

| 탭 | 등록 | 검색과 목록 |
| --- | --- | --- |
| 엔터티 | 엔터티 등록 | 기존 속성1 부분 일치 검색, 기존 정렬/속성 조건 유지 |
| 활동 | 할 일 등록 / 기록 작성 | 탭 내부 할 일·기록 전환. 현재 종류 안에서 검색, 기존 상태/태그/연결 조건 유지 |
| 원칙 | 현재 없음이면 등록, 있으면 현재 문서 편집 | 상단 현재 원칙 하나, 아래 과거본 목록·검색. 태그/활성 상태 필터 없음 |

- 입력한 초안과 적용된 검색어를 구분한다. Enter/검색 버튼으로 적용하며 한글 IME 조합 중에는 제출하지 않는다. 검색어를 지우면 같은 탭의 등록 목록으로 돌아간다.
- 필터를 바꾸면 적용 검색어와 함께 다시 조회하고 커서를 초기화한다. 탭별 검색·필터·정렬·페이지·스크롤·선택 항목을 URL로 복원한다. 늦게 도착한 이전 응답이 새 조건을 덮어쓰지 못한다.
- 검색어 없는 기본 목록과 검색 결과를 한 자리에서 교체한다. 별도 검색 결과 카드/목록을 중복 생성하지 않는다. 검색 결과임과 정렬 기준을 짧게 표시한다. 날짜 그룹은 기본 기록 목록에만 적용하고 관련도 순 검색 결과에 강제하지 않는다.
- 목록 행은 제목·짧은 요약·관련 상태/날짜·태그·보기/편집 순서를 통일한다. 빈 값을 의미 없이 표시하거나 내부 version/ID를 업무 정보처럼 강조하지 않는다. 본문 전체를 클릭 영역에 넣지 않는다.
- 위 목록 행 규칙의 태그는 엔터티 태그/활동 태그로 각각 적용한다. 원칙의 과거본은 저장 시각·변경 메모를 먼저 표시하며 원칙에는 태그를 붙이지 않는다. 기록 목록에는 직접 작성/수행 결과와 자동 변경 기록이 함께 나타난다. 상세 의미는 Template-20이 소유한다.
- 많은 조건은 추가 조건으로 펼치되 적용 조건은 항상 보이게 한다. 필터 해제와 검색어 지우기는 구분한다. 목록이 없는 이유가 미등록인지 조건/검색 결과 없음인지 구분한다.

### 3. 검색 계약과 호환성

검색 탭 제거는 RAG 기능 제거가 아니다. 엔터티는 현재 `GET /entities?keyword=`(속성1 부분 일치, 최대100자)를 유지한다. 업무 검색은 기존 `POST /search`의 kinds 범위를 현재 task/record/principle로 한정한다(질의 최대200자).

- 첫 기본안은 명시적 키워드 검색, 활동/원칙의 추가 옵션으로 의미를 포함하는 자동 검색을 제공한다. 검색 방식과 대체 검색 여부는 사용자에게 알려준다. 이 기본값은 구현 전에 확정할 제안이다.
- 의미 검색은 제목+요약, 키워드는 기존 서버의 원문 검색 범위를 따른다. 엔터티를 근거 없이 의미 검색 지원 대상으로 표시하지 않는다.
- 현재 검색 API는 할 일 kind/status 조건 전체를 지원하지 않는다. 검색 중에도 해당 필터를 유지하려면 실제 서버 필터·커서·HTTP/MCP 계약을 함께 보강하는 티켓이 필요하다. 현재 페이지의 결과만 클라이언트로 걸러 전체 검색인 것처럼 표시하지 않는다. 상태/기간의 적용 대상도 목록과 검색 양쪽에서 동일하게 명시한다. 원칙의 기존 active/inactive·tag_id 검색은 목표 정책이 아니며 현재/과거본 조회로 전환한다.
- 기존 `/search?...` 링크는 호환 진입점으로 유지하되 신규 탐색에 검색 탭을 만들지 않는다. 기존 혼합 검색 링크의 결과 종류를 조용히 줄이지 않는다. 기존 화면을 호환용으로 유지하고 단계적으로 탭 검색으로 전환하는 방식을 권한다.
- 저장 원본과 색인 반영은 다르다. 색인 대기·키워드 대체·검색 실패·결과 없음은 각각 안내한다. 조회 실패는 결과를 삭제하지 않고 조회만 재시도한다.

### 4. 보기·편집과 반응형 모달 정책

목록의 보기와 편집은 URL을 가진 같은 상세 surface를 연다. 보기에서는 문서형 읽기, 편집에서는 같은 위치의 입력 폼으로 전환한다. 상세 ID와 편집 여부, 출발 목록 문맥을 URL로 관리한다. 새로고침·직접 링크도 정상 동작하고 출발 목록이 없으면 소속 탭으로 돌아간다.

| 용도 | 640px 미만 | 640px 이상 |
| --- | --- | --- |
| 등록·보기·편집 | 화면 전체를 쓰는 surface | 중앙 모달, 최대40rem, 사방24px 이상 여백 |
| 삭제·초안 폐기 확인 | 내용 크기의 중앙 확인창 | 동일, 최대28rem |
| 하단 프로필·메뉴 | 푸터에 연결된 팝오버 | 동일 |
| 설정·가이드 | 일반 페이지 | 일반 페이지 |

- 처음에는 상세 드로어를 추가하지 않고 중앙/전체 화면 두 형태로 통일한다. 실제 병렬 읽기 수요가 확인되면 별도 검토한다.
- 헤더는 제목/모드·닫기, 본문만 세로 스크롤, 편집 footer는 취소/저장이다. 보기에는 빈 저장 footer를 만들지 않는다. 긴 제목이 닫기를 밀어내지 않고 긴 본문/태그/URL은 줄바꿈한다.
- 모바일은 동적 화면 높이·safe-area·가상 키보드로 가려지는 입력/저장 조작을 확인한다. 큰 모달의 배경 페이지는 스크롤되지 않아야 한다. 작은 확인창은 가상 키보드가 닫힌 뒤에도 화면 안에 남는다.
- Escape·닫기·취소·뒤로가기·탭 전환은 같은 dirty 규칙을 사용한다. 편집 배경 클릭으로 초안을 버리지 않는다. 저장 중 중복 저장/닫기와 대기 중 이동 의도를 막는다.
- 초안 폐기 확인은 최대 한 겹만 추가한다. 보기→편집은 shell 교체/중첩으로 만들지 않는다. 관련 엔터티/태그 선택도 일반 폼을 중첩하지 않는다.
- 보기 첫 초점은 제목, 등록/편집은 첫 의미 있는 필드, 오류 제출은 첫 오류 필드로 둔다. 닫기 뒤 원래 행/조작으로 돌아가고 삭제로 사라졌으면 인접 항목 또는 목록 제목으로 이동한다.

### 5. 설정과 프로필 아이콘

설정은 `내 계정 → 프로필 아이콘 → 자료 관리(태그) → 연결 안내 → 로그아웃`으로 구성한다. 아이콘은 고정된 작은 SVG 목록에서 선택하고 미리보기·저장·기본값 복원을 제공하는 방식을 권한다. 첫 범위에 사진 업로드·자르기·외부 이미지 URL·공개 프로필/공유를 넣지 않는다.

제안하는 저장 계약은 계정의 장식용 Auth metadata `workspace_avatar_id`다. 고정 목록의 안정적인 ID만 저장하고 알 수 없는 값은 고정 기본 아이콘으로 표시한다. 기존 Google 이름/이미지 metadata를 덮어쓰지 않는다. 다른 기기·재로그인에서 유지하며 로그아웃/사용자 변경 시 이전 계정 표시를 남기지 않는다. 이 선택은 구현 전에 확정할 설계안이며 지금 저장 기능을 구현하거나 실제 계정 값을 변경하지 않았다.

저장 성공 후 서버 응답을 반영하고 하단 아이콘을 갱신한다. 실패 시 초안은 보존하고 저장 완료로 표시하지 않는다. 사용자 편집 metadata는 권한·owner·관리자 판단에 사용하지 않는다. 이 장식용 계정 설정을 업무 MCP CRUD로 임의 확대하지 않는다.

44×44px은 현재 제품의 자체 조작 기준이다. WCAG 2.2 AA의 Target Size Minimum과 동일한 숫자라고 설명하지 않는다. native dialog의 배경 비활성화, 초기 초점, Escape, 초점 복귀 기준은 [W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)를 참고한다. 재배치·초점 가림은 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)로 확인한다. 계정 metadata 변경 가능성은 [Supabase updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser)와 [사용자 자료](https://supabase.com/docs/guides/auth/managing-user-data)를 참고한다.

실제 휴대폰 확인은 기존 사용자 이관을 유지한다. 스크린리더 직접 실행은 기존 제외 범위를 임의 변경하지 않으며 의미 있는 이름·초점·키보드 계약은 유지한다. 운영 배포와 자동 비용 발생은 설계 요청에 포함하지 않는다.

## PR 분할 계획과 구현 인계

| 순서 | 범위 | 머지 후 직접 확인할 것 |
| --- | --- | --- |
| 1 | 세 탭·하단 프로필/메뉴·설정 아이콘 선택 | 로그인→설정 선택/저장→하단 표시→재로그인 유지 |

| 4 | 원칙 현재 문서·과거본 조회와 검색 | 현재 문서 편집+메모→과거 저장본·활동 변경 기록→본문 조회 |

공통 shell/탐색/검색 계약은 선행 PR에서 소유자를 지정한다. 본 세션은 설계/결정/배정을 맡고 구현 세션은 자신의 기능·검증·실패 수정을 맡는다. 동시 구현 시 별도 worktree를 사용하고 같은 tracked 파일을 동시에 편집하지 않는다. 이번에는 설계 문서만 작성했으며 새 구현 세션을 배정하지 않았다.

검증 명령은 현재 package.json의 `npm run check:docs`, `npm run test:web`, `npm run build`, `npm run check:boundaries`, `npm run test:e2e`를 기준으로 한다. 검색/저장 계약 변경에는 기존 빠른 검사와 격리 DB·HTTP·MCP 검사를 함께 배정한다. 공유 로컬 실행은 한 담당만 소유하며 운영 DB를 테스트로 사용하지 않는다. 최종 head 독립 리뷰·필수 CI 후 PR을 머지한다.
