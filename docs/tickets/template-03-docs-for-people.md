## 목표와 기준 문서

[PRD](../product/concept.md)는 이 템플릿을 "에이전트와 함께 작업하는 초보자도 사용할 수 있어야 한다"고 정한다. 이 티켓은 그 목표에 맞춰 문서를 사람이 읽기 쉽게 정리하고, 같은 규칙이 여러 문서에 복제된 곳을 정본 하나로 모은다. 기능·기술 결정은 바꾸지 않는다.

문서 소유와 승인은 [ADR-0008](../adr/0008-document-ownership.md)을 따른다. T03-1~T03-5는 에이전트가 소유하는 가이드·티켓·스킬의 변경이고, T03-6·T03-7은 사람이 소유하는 ADR·PRD의 변경안이다. 변경안은 사람의 승인 전에 머지하지 않는다.

## 배경: overview 작업에서 드러난 문제

2026-10-02 `docs/overview.html`(#17)을 비개발자 눈높이로 만들면서 다음을 확인했다. 각 항목의 근거는 아래 작업 절에 둔다.

1. 문서가 에이전트 기준의 개발 용어로 쓰여 있어 사람용 입구가 약하다. overview에서는 유스케이스·포트·트랜잭션·revision을 쉬운 말로 하나씩 옮겨야 했다.
2. 템플릿을 만드는 작업 기록(Template-01·02 티켓, `experiments/t02-1`)과 새 앱이 물려받을 기본 문서가 섞여 있고, 일반 가이드와 PRD가 템플릿 전용 티켓을 직접 링크한다.
3. 교차 리뷰를 선택으로 바꾸는 #18 하나에 7개 파일을 고쳤다. 머지·리뷰 조건이 ADR·AGENTS.md·개발 스킬·두 개발 가이드에 각각 문장으로 적혀 있기 때문이다.
4. ADR-0008의 분류 기준은 "방법은 가이드"인데 ADR-0008 자신에 머지 절차가 들어 있어, 운영 절차 변경에 ADR 대체가 필요했다.
5. PRD에 대상 사용자와 해결하는 문제가 없어 overview의 "해결하는 문제"를 PRD 목적 문장에서 다시 써야 했다.
6. FAQ를 쓰며 근거 문서가 없는 질문이 있었다: 비용이 어디서 드는지, 새 앱을 어떻게 시작하는지, 티켓 이름을 어떻게 짓는지.

## T03-3 — 티켓 이름 규칙과 양식

### 근거

- 티켓 파일 이름 규칙이 문서에 없다. 현재 이름(`template-NN-…`)은 템플릿을 만드는 작업 전용이다.
- ADR은 [ADR 목록](../adr/README.md)에 이름 규칙·상태·양식이 있지만 티켓에는 해당 문서가 없다. [개발 방법](../development/workflow.md)의 "작게 나누기"는 티켓에 PR 분할 계획을 적으라고만 한다.

### 작업

- `docs/tickets/README.md`를 만들어 이름 규칙, 상태 값, 필수 절(목표와 기준 문서·작업·완료 조건·PR 분할 계획·구현 인계와 완료 기록), 빈 양식을 둔다. 현재 티켓들의 공통 구조를 근거로 쓴다.
- 이름 규칙 후보: `NN-slug.md` 또는 `ticket-NN-slug.md`. 하위·상세 티켓(현재 `template-02-t02-1-contracts.md`처럼 한 단계의 계약·실험 기록을 따로 둔 파일)의 이름 짓는 방법도 함께 정한다(예: `NN-slug.md`의 하위는 `NN-MM-slug.md`).
- 기존 `template-NN-…` 티켓은 T03-5의 분리 방침에 따라 이름을 유지하거나 옮긴다. 이미 링크된 파일 이름을 바꾸면 `experiments/`를 포함한 모든 링크를 같은 PR에서 고친다.
- working-with-agents.md의 "티켓 만들어" 설명이 이 양식을 가리키게 한다.

### 완료 조건

- [ ] 티켓 README에 이름 규칙·상태·필수 절·양식이 있다.
- [ ] 이 티켓(Template-03)이 양식과 맞거나, 차이가 있으면 이유가 적혀 있다.

## T03-5 — 템플릿 기록과 새 앱 문서 분리 방침

- 가이드(Template-01·02 본문 링크): [개발 방법](../development/workflow.md) 102행, [배포 방법](../deployment/release.md) 93행, [폴더 구조](../design/template-structure.md) "다음 작업" 절(105행), [보안 가이드](../security/guide.md) 7행, [아키텍처](../architecture/hexagonal-review.md) 5·152행
- 가이드(T02-1 실험 결과 링크, 결정의 근거): [아키텍처](../architecture/hexagonal-review.md) 42·75·89행 → `template-02-t02-1-contracts.md`
- 실험: [실험 목록](../../experiments/README.md) 7행 → `template-02-t02-1-contracts.md`, [t02-1 실험](../../experiments/t02-1/README.md) 3행 → `template-02-implementation-base.md`·`template-02-t02-1-contracts.md`

- PRD: [제품 요구사항](../product/concept.md) 89행(사람 소유)

T02-1 실험 결과로 가는 링크는 결정의 근거라 새 앱에서도 의미가 있고, T02-6은 이미 "`experiments/`는 새 프로젝트에서도 유지"로 정했다. 티켓을 다른 폴더로 옮기면 유지되는 `experiments/`의 링크도 깨진다. 따라서 일괄 삭제가 아니라 "근거로 남길 것"과 "새 앱에서 바뀌어야 할 것"을 구분해야 한다.

### 작업

## T03-6 — ADR에는 결정과 이유만 (사람 결정)

### 근거

ADR-0008의 분류 기준은 "같은 결과를 더 일관되거나 효율적으로 만드는 방법"을 가이드로 둔다. 그런데 ADR-0008에 머지 절차가, ADR-0009에 리뷰 방법(새 세션 또는 다른 에이전트)이 들어 있어 운영 절차를 바꿀 때마다 ADR 대체와 사람 승인이 필요하다.

### 결정 요청

다음 중 하나를 사람이 고른다.

2. **결정만 ADR에(권장):** ADR에는 "PRD·ADR을 벗어나지 않고, 독립된 리뷰와 자동 검사를 통과한 변경은 에이전트가 머지한다" 같은 권한 결정만 남긴다. 리뷰어 조건·결론 형식 같은 절차는 workflow.md가 소유한다. 승인되면 ADR-0008·0009를 대체하는 새 ADR과 ADR 작성 규칙에 "절차는 가이드에 둔다"를 추가한다.

## T03-7 — PRD에 대상 사용자와 해결하는 문제 (사람 결정)

### 근거

[PRD](../product/concept.md)는 "어떤 템플릿인가"와 필수 기능은 정하지만 누가 어떤 문제 때문에 쓰는지는 적지 않는다. 대상과 문제가 없으면 기능 우선순위와 범위 판단의 기준이 약하다.

### 변경안 초안

overview 작업 때 쓴 다음 세 문제를 출발점으로 PRD 변경안을 만든다. 표현과 범위는 사람이 정한다.

- 해 둔 일이 다음 판단에 쓰이지 않는다 → 기록을 남기고 다음에 찾아 참고한다.
- 사람이 쓰는 앱과 AI가 쓰는 도구가 따로 논다 → 같은 기능과 데이터를 쓴다.
- 업무 분야가 바뀔 때마다 처음부터 만든다 → 복제하고 업무 대상만 바꾼다.

대상 사용자 후보: 에이전트와 함께 업무 앱을 만들려는 초보 개발자·비개발자, 그 앱을 웹과 AI 에이전트로 쓰는 개인 사용자.

### 완료 조건

- [ ] PRD 변경안 PR이 올라가 사람이 승인했거나, 하지 않기로 한 결정이 기록됐다. 2026-10-02 사용자가 초안대로 변경안 작성을 골랐고, "대상 사용자와 해결하는 문제" 절을 PR로 올렸다. 머지가 곧 승인이다.
