# 티켓 작성 규칙

티켓은 작업 하나의 목표·계획·완료 조건·진행 기록을 담는 작업 지시서다. 에이전트가 작성하고 소유한다([ADR-0008](../adr/0008-document-ownership.md)). 작업 절차와 검증 기준은 [개발과 검증 방법](../development/workflow.md)이 정본이며 이 문서는 티켓의 이름과 형식만 정한다.

## 이름

- 파일 이름은 `NNN-영문-요약.md`다. 번호는 세 자리, 순서대로 붙이고 재사용하지 않는다(예: `001-customer-search.md`).
- 한 티켓의 계약·실험 기록처럼 따로 둘 만큼 큰 상세 문서는 하위 티켓으로 `NNN-MM-영문-요약.md`를 쓴다(예: `001-01-contracts.md`). 하위 티켓의 진행 상태는 상위 티켓의 기록 표가 소유한다.
- 제목은 `# NNN — 한국어 제목`, 하위 티켓은 `# NNN-MM — 한국어 제목`이다.
- 이름을 바꾸면 저장소 안의 모든 링크(`experiments/` 포함)를 같은 PR에서 고친다.

템플릿을 만드는 작업의 티켓(`template-NN-…`)은 이 규칙 이전에 만들어졌고 이름을 바꾸지 않는다. 새 앱에서도 지우거나 옮기지 않고 템플릿 기록으로 보존한다. 공통 기능의 계약과 기술 실험의 근거가 들어 있고 `experiments/`와 가이드가 링크하기 때문이다. 새 앱의 티켓은 `001`부터 위 규칙으로 쓴다([Template-03 T03-5](template-03-docs-for-people.md#t03-5--템플릿-기록과-새-앱-문서-분리-방침)).

## 상태

| 위치 | 값 |
| --- | --- |
| 티켓 머리말 | `계획`, `진행 중`, `완료`, `완료(일부 미완료)`, `보류`, `취소` |
| 단계별 기록 표 | `미시작`, `진행 중`, `구현(리뷰 대기)`, `결정 대기`, `완료`, `미완료(사유)` |

구현 상태는 [START-HERE의 현재 상태](../START-HERE.md#현재-상태)와 티켓에만 쓴다. 완료로 바꿀 때는 기록 표에 검증 명령과 결과가 있어야 한다.

## 인계와 작업 배정

새 세션이 대화 전체 없이 시작할 수 있도록 아래 정보를 티켓에 남긴다. 기존 절에 이미 있으면 위치를 링크하며 같은 계약을 다시 쓰지 않는다. 승인 기록은 기존 사용자 지시를 추적하기 위한 것으로 새 권한을 부여하지 않는다. 실행 절차는 [세션 배정과 인계](../development/workflow.md#세션-배정과-인계)가 정본이다.

| 필드 | 내용 |
| --- | --- |
| 목표·승인 범위 | 사용자와 합의한 결과, 실행 가능한 범위와 제외·중단 조건, 승인 근거 위치 |
| 기준과 작업 공간 | base commit, branch, checkout/worktree 경로, 시작 시 미커밋 변경 |
| 담당 변경 | 세션 역할과 소유 파일/기능, 공통 파일·계약·migration·환경 담당 |
| 계약과 의존성 | 관련 티켓·PRD/ADR·가이드 위치, 선행 결과와 소비 관계, 미정 결정 |
| 완료 조건과 검증 | 직접 확인할 결과, 명령·데이터 조건, 환경 담당/순서와 제약 |
| 결과와 다음 행동 | 현재 head·PR, 검증 증거/실패 artifact 위치, 독립 리뷰·CI·머지 확인 위치, 남은 작업 |

동시에 여러 구현을 배정하면 작업 배정표를 둔다. 작은 단일 작업은 인계 필드만으로 충분하다.

| 작업 | 담당 세션 | branch / 작업 공간 | 소유 변경 | 선행·공유 계약 | 검증 환경·담당·순서 | 완료 조건 |
| --- | --- | --- | --- | --- | --- | --- |
| 기능 하나 | | | | | | |

## 필수 절

| 절 | 담는 내용 |
| --- | --- |
| 머리말 | 작성일, 상태, 검토 기준 revision, 선행 조건 |
| 목표와 기준 문서 | 무엇을 왜 하는지, 따르는 PRD·ADR·가이드. PRD·ADR을 벗어나야 하면 멈추고 사람의 승인을 받는다는 점 |
| 작업과 완료 조건 | 할 일 목록과 체크박스 완료 조건. 여러 단계면 단계별로 나누고 단계와 의존성 표를 둔다 |
| PR 분할 계획 | 순서·브랜치·내용·완료 기준·관련 결정. 작업을 시작할 때 먼저 적는다. PR은 계층이 아니라 기능 조각 단위로 나누고, 완료 기준에는 그 PR까지 머지하면 직접 확인할 수 있는 것을 적는다([작게 나누기](../development/workflow.md#작게-나누기)) |
| 검증 | 실행할 명령과 확인 위치. 자동 검사로 확인할 수 없는 항목은 확인 방법 |
| 구현 인계와 완료 기록 | 위 인계 필드, 필요시 작업 배정표, 단계별 상태·revision·검증 결과·남은 작업 표와 이력 |

작은 작업은 단계와 의존성 표 없이 작업·완료 조건·PR 분할 계획 한 줄·기록만 써도 된다.
