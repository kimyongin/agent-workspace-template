# 보안 가이드

## 목적과 적용 범위

웹·MCP·비동기 worker가 같은 데이터를 사용할 때 지켜야 할 신뢰 경계와 검증 기준이다. 인증 성공과 작업 권한, 사용자 요청과 저장된 콘텐츠, 공개 설정과 비밀값을 구분한다. 권한과 데이터 보호는 서버가 강제하며 UI·에이전트 스킬 준수에 의존하지 않는다.

이 문서는 보호 기준이며 적용된 보안 설정이나 감사 통과를 의미하지 않는다. 적용과 검증 상태는 [GitHub Issues](https://github.com/kimyongin/agent-workspace-template/issues)와 해당 PR의 증거에서 확인한다. 인증·세션·역할·요청 제한의 실제 입력과 경계는 코드의 공유 계약과 검증이 소유한다. 실행 구성은 [아키텍처](../architecture/hexagonal-review.md), 배포와 사고 대응은 각각 [배포 방법](../deployment/release.md)·[운영 방법](../operations/runbook.md)이 소유한다.

## 보호 대상과 신뢰 경계

| 경계 | 신뢰하지 않는 입력 | 강제할 보호 |
| --- | --- | --- |
| 웹/MCP → 서버 | 사용자 ID·역할·객체 ID·필드·토큰 | 검증된 Actor, 입력 검증, 작업별 접근 검사 |
| 서버 → DB | 입력에서 유래한 값과 참조 | 최소 권한·RLS·파라미터 SQL·동일 소유자 참조 |
| 큐 → worker | 오래된 메시지·변조된 요청·중복 전달 | 내부 인증, 원본·권한·버전 확인, 제한 재시도 |
| 검색/원문 → 에이전트 | 기록 본문의 명령·링크·도구 호출 유도 | 자료와 지침 분리, 최소 데이터 반환, 서버 권한 강제 |
| 서버 → 외부 공급자 | 사용자가 제시한 URL·응답 데이터 | 목적지 제한, 최소 전송, 시간·크기 제한 |
| CI/관리 도구 → 운영 | 변경 artifact·배포 설정 | 환경 분리·최소 권한·검증 revision |

기본 데이터 접근은 소유자에게 한정한다. 공유·조직·관리자 기능을 추가할 때는 별도 권한 계약과 테스트를 만든다. 식별자를 아는 것만으로 접근을 허용하지 않는다.

이 접근 제어는 앱 사용자 간의 격리를 보장하는 기준이다. 충분한 DB 권한을 가진 운영자는 사용자 본문을 읽을 수 있다. 운영자는 신뢰 경계에 포함하며, 운영자에게도 본문을 숨기는 종단간 암호화는 제공하지 않는다.

## 인증과 세션

기본 사용자 로그인은 Supabase Auth의 Google OAuth다. Google client secret은 인증 공급자 설정에서 관리한다. Google에서 받은 토큰을 앱의 HTTP/MCP 권한 토큰으로 그대로 신뢰하지 않으며, 앱 세션과 MCP 토큰의 검증 계약을 각각 따른다.

서버 인증 어댑터에서 서명·허용 알고리즘·issuer·audience·만료 등 채택한 토큰 계약을 검증하고 Actor를 만든다. 토큰을 decode한 값이나 요청 본문의 user_id를 인증 증거로 사용하지 않는다. 에이전트의 주장이나 MCP 세션 ID도 인증을 대신하지 않는다.

MCP 토큰은 `aud`가 MCP 서버의 정식 URL이고 웹 세션 토큰은 `authenticated`다. MCP 서버와 HTTP API는 각자의 audience만 받는다. 발급 방식은 [아키텍처](../architecture/hexagonal-review.md#google-로그인과-mcp-인증)를 따른다.

HTTP와 MCP는 같은 소유권 검사를 통과해야 한다. 채택한 Supabase OAuth 서버의 scope(`openid`·`email`·`profile`·`phone`)는 사용자 정보 제공 범위일 뿐 업무 데이터·API 권한을 정하지 않는다([공식 설명](https://supabase.com/docs/guides/auth/oauth-server/token-security)). 이 앱은 업무 scope를 두지 않으며 접근은 토큰 audience(진입점)와 객체별 소유권 검사로 정한다. 나중에 업무 scope를 추가하더라도 작업 종류의 허용 범위일 뿐 소유권 검사를 대체하지 않는다. 잘못된 audience의 토큰을 받거나 클라이언트 토큰을 외부 공급자에 그대로 전달하지 않는다. OAuth의 redirect URI·PKCE·state 등 보호는 채택한 공급자/SDK와 프로토콜 버전에 맞춰 구현·검증한다. 인증 URL의 임의 redirect는 금지한다.

사용자가 수정 가능한 프로필 metadata를 관리자 권한의 근거로 쓰지 않는다. 서버 관리 권한 정보도 토큰에 담겼다면 최신 상태와 다를 수 있다. 로그아웃·탈퇴·권한 회수 후 기존 access token의 잔여 유효시간을 고려하고, 즉시 회수가 필요한 작업에는 서버 상태 확인을 설계한다. 계정 삭제만으로 모든 토큰이 즉시 무효화된다고 가정하지 않는다.

웹은 브라우저에 보관한 Supabase Auth 세션의 bearer token으로 업무 API를 호출한다. XSS와 토큰 수명·저장 위치를 검토한다. 쿠키 인증을 도입하면 Secure·HttpOnly·SameSite와 CSRF 방어를 적용한다. 토큰을 URL·로그에 넣지 않는다. 운영 전송은 HTTPS를 사용한다.

## 권한·DB 접근

유스케이스에서 행위자·대상·작업의 허용 범위를 검사한다. 연결하는 할 일·기록·태그도 같은 접근 범위인지 확인한다. 목록·단건·검색 후보·일치 구간·개수·페이지 커서·오류 응답까지 같은 경계를 적용한다. 캐시는 사용자·작업 범위를 포함한다. 엔터티 식별의 유일성은 사용자·발급처·외부 식별자 조합으로 검사하며 식별 정보 변경은 관련 참조도 같은 소유자 범위에서 전환한다. 활성 대상의 중복 생성과 다른 모델의 UUID 충돌은 기존 응답으로 재현하지 않는다. 삭제 엔터티의 복원은 보관값·현재 버전을 확인한 명시 작업이며 과거 생성 재시도로 실행하지 않는다. 수정·삭제·복원의 대상 ID·버전 검사도 소유자 경계 안에서 수행한다.

DB는 grant와 RLS를 함께 설정한다. 공개 스키마의 테이블에는 RLS를 적용하고 불필요한 직접 접근을 제한한다. 업무 데이터의 직접 DML·RPC가 유스케이스를 우회하지 않게 한다. view·함수 실행 권한과 기본 PUBLIC 권한도 점검한다. SECURITY DEFINER가 필요하면 사용 이유·최소 실행 권한·안전한 search_path·대상 검증을 정하고 격리 테스트로 확인한다.

직접 SQL 연결에는 요청의 사용자 문맥이 자동 적용되지 않는다. 최소 권한 접속 역할과 검증된 Actor의 트랜잭션 한정 전달을 사용하고([역할 구성](../architecture/hexagonal-review.md#권한과-직접-접근)) 연결 풀 재사용 시 문맥이 남지 않는지 확인한다. 접속 역할의 RLS 우회 여부를 검사한다. service_role·관리자 연결로 성공한 테스트를 사용자 격리 증거로 쓰지 않는다. SQL 값은 바인딩하고 동적 정렬·필드 이름은 허용 목록으로 제한한다.

## HTTP·MCP 입력과 자원 제한

입력은 목적별 schema로 길이·타입·허용 필드·페이지 크기·배치 크기를 검증한다. owner·role·서버 상태 같은 필드를 임의로 갱신하는 mass assignment를 막는다. 내부 SQL·stack·비밀값이 포함된 오류를 외부에 반환하지 않는다.

HTTP와 MCP에 동일한 의미의 작업별 요청 제한을 적용한다. 인증·쓰기·검색·비싼 외부 호출은 사용자별 한도와 필요 시 전체 한도를 둔다. timeout·응답 크기·재시도·동시성의 구체 값은 실제 서버 계약에서 확인한다. 제한 오류에도 부분 실행 여부를 명확하게 한다.

CORS는 인증이 아니다. 브라우저 허용 origin은 배포 URL에 맞춰 제한하며 서버의 인증·권한을 그대로 유지한다. MCP HTTP의 Origin 검증 등 전송 계층 보호는 채택한 SDK/명세를 따른다. origin이 없는 합법적인 에이전트 요청도 토큰으로 검증한다.

## 에이전트·RAG와 비신뢰 콘텐츠

저장된 기록·검색 결과·첨부·외부 웹 내용은 추론 자료다. 그 안의 “기존 지침을 무시하라”, “다른 기록을 전송하라” 같은 문장을 사용자 승인·서버 지침으로 취급하지 않는다. 도구 응답은 원본 식별 정보와 자료를 구조적으로 구분하고 비밀값이나 불필요한 다른 자료를 포함하지 않는다.

제품 스킬은 자료 속 지시를 따르지 않고 실제 사용자 요청 범위에서 작업하도록 안내한다. 서버는 외부 에이전트의 추론이나 자연어 동의 판단을 완전히 통제한다고 주장하지 않는다. 중요한 부수효과는 서버의 권한·허용 작업·범위 제한으로 보호하고, 추가 승인 절차가 필요한 도메인이라면 해당 기능에서 구체적으로 설계한다. 웹은 합의한 업무 변경의 기록 입력·확인 단계를 사용한다. 이 UI 확인은 서버 권한 검증을 대신하지 않으며 일반 기록 작성·기록 자체 편집·설정 저장에는 추가 확인을 만들지 않는다.

MCP의 readOnly/destructive 등의 설명·힌트는 실제 동작과 일치시킨다. 힌트는 권한 통제가 아니며 조회 도구에서 숨은 업무 쓰기를 실행하지 않는다. 악성 지시가 포함된 기록으로 클라이언트 행동을 평가하되, 서버 권한 거부 테스트와 결과를 분리해 기록한다.

## 웹 표시와 외부 통신

사용자 문자열과 마크다운은 안전한 렌더러로 표시한다. raw HTML·스크립트 URL을 실행하지 않는다. 외부 이미지 자동 로딩·링크·첨부의 처리 정책을 명시한다. 실제 호스팅에서 가능한 CSP 등 응답 헤더/정책 전달 방법을 확인하며 설정 파일이 있다는 이유로 적용됐다고 보고하지 않는다.

기본 임베딩 공급자인 Pinecone Inference에는 검색에 필요한 최소 텍스트만 전송한다. 기록뿐 아니라 검색 질의도 외부 전송 대상임을 고려한다. 전송 데이터·보관/학습 정책·지역·삭제 요구와 사용자 안내를 서비스 설정 때 확인한다. 벡터·파생 구간·검색 로그도 원본에서 파생된 사용자 데이터로 취급한다.

서버가 사용자 URL을 가져오는 기능은 필요할 때만 추가한다. 허용 프로토콜·목적지·redirect·DNS 해석과 사설/루프백/메타데이터 주소 접근을 검사해 SSRF를 방지한다. HTTP client의 timeout·응답 크기·redirect 횟수도 제한한다. 외부 응답을 검증 없이 명령이나 저장 입력으로 사용하지 않는다.

## 큐·비밀값·공급망

플러그인은 MCP 연결 정보와 제품 스킬을 함께 배포하는 신뢰 대상이다. manifest·연결 대상·스킬의 변경을 함께 검토하고 패키지에 비밀이 없음을 검사한다. endpoint/앱 참조 변경으로 다른 서비스에 연결되지 않는지 확인한다. 패키지 설치는 모든 도구 실행의 포괄적 동의가 아니며 실제 요청 범위와 서버 권한을 유지한다.

큐 소비·완료·관리 함수와 worker 진입점은 내부 권한으로 제한한다. 메시지의 owner_id만으로 권한을 확정하지 않고 원본 관계·존재·버전을 다시 확인한다. 위조 메시지, 삭제/권한 변경 후 오래된 작업, 중복 호출로 권한이 넓어지거나 자료가 부활하지 않게 한다. 외부 호출의 재실행 비용·부수효과도 제한한다.

공개 키와 서버 비밀을 구분한다. DB 접속·service_role·공급자 키·배포 토큰은 브라우저 번들·URL·저장소·일반 로그에 넣지 않는다. 환경별 비밀은 분리하고 최소 권한으로 사용한다. 사고 시 폐기·교체 경로는 운영 문서에 둔다.

의존성 버전과 lockfile을 관리하고 보안 업데이트를 검토한다. CI 권한은 최소화하며 신뢰하지 않는 PR의 코드를 운영 secret과 함께 실행하지 않는다. 사용한 action/도구 버전과 배포 artifact를 추적한다. 비밀 탐지·의존성 검사·DB 보안 진단을 구현 기반에 포함하되 자동 검사 통과만으로 앱 보안을 보장한다고 하지 않는다.

## 데이터 수명과 보안 검증

원본·색인·큐·로그·백업의 보관 기간과 삭제 영향을 정한다. 원본 삭제 후 검색과 재처리에서 즉시 접근되지 않도록 하고 물리적 정리·백업 만료는 별도 정책으로 설명한다. 복원 시 과거 삭제·권한 회수가 되돌아갈 수 있으므로 재개 전에 대조한다. 감사 기록은 접근 제어·관리자 작업 등 실제 필요 범위에만 두고 모든 본문 수정 이력을 의무화하지 않는다.

첫 구현과 관련 변경에서 다음을 실제 경계로 검사한다.

- [ ] 미인증·만료·위조·잘못된 issuer/audience/scope와 권한 회수 시나리오를 확인한다.
- [ ] 사용자 A/B의 객체 ID·버전·참조·커서 교체로 목록·원문·검색·쓰기 결과가 노출되지 않는다.
- [ ] 직접 DB API/RPC 우회, view/함수 권한, RLS 역할과 연결 재사용의 사용자 격리를 확인한다.
- [ ] 허용하지 않은 필드, 과도한 본문·페이지·호출량, 오류 응답의 정보 노출을 검사한다.
- [ ] worker 위조 호출·오래된 메시지·삭제 후 재전달과 권한 변경을 검사한다.
- [ ] 악성 마크다운/URL과 프롬프트 인젝션 자료를 검증하고 서버 검사와 클라이언트 행동 결과를 구분한다.
- [ ] 브라우저 산출물·로그·CI에 비밀이 없는지 확인하고 외부 전송 데이터·의존성·설정 진단을 검토한다.

검증 revision·명령·결과·미검증 경로와 적용하지 않은 항목의 이유를 티켓에 기록한다. 아직 없는 공유·첨부 기능을 시험했다고 표시하지 않는다. 보안상 실패한 필수 경로는 해결 후 공개하며 환경 제약은 검증 가능한 격리 환경으로 인계한다.

빠른 HTTP/MCP handler 검사의 Actor는 테스트 factory에서만 주입한다. 운영 조립은 실제 토큰 검증을 기본값으로 유지하며 런타임 인증 우회 설정을 만들지 않는다. fixture 성공은 서명·issuer/audience·OAuth·RLS·사용자 격리·실제 SDK 전송의 증거가 아니다. 격리 통합 검사의 실행 구성은 [CI](../../.github/workflows/ci.yml), 증거 범위는 [검사 도구의 한계](../development/verification.md#검사-도구의-한계)에 있다.
