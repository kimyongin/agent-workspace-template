두 가지 길로 사용한다: 웹 앱과 AI 에이전트

사람은 두 가지 길로 앱을 씁니다. 웹 화면에서 직접 다루거나, AI 에이전트에게 말로 맡기거나. 어느 길로 가도 도착하는 곳은 같은 앱이라, 같은 규칙과 같은 데이터가 적용됩니다.

사람

웹 앱에서 직접

브라우저 · Google 계정으로 로그인

목록·상세·편집 화면에서 할 일, 기록, 원칙을 직접 보고 쓰고 고칩니다. 내가 누른 대로 정확히 바뀝니다.

데이터를 직접 조작

플러그인이란?

AI 에이전트에 설치하는 확장 기능입니다. 앱을 다루는 도구(조회·저장)와 “자료를 어떻게 찾고, 결과를 어떻게 기록할지” 알려 주는 사용 요령이 함께 들어 있습니다. 에이전트 연결은 웹 로그인과 따로 인증합니다.

두 길을 오가며 이어서 쓴다

웹에서 할 일을 적어 두면 에이전트가 그걸 읽고 처리해 결과를 기록합니다. 그 결과는 웹에서 바로 확인할 수 있고, 다음 대화에서 에이전트가 다시 찾아 참고합니다.

한 일이 다음 일의 참고 자료가 되는 순환

시작은 “일을 한다”부터

할 일을 미리 만들지 않아도 됩니다. 한 일을 바로 기록하면 그때부터 순환이 시작됩니다.

할 일은 계획이 필요할 때만

미리 계획해 두고 싶으면 할 일을 만들고, 끝낸 뒤 그 할 일에 연결해 기록을 남깁니다.

AI를 다시 가르치지 않는다

AI 모델을 새로 학습시키는 대신, 일할 때마다 쌓인 기록을 찾아 읽게 합니다. 그래서 기록이 늘수록 바로 더 똑똑하게 도와줍니다.

02

어떻게 개발을 시키는가

지금 해결할 일을 고르고, 그 일에 맞는 스킬로 요청합니다. 에이전트는 필요한 조사·구현·검토를 수행하고, 사람은 목표와 중요한 선택을 정합니다.

지금 무엇을 하고 싶나요?

Codex에서는 $스킬이름 요청, Claude Code에서는 /스킬이름 요청으로 시작합니다. 이미 정해진 작업은 바로 구현을 맡겨도 됩니다.

아이디어를 구체화하고 싶을 때

무엇을 만들지 함께 정하기

grill-with-docs “기록에 사진을 첨부하고 싶어.”

질문을 통해 사용자 흐름과 제약을 정하고, 합의한 용어와 중요한 결정을 문서에 남깁니다.

코드가 복잡해졌을 때

구조 개선 후보 찾기

improve-codebase-architecture “백엔드 구조를 개선할 곳을 조사해줘.”

코드 근거와 전후 그림이 있는 후보 보고서를 만듭니다. 후보를 선택하면 설계를 논의합니다.

오류나 성능 문제가 있을 때

원인을 재현하고 해결하기

diagnosing-bugs “저장 뒤 목록에 반영되지 않는 원인을 찾아줘.”

실패를 확인할 수 있는 검증부터 만들고, 원인을 좁혀 수정과 회귀 검증으로 이어갑니다.

무엇을 만들지 합의했을 때

실행 가능한 계획으로 정리하기

to-spec → to-tickets “합의한 내용을 명세와 티켓으로 정리해줘.”

GitHub Issues에 목표·완료 조건·작은 작업과 선행 관계를 남깁니다. 여러 세션에 걸친 작업에 사용합니다.

확정한 작업을 만들 때

구현과 검증 맡기기

implement “GitHub issue #N을 구현해줘.”

한 작업은 implement, 연결된 티켓 전체는 implement-spec으로 맡깁니다. 구현 뒤 코드 리뷰도 수행합니다.

어디서 시작할지 모르겠을 때

알맞은 방법 추천받기

ask-matt “이 작업은 어떤 스킬로 시작하면 좋을까?”

상황에 맞는 시작점과 흐름을 추천합니다. 추천을 읽고 실행할 스킬을 선택합니다.

결과는 어디에 남고, 다음 작업은 무엇을 읽나요?

명세부터 구현까지 이어갈 때의 자료 흐름입니다. 스킬을 요청할 때 이전 결과의 이슈 번호·URL·문서 경로를 전달하면 다음 작업의 입력으로 읽습니다.

출발점 A · 아이디어와 요구

grill-with-docs

질문과 답변은 현재 대화에 남습니다. 정리한 용어는 GLOSSARY.md, 중요한 아키텍처 결정은 필요할 때 docs/adr/에 기록합니다.

다음 입력: 대화에서 합의한 요구 + 관련 저장소 문서.

출발점 B · 기존 구조 개선

improve-codebase-architecture

후보와 전후 그림은 OS 임시 폴더의 HTML 보고서에 저장합니다. 후보를 고르고 논의한 설계는 대화와 필요한 용어·결정 문서에 남습니다.

다음 입력: 선택한 후보의 합의된 설계 + 코드 근거. 보고서는 후보를 설명하는 임시 자료입니다.

↓ 합의한 대화·설계와 현재 코드 이해

  1. 1 · 명세로 정리

    to-spec

    입력: 현재 대화의 합의와 코드 이해. 다시 처음부터 인터뷰하지 않고 내용을 종합하며, 검증 지점을 확인합니다.

    저장 → GitHub Issue: 명세

    개선 목적·사용자 동작·설계 결정·검증·제외 범위를 이슈 본문으로 등록합니다.

    다음 요청 예시: $to-tickets #N 명세를 구현 티켓으로 나눠줘

  2. 2 · 실행 가능한 작업으로 분할

    to-tickets

    입력: 앞 단계 명세 이슈의 본문·댓글. 계획이나 현재 대화에서 직접 시작할 수도 있습니다. 작업 크기와 선행 관계를 함께 확인합니다.

    저장 → GitHub Issues: 구현 티켓들

    작업마다 별도 이슈를 만들고 완료 조건·원본 명세 연결·선행 관계를 남깁니다. 명세 이슈와 구현 티켓은 역할이 다릅니다.

    다음 요청 예시: $implement-spec #N 명세와 연결된 티켓들을 구현해줘

  3. 3 · 코드로 구현하고 검증

    implement-spec / implement

    입력: 전체 구현은 명세 + 연결된 티켓과 선행 관계, 한 작업은 해당 티켓·요구사항을 읽습니다.

    저장 → 작업 브랜치의 코드·테스트 + GitHub PR·이슈

    구현을 커밋하고 프로젝트 절차에 따라 PR로 제출합니다. 리뷰·CI·완료 근거는 연결된 PR·이슈에서 확인합니다.

    내부에서 이어짐: 필요한 TDD → code-review. PR 본문 작성에는 pr를 사용합니다. 리뷰는 변경 diff와 원본 명세·요구사항을 읽습니다.

화살표는 자료를 넘기는 관계입니다. to-spec이 끝났다고 to-tickets나 구현이 자동으로 시작되지는 않습니다. 다음 스킬을 이름으로 요청합니다. 이미 확정된 작은 작업은 바로 implement로 시작해도 됩니다.

다른 세션에서도 GitHub 자료를 읽고 이어갑니다. 이슈 번호·URL을 전달하고, 대화에만 남은 결정은 handoff로 인계합니다. 임시 보고서의 파일 경로는 같은 컴퓨터에서만 접근할 수 있으므로 필요한 결론과 근거를 명세에 담습니다.

→
에이전트가 이어서 사용

implement는 합의한 검증 지점에서 가능한 경우 tdd를 사용하고 완료 뒤 code-review를 호출합니다. implement-spec은 티켓별 TDD와 전체 통합 뒤 리뷰를 수행합니다.

리뷰는 코딩 기준(Standards)과 요구사항(Spec)을 별도 에이전트가 검토합니다. PR 본문을 쓸 때는 pr로 변경·증거·위험을 설명합니다.

결과: 검증한 변경과 리뷰·PR

리뷰를 따로 요청하지 않아도 됩니다. 구현 스킬의 절차에 포함됩니다. 리뷰만 필요하면 code-review를 직접 요청할 수도 있습니다.

자동 선택은 항상 실행된다는 뜻이 아닙니다. 에이전트가 필요에 따라 선택할 수 있는 스킬과 사람이 이름을 지정해 시작하는 스킬이 있습니다. 전체 27개 목록과 호출 관계에서 확인합니다.

머지와 배포는 별개입니다. 리뷰와 필수 자동 검사(CI)를 통과하면 프로젝트 기준에 따라 코드를 합칩니다. 실제 서비스 배포는 사람이 지시한 범위에서 수행합니다. 스킬의 리뷰와 GitHub의 CI도 별도 검사입니다.

사람은 언제 결정하나요?

목표와 선택

중요한 결정을 정할 때

원하는 사용자 동작, 개선할 후보, 중요한 설계 선택을 함께 정합니다. 이미 합의한 결정은 승인 근거로 기록하고 반복 확인하지 않습니다.

작업 범위

새 선택이 필요할 때

미정 사항이 남았거나 합의한 요구·아키텍처를 바꿔야 하면 에이전트가 이유와 선택지를 설명합니다. 시작 단계만 맡길 수도, 정한 범위의 전체 작업을 맡길 수도 있습니다.

운영 실행

실제 서비스에 적용할 때

“운영에 배포해”처럼 실행 범위를 지시합니다. 운영 데이터 변경과 비용이 드는 작업도 지시한 범위 안에서 진행합니다.

진행 상황은 GitHub Issues와 연결된 PR에서 확인합니다. 이해가 어려우면 wait-what으로 재설명을, 다른 세션으로 옮길 때는 handoff로 인계를, 작업 후에는 retro로 회고를 요청할 수 있습니다.

03

코드 구조는 어떠한가

업무 규칙을 가운데 한 곳에 모아 두고, 웹 화면·AI 에이전트·데이터 저장소 같은 바깥 부품을 그 주위에 연결하는 구조입니다. 입구가 둘이어도 규칙이 한 곳에만 있으니, 어느 쪽으로 와도 똑같이 동작합니다.

헥사고날 구조

육각형(헥사곤) 가운데에 핵심 규칙을, 바깥에 갈아 끼울 수 있는 연결 부품을 두는 설계 방식입니다.

들어오는 쪽 (요청을 받는 부품)

규칙은 한 곳에

“완료할 수 있는가” 같은 판단은 가운데 업무 규칙에만 둡니다. 화면이나 에이전트 쪽에 같은 규칙을 다시 만들지 않습니다.

함께 저장할 것은 한 번에

할 일 완료와 결과 기록처럼 같이 바뀌어야 하는 것은 한 번에 저장합니다. 하나라도 실패하면 전부 취소됩니다.

누가 무엇을 볼 수 있는지는 앱 서버가 지킵니다. AI 에이전트가 지침을 따르지 않더라도 보호 수준은 같습니다.

04

자주 묻는 질문

앱 사용

앱 안에 AI가 들어 있나요?

아니요. 앱은 할 일·기록·원칙을 정확하게 저장하고 꺼내 주는 역할만 합니다. 기록을 읽고 생각해서 판단하는 일은 사용자가 연결한 AI 에이전트(Claude·Codex)가 합니다. 검색을 위해 글을 숫자로 바꾸는 일(임베딩)에만 외부 서비스를 씁니다.

어떤 AI 에이전트로 쓸 수 있나요?

Claude와 Codex를 지원합니다. 각 에이전트에 플러그인을 설치하면 같은 도구와 같은 사용 요령으로 앱을 다룹니다.

내 기록은 누가 볼 수 있나요?

기본적으로 나만 볼 수 있습니다. 웹으로 오든 에이전트로 오든 서버가 누구인지 확인하고 그 사람의 데이터만 보여 줍니다. 팀 공유 같은 기능은 기본에 없고, 필요하면 기획서(PRD)와 결정 기록(ADR)을 바꿔서 추가합니다.

꼭 할 일을 먼저 만들어야 하나요?

아니요. 한 일은 언제든 바로 기록할 수 있습니다. 할 일은 미리 계획해 두고 싶을 때만 만들고, 끝낸 뒤 그 할 일에 연결해 기록을 남깁니다.

반복 할 일은 정해진 시간에 알림을 주나요?

아니요. 반복 할 일은 매일·매주(요일)·매월(날짜) 규칙으로 “언제 할 차례인지”를 정해 줄 뿐, 자동으로 실행하거나 알림을 보내지 않습니다. 그 회차에 기록이 하나라도 있으면 한 것으로, 없으면 아직 안 한 것으로 표시합니다. 끝낼 때는 완료 대신 중단하고, 나중에 다시 재개할 수 있습니다.

검색은 기록 본문까지 찾나요?

의미로 찾는 검색은 기록의 제목과 요약을 봅니다. 본문은 정확한 단어로 찾는 키워드 검색과 전체 내용 보기에 쓰입니다. 그래서 기록할 때 핵심을 요약에 잘 적어 두면 나중에 훨씬 잘 찾아집니다.

방금 쓴 기록이 검색에 안 나와요.

기록은 바로 저장되지만, 의미로 찾는 검색에 반영되기까지는 잠시 걸릴 수 있습니다. 앱은 “결과 없음”과 “아직 정리 중”을 구분해서 알려 주므로, 못 찾았다고 해서 기록이 없는 것은 아닙니다.

에이전트가 기록 속 문장을 명령으로 따르지는 않나요?

따르지 않습니다. 기록 안에 “이렇게 해라” 같은 문장이 있어도 에이전트와 서버는 참고 자료로만 다룹니다. 그리고 누가 무엇을 할 수 있는지는 서버가 지키기 때문에, 에이전트가 지침을 어기더라도 데이터 보호 수준은 같습니다.

“사용자 원칙”과 “코드 설계 원칙”은 같은 건가요?

다릅니다. 사용자 원칙은 앱 사용자가 저장해 두는 판단 기준(데이터)이고, 코드 설계 원칙은 개발 에이전트가 코드를 만들 때 따르는 문서입니다.

새 앱 만들기

내 업무에 맞는 앱으로 바꾸려면 무엇을 하나요?

업무 대상(예: 고객, 책)과 그 항목, 화면, 에이전트가 참고하는 사용 요령을 바꿉니다. 로그인·할 일·기록·원칙·검색은 그대로 씁니다. 에이전트에게 “정리해봐: 고객 관리 앱으로 바꾸고 싶어”처럼 시작하면 됩니다.

프로그래밍을 몰라도 쓸 수 있나요?

그것이 목표입니다. 사람은 무엇을 왜 만들지 정하고, 중요한 결정을 승인하고, 배포를 지시하면 됩니다. 코드 작성과 검증은 에이전트가 합니다. 다만 서비스 계정 연결이나 비용이 드는 작업처럼 사람이 직접 결정해야 하는 일은 남아 있습니다.

비용이 드나요?

앱은 Supabase(서버·데이터베이스), Pinecone(검색용 임베딩), GitHub Pages(웹 화면) 같은 외부 서비스를 씁니다. 각 서비스의 요금은 사용량과 요금제에 따라 다릅니다. 비용이 드는 서비스 생성은 에이전트가 마음대로 하지 않고 사람이 지시할 때만 합니다.

개발 진행

기획을 바꾸고 싶으면 어떻게 하나요?

“grill-with-docs로 정리하자: …”부터 시작합니다. 구체적으로 합의한 내용은 PRD·ADR에 반영하고 같은 승인을 반복 요청하지 않습니다. 역할과 인계를 따릅니다. 문서를 직접 고쳐도 되지만, 그때도 관련 작업에 영향이 있는지 에이전트에게 확인시키는 것이 좋습니다.

에이전트가 방향을 잘못 잡은 것 같아요.

“멈추고 지금까지 한 것과 남은 것을 정리해줘”라고 말한 뒤 다시 정하면 됩니다. 같은 실패를 반복하면 원인과 수정 결과를 확인하고 모델·추론 강도 정책에 따라 조정합니다.

어디까지 진행됐는지 모르겠어요.

“GitHub issue #N의 진행 상태를 정리해줘”라고 하면 됩니다. issue에서 결과·blocker·남은 작업을 확인하고 연결된 PR과 checks에서 리뷰·CI·머지 증거를 확인합니다. 기록 규칙을 따릅니다.

PR이 너무 커서 읽기 어려워요.

“이 PR을 작은 PR로 나눠줘”라고 요청합니다. PR은 30분 안에 검토할 수 있는 크기를 기준으로 합니다.

머지하면 바로 실제 서비스에 반영되나요?

아니요. 머지는 바뀐 코드를 공식 코드에 합치는 것까지입니다. 실제 사용자가 쓰는 서비스에 올리는 배포는 사람이 “배포해”라고 지시할 때만 합니다.

에이전트가 실제 데이터를 망가뜨리지는 않나요?

시험은 실제 서비스와 분리된 환경에서 합니다. 실제 데이터베이스 변경, 데이터 복원, 비밀값 교체처럼 되돌리기 어려운 일은 사람이 지시한 범위에서만 합니다.

개발 에이전트를 하나만 써도 되나요?

네. 같은 스킬 정본과 프로젝트 문맥으로 일합니다. implement는 직접 구현하고 implement-spec은 여러 티켓을 배정·통합합니다. code-review로 Standards와 Spec을 분리해 검토합니다.

어떤 모델을 골라야 하나요?

Codex는 GPT-6.1 Sol, Claude Code는 Opus 5.5를 사용합니다. 보통 medium으로 시작하고 작업 난이도에 맞춰 같은 모델의 추론 강도를 조절합니다. 상세한 선택·지원 확인은 모델 정책을 따릅니다.

이 페이지와 다른 문서의 내용이 다르면요?

링크된 원래 문서가 맞습니다. 이 페이지는 이해를 돕는 안내이며, 지금 어디까지 만들어졌는지는 START-HERE의 현재 상태에서 확인합니다.
