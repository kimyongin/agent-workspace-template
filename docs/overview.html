01

무엇을 만드는가

할 일·활동 기록·판단 원칙을 쌓고, 그 기록을 사람과 AI 에이전트가 함께 다음 업무에 쓰는 앱입니다. 그리고 그런 앱을 도메인마다 빠르게 만들 수 있게 하는 템플릿입니다.

해결하는 문제

문제

해 둔 일이 다음 판단에 쓰이지 않는다

무엇을 왜 했고 결과가 어땠는지가 흩어져, 다음에 비슷한 일을 할 때 다시 찾거나 기억에 의존합니다.

해결

기록을 쌓고 검색해 원문으로 다시 꺼내 쓴다

기록마다 제목·요약에 핵심을, 본문에 근거를 남기고 검색으로 찾아 원문을 확인합니다. 모델을 재학습시키지 않고 작업할 때 꺼내 씁니다.

문제

사람이 쓰는 앱과 에이전트가 쓰는 도구가 따로 논다

입구마다 규칙이 다르면 결과·권한·데이터가 어긋나고, 한쪽에서 한 일을 다른 쪽에서 이어가기 어렵습니다.

해결

웹과 에이전트가 같은 기능과 데이터를 쓴다

사람은 웹 앱으로, 에이전트는 플러그인으로 들어오지만 서버에서는 같은 업무 로직을 실행합니다. 웹에서 만든 일을 에이전트가 이어받을 수 있습니다.

문제

도메인이 바뀔 때마다 처음부터 만든다

인증·할 일·기록·검색 같은 공통 기반을 앱마다 다시 짓습니다.

해결

복제하고 도메인 부분만 바꾼다

공통 기능은 그대로 두고 예제 엔터티의 속성·업무 규칙·화면·제품 스킬만 바꿔 새 앱을 시작합니다.

모든 앱이 갖는 기본 기능

계획

할 일

앞으로 할 행동. 한 번 하는 일회성 할 일과 매일·매주·매월 되풀이하는 반복 할 일.

결과

활동 기록

실제로 한 일과 결과. 할 일 없이도 바로 쓸 수 있습니다.

기준

사용자 원칙

사용자가 저장해 두는 판단 기준. 에이전트가 판단할 때 먼저 확인합니다.

회수

검색과 원문 확인

쌓인 할 일·기록·원칙을 찾고, 결과에서 원본으로 이어집니다.

기록이 지식이 되는 순환

  1. 할 일 계획앞으로 할 일을 만든다
  2. 수행웹이나 에이전트로 한다
  3. 결과 기록제목·요약에 핵심, 본문에 근거
  4. 새 질문다음 업무에서 생긴다
  5. 원칙·기록 검색 → 원문 확인관련 자료를 찾아 원문을 읽는다
  6. 에이전트의 판단다음 할 일과 기록으로 이어진다

↺ 판단의 결과가 다시 할 일과 기록이 되어 처음으로 돌아갑니다.

02

어떻게 사용하는가

입구는 둘이지만 서버에서는 같은 기능을 실행하므로 결과·권한·변경 범위가 같습니다. 앱은 데이터를 정확히 보관·조회·변경하고, 판단은 외부 에이전트가 합니다. 앱 안에 대화형 AI를 넣지 않습니다.

사람

웹 앱에서

접속
브라우저로 웹 앱을 열고 Google 계정으로 로그인합니다.
하는 일
할 일을 만들고 완료하거나, 반복 할 일의 회차에 기록을 남깁니다. 기록·원칙을 쓰고, 검색해서 원문을 엽니다.
특징
목록·상세·편집 화면으로 데이터를 직접 보고 관리합니다. 에이전트가 참고하거나 남긴 기록도 여기서 열어 확인할 수 있습니다.
AI 에이전트 (Claude·Codex)

플러그인으로

접속
플러그인을 설치하고 MCP 인증으로 앱에 연결합니다. 웹 로그인과는 별도 인증입니다.
하는 일
“지난번 비슷한 일은 어떻게 했지?”처럼 물으면 원칙과 기록을 찾아 원문을 읽고 판단합니다. 할 일을 처리하고 결과를 기록합니다.
특징
플러그인은 두 가지를 함께 줍니다. MCP 연결은 데이터 조회·업무 실행 도구를, 제품 스킬은 무엇을 먼저 찾고 원문을 어떻게 확인하고 결과를 어떻게 기록할지를 안내합니다.

웹과 에이전트를 오가며 이어지는 예

  1. 웹에서 할 일 작성사람
  2. 에이전트가 읽고 수행관련 원칙·기록을 찾아 참고
  3. 결과를 기록으로 저장제목·요약·본문
  4. 웹에서 결과 확인사람
  5. 다음 대화에서 다시 검색쌓인 기록을 근거로

웹 앱(사람)플러그인(에이전트)

어느 입구로 써도 지켜지는 것

내 데이터는 나만

기본 접근은 소유자 본인으로 한정합니다. 공유·조직 기능은 요구가 생기면 별도로 추가합니다.

“없음”과 “아직 못 찾음”을 구분

검색 결과 없음, 색인 중, 검색 장애를 구분해 알려 줍니다. 새 기록은 즉시 저장되지만 의미 검색 반영은 잠시 늦을 수 있습니다.

기록 속 문장은 지시가 아니다

저장된 기록 안에 “이렇게 해라” 같은 문장이 있어도 에이전트와 서버는 자료로만 다룹니다.

03

어떻게 개발을 시키는가

사람은 “무엇을, 왜”를 정하고 개발 에이전트(Codex·Claude Code)는 “어떻게”를 맡습니다. 짧은 말로 단계를 넘기면 에이전트가 계획·구현·검증·머지까지 진행합니다.

  1. 정리해봐: …하고 싶은 것을 말한다
  2. PRD 반영해 / ADR 초안 만들어제품·결정에 영향이 있을 때만, 사람이 승인
  3. 티켓 만들어목표·PR 분할·검증 방법
  4. 티켓 진행해작은 PR로 구현·검증
  5. 교차 리뷰 → 머지다른 에이전트가 리뷰, 통과하면 머지
  6. 배포해 (환경)사람의 지시가 곧 승인

사람이 말하는 것에이전트끼리 처리

이렇게 말하면에이전트가 하는 일사람이 할 일
정리해봐: …내용을 정리하고 PRD·ADR에 영향이 있는지 알려 준다결과를 읽는다
PRD 반영해 / ADR 초안 만들어PRD·ADR 변경 PR을 만든다PR을 읽고 승인한다
티켓 만들어목표·관련 문서·PR 분할 계획·검증 방법을 티켓에 적는다없음
티켓 진행해작은 PR로 나눠 구현하고 검증한다다른 에이전트에게 PR #N 리뷰해줘
(말할 필요 없음)리뷰와 자동 검사를 통과하면 머지한다없음
배포해 (환경)검증된 revision을 확인하고 배포한다명령이 곧 승인
누가 무엇을 소유하나

사람은 PRD·ADR, 에이전트는 나머지

  • PRD(무엇을 왜)와 ADR(되돌리기 비싼 결정)은 사람이 승인합니다.
  • 티켓·구현·테스트·리뷰·가이드·스킬은 에이전트가 소유합니다.
  • 작업 중 PRD·ADR을 벗어나야 하면 에이전트가 멈추고 묻습니다.

두 에이전트가 같은 지침을 읽는다

  • Codex: $develop-agent-app 요청
  • Claude Code: /develop-agent-app 요청
  • 스킬 이름 없이 말해도 AGENTS.md(Claude Code는 CLAUDE.md를 거쳐)가 같은 규칙을 읽게 합니다.
  • 교차 리뷰는 만든 쪽이 아닌 다른 에이전트에게 맡깁니다.

04

코드 구조는 어떠한가

복제해서 쓰는 구현형 템플릿입니다. 업무 로직을 가운데(core)에 두고 웹·에이전트·DB·외부 서비스를 바깥에서 연결하는 헥사고날 구조라, 입구가 둘이어도 규칙은 한 곳에만 있습니다.

템플릿: 무엇을 바꾸고 무엇을 유지하나

새 앱마다 바꾸는 것

예제 엔터티 Entity와 그 주변

명시적인 컬럼(id, prop1, prop2…)을 가진 테이블 하나와 그 모델·유스케이스·화면·제품 스킬입니다. 예를 들어 고객 앱은 entity 자리를 customers로 바꿉니다.

그대로 쓰는 것

인증·할 일·기록·원칙·검색의 공통 구조

모든 앱의 기본 기능이라 다시 만들지 않습니다. 여러 도메인을 한 테이블에 담는 범용 키–값 저장소는 만들지 않습니다.

규칙은 한 곳에

업무 판단은 도메인에만 둡니다. 화면·MCP·DB 프로시저에 같은 규칙을 다시 만들지 않습니다.

함께 성공할 것은 한 트랜잭션으로

원본 저장과 후속 작업의 큐 등록을 하나의 Postgres 트랜잭션으로 확정합니다. 외부 호출은 트랜잭션 밖에서 합니다.

보호는 서버가

권한·업무 규칙·데이터 일관성은 서버가 강제합니다. 에이전트가 스킬을 따르든 말든 보호 수준은 같습니다.
