대상을 바꿀 때는 그 대상의 항목, 화면, 에이전트가 참고하는 사용 요령을 함께 바꿉니다. 세 앱과 값은 이해를 돕는 예시입니다.

두 가지 길로 사용한다: 웹 앱과 AI 에이전트

사람은 두 가지 길로 앱을 씁니다. 웹 화면에서 직접 다루거나, AI 에이전트에게 말로 맡기거나. 어느 길로 가도 도착하는 곳은 같은 앱이라, 같은 규칙과 같은 데이터가 적용됩니다.

사람

웹 앱에서 직접

브라우저 · Google 계정으로 로그인

목록·상세·편집 화면에서 할 일, 기록, 원칙을 직접 보고 쓰고 고칩니다. 내가 누른 대로 정확히 바뀝니다.

데이터를 직접 조작

AI 에이전트에게 말로

Claude·Codex · 플러그인으로 앱에 연결

“지난번 비슷한 일은 어떻게 했지?”라고 물으면 에이전트가 관련 기록과 원칙을 찾아 읽고, 생각해서 답하거나 일을 처리한 뒤 결과를 기록합니다.

플러그인이란?

AI 에이전트에 설치하는 확장 기능입니다. 앱을 다루는 도구(조회·저장)와 “자료를 어떻게 찾고, 결과를 어떻게 기록할지” 알려 주는 사용 요령이 함께 들어 있습니다. 에이전트 연결은 웹 로그인과 따로 인증합니다.

두 길을 오가며 이어서 쓴다

웹에서 할 일을 적어 두면 에이전트가 그걸 읽고 처리해 결과를 기록합니다. 그 결과는 웹에서 바로 확인할 수 있고, 다음 대화에서 에이전트가 다시 찾아 참고합니다.

한 일이 다음 일의 참고 자료가 되는 순환

시작은 “일을 한다”부터

할 일을 미리 만들지 않아도 됩니다. 한 일을 바로 기록하면 그때부터 순환이 시작됩니다.

할 일은 계획이 필요할 때만

미리 계획해 두고 싶으면 할 일을 만들고, 끝낸 뒤 그 할 일에 연결해 기록을 남깁니다.

AI를 다시 가르치지 않는다

AI 모델을 새로 학습시키는 대신, 일할 때마다 쌓인 기록을 찾아 읽게 합니다. 그래서 기록이 늘수록 바로 더 똑똑하게 도와줍니다.

정본: PRDADR-0004 검색 방식제품 스킬ADR-0005 플러그인ADR-0006 접근과 인증보안 가이드

02

어떻게 개발을 시키는가

코드는 AI 개발 에이전트(Codex, Claude Code)가 작성합니다. 사람은 무엇을 왜 만들지 정하고 중요한 결정을 승인하며, 짧은 말로 다음 단계를 지시합니다. 먼저 이 과정에서 오가는 문서와 용어부터 알아 둡니다.

알아 둘 용어

여기 없는 용어는 용어집에서 찾습니다.

PRD 제품 요구사항 문서사람이 정함

무엇을, 누구를 위해, 왜 만드는지 적은 기획서입니다. 어떤 기능이 꼭 있어야 하는지도 여기서 정합니다.

집을 짓기 전 “방 3개, 남향, 4인 가족용”이라고 적은 요청서

ADR 아키텍처 결정 기록사람이 승인

나중에 바꾸기 어렵고 비용이 큰 기술 선택(어떤 서비스를 쓸지, 데이터를 어떻게 보호할지 등)과 그 이유를 남긴 결정 메모입니다.

“기초는 철근 콘크리트로 한다, 이유는 …”라는 설계 결정서

티켓 작업 지시서에이전트가 작성

해야 할 작업 하나를 적은 문서입니다. 목표, 작은 단계로 나눈 계획, 다 됐는지 확인하는 방법, 진행 기록이 들어 있습니다.

“이번 주 욕실 공사: 배관 → 방수 → 타일, 물 새는지 확인”

PR Pull Request, 변경 요청에이전트가 작성

“이렇게 고쳤으니 검토하고 반영해 주세요”라는 요청입니다. 무엇을 어떻게 바꿨는지 한 묶음으로 보여 줍니다. 한 번에 검토하기 쉽도록 작게 나눠 올립니다.

공사 한 구간을 마치고 받는 “검수 요청서”

리뷰와 머지 검토와 반영에이전트끼리

구현 대화의 내용을 모르는 새 세션이 로컬 커밋을 검토(리뷰)하고, 같은 버전을 PR로 제출해 자동 검사까지 통과하면 공식 코드에 합칩니다(머지). 순서는 개발 절차를 따릅니다.

시공하지 않은 감리자가 검수하고, 통과하면 설계도 원본에 반영

배포 실제 서비스에 올리기사람이 지시

합쳐진 변경을 실제 사용자가 쓰는 서비스에 올리는 일입니다. 머지했다고 바로 배포되지 않고, 사람이 지시할 때만 합니다.

공사를 마친 집에 실제로 입주하는 날

왼쪽은 사람이 에이전트에게 하는 말, 오른쪽은 그 말을 듣고 에이전트가 하는 일입니다. 위에서 아래로 진행합니다.

사람이 하는 말 에이전트가 하는 일

1

요청을 정리해서 무엇을 바꿔야 하는지 알려 줍니다. 특히 기획서(PRD)나 결정 기록(ADR)까지 바꿔야 하는 일인지 판단해 줍니다.

결과물: 정리 메모

“PRD 반영해” / “ADR 초안 만들어”

1번에서 기획이나 중요한 결정을 바꿔야 한다고 했을 때만 하는 단계입니다. 그런 일이 아니면 바로 3번으로 갑니다.

✓ 수정안을 읽고 괜찮으면 승인합니다

2

기획서나 결정 기록을 어떻게 바꿀지 수정안을 만들어 올립니다. 사람이 승인하기 전에는 그 방향으로 만들지 않습니다.

결과물: PRD·ADR 변경 PR

“티켓 만들어”

무엇을 만들지 작업 지시서로 정리하라는 뜻입니다.

3

목표, 작게 나눈 작업 순서, 다 됐는지 확인하는 방법을 티켓에 적습니다.

결과물: 티켓

“티켓 진행해”

티켓대로 만들기 시작하라는 뜻입니다.

4

본 대화에서 범위와 작업을 정하고, 작은 기능별 새 대화에 구현과 검증을 맡깁니다. 결과와 인계는 티켓에 남기고 본 대화에서 통합합니다.

결과물: PR

따로 말하지 않아도 됩니다. 에이전트가 만든 대화의 내용을 모르는 새 서브 에이전트를 띄워 검토하게 합니다. 다른 에이전트(Codex·Claude)의 교차 리뷰는 원할 때만 요청합니다.

5

작업 결과의 버그, 빠진 확인, 기획이나 결정에서 벗어난 부분을 독립적으로 검토합니다. 수정이 필요하면 구현 담당이 고칩니다. 자세한 절차는 마무리 순서를 따릅니다.

따로 말하지 않아도 됩니다

6

리뷰 결론이 “머지 가능”이고 자동 검사도 통과하면 공식 코드에 합칩니다(머지). 아직 실제 서비스에 올라간 것은 아닙니다.

각 세션의 역할과 작업 난이도에 맞는 모델을 선택합니다. 상세한 선택 기준은 모델 정책을 따릅니다.

사람이 개입하는 때

네 가지 경우만 챙기면 됩니다

  • 기획서(PRD)·결정 기록(ADR) 변경을 승인할 때
  • 에이전트가 “기획이나 결정과 다르게 해야 합니다”라며 멈추고 물을 때
  • 다른 에이전트의 교차 리뷰를 원할 때(선택): 리뷰 자체는 에이전트가 알아서 합니다
  • 배포, 실제 데이터 변경, 비용이 드는 일을 지시할 때
시작하는 법

하나만 써도, 둘 다 써도 됩니다

  • Codex에서는 $develop-agent-app 요청
  • Claude Code에서는 /develop-agent-app 요청
  • 스킬 이름 없이 “할 일 화면을 고쳐줘”처럼 평범하게 요청해도 됩니다.
  • 두 에이전트는 공통 지침을 따릅니다. 자세한 요청 방법은 에이전트와 일하는 방법에서 봅니다.

03

코드 구조는 어떠한가

업무 규칙을 가운데 한 곳에 모아 두고, 웹 화면·AI 에이전트·데이터 저장소 같은 바깥 부품을 그 주위에 연결하는 구조입니다. 입구가 둘이어도 규칙이 한 곳에만 있으니, 어느 쪽으로 와도 똑같이 동작합니다.

헥사고날 구조

육각형(헥사곤) 가운데에 핵심 규칙을, 바깥에 갈아 끼울 수 있는 연결 부품을 두는 설계 방식입니다.

들어오는 쪽 (요청을 받는 부품)

사람웹 앱 → HTTP화면에서 보낸 요청을 받음
AI 에이전트플러그인 → MCP에이전트의 도구 호출을 받음
예약 작업검색 색인 작업새 기록을 검색되게 정리

핵심 (core)

특정 서비스에 묶이지 않음

업무 처리 순서유스케이스 · 읽고, 판단하고, 저장
업무 규칙도메인 · “완료할 수 있는가?” 같은 판단
연결 규격포트 · 바깥 부품이 맞춰야 할 모양

나가는 쪽 (실제 서비스를 쓰는 부품)

Supabase데이터베이스원본 저장, 권한 검사
Supabase작업 대기열 · 벡터 검색오래 걸리는 일 줄 세우기, 의미로 찾기
Supabase Auth로그인 · 에이전트 인증둘은 서로 다른 인증
Pinecone임베딩글을 검색용 숫자로 바꿈

규칙은 한 곳에

“완료할 수 있는가” 같은 판단은 가운데 업무 규칙에만 둡니다. 화면이나 에이전트 쪽에 같은 규칙을 다시 만들지 않습니다.

함께 저장할 것은 한 번에

할 일 완료와 결과 기록처럼 같이 바뀌어야 하는 것은 한 번에 저장합니다. 하나라도 실패하면 전부 취소됩니다.

보호는 서버가

누가 무엇을 볼 수 있는지는 앱 서버가 지킵니다. AI 에이전트가 지침을 따르지 않더라도 보호 수준은 같습니다.

04

자주 묻는 질문

앱 사용

앱 안에 AI가 들어 있나요?

아니요. 앱은 할 일·기록·원칙을 정확하게 저장하고 꺼내 주는 역할만 합니다. 기록을 읽고 생각해서 판단하는 일은 사용자가 연결한 AI 에이전트(Claude·Codex)가 합니다. 검색을 위해 글을 숫자로 바꾸는 일(임베딩)에만 외부 서비스를 씁니다.

어떤 AI 에이전트로 쓸 수 있나요?

Claude와 Codex를 지원합니다. 각 에이전트에 플러그인을 설치하면 같은 도구와 같은 사용 요령으로 앱을 다룹니다.

내 기록은 누가 볼 수 있나요?

기본적으로 나만 볼 수 있습니다. 웹으로 오든 에이전트로 오든 서버가 누구인지 확인하고 그 사람의 데이터만 보여 줍니다. 팀 공유 같은 기능은 기본에 없고, 필요하면 기획서(PRD)와 결정 기록(ADR)을 바꿔서 추가합니다.

꼭 할 일을 먼저 만들어야 하나요?

아니요. 한 일은 언제든 바로 기록할 수 있습니다. 할 일은 미리 계획해 두고 싶을 때만 만들고, 끝낸 뒤 그 할 일에 연결해 기록을 남깁니다.

반복 할 일은 정해진 시간에 알림을 주나요?

아니요. 반복 할 일은 매일·매주(요일)·매월(날짜) 규칙으로 “언제 할 차례인지”를 정해 줄 뿐, 자동으로 실행하거나 알림을 보내지 않습니다. 그 회차에 기록이 하나라도 있으면 한 것으로, 없으면 아직 안 한 것으로 표시합니다. 끝낼 때는 완료 대신 중단하고, 나중에 다시 재개할 수 있습니다.

검색은 기록 본문까지 찾나요?

의미로 찾는 검색은 기록의 제목과 요약을 봅니다. 본문은 정확한 단어로 찾는 키워드 검색과 전체 내용 보기에 쓰입니다. 그래서 기록할 때 핵심을 요약에 잘 적어 두면 나중에 훨씬 잘 찾아집니다.

방금 쓴 기록이 검색에 안 나와요.

기록은 바로 저장되지만, 의미로 찾는 검색에 반영되기까지는 잠시 걸릴 수 있습니다. 앱은 “결과 없음”과 “아직 정리 중”을 구분해서 알려 주므로, 못 찾았다고 해서 기록이 없는 것은 아닙니다.

에이전트가 기록 속 문장을 명령으로 따르지는 않나요?

따르지 않습니다. 기록 안에 “이렇게 해라” 같은 문장이 있어도 에이전트와 서버는 참고 자료로만 다룹니다. 그리고 누가 무엇을 할 수 있는지는 서버가 지키기 때문에, 에이전트가 지침을 어기더라도 데이터 보호 수준은 같습니다.

“사용자 원칙”과 “코드 설계 원칙”은 같은 건가요?

다릅니다. 사용자 원칙은 앱 사용자가 저장해 두는 판단 기준(데이터)이고, 코드 설계 원칙은 개발 에이전트가 코드를 만들 때 따르는 문서입니다.

새 앱 만들기

내 업무에 맞는 앱으로 바꾸려면 무엇을 하나요?

업무 대상(예: 고객, 책)과 그 항목, 화면, 에이전트가 참고하는 사용 요령을 바꿉니다. 로그인·할 일·기록·원칙·검색은 그대로 씁니다. 에이전트에게 “정리해봐: 고객 관리 앱으로 바꾸고 싶어”처럼 시작하면 됩니다.

프로그래밍을 몰라도 쓸 수 있나요?

그것이 목표입니다. 사람은 무엇을 왜 만들지 정하고, 중요한 결정을 승인하고, 배포를 지시하면 됩니다. 코드 작성과 검증은 에이전트가 합니다. 다만 서비스 계정 연결이나 비용이 드는 작업처럼 사람이 직접 결정해야 하는 일은 남아 있습니다.

비용이 드나요?

앱은 Supabase(서버·데이터베이스), Pinecone(검색용 임베딩), GitHub Pages(웹 화면) 같은 외부 서비스를 씁니다. 각 서비스의 요금은 사용량과 요금제에 따라 다릅니다. 비용이 드는 서비스 생성은 에이전트가 마음대로 하지 않고 사람이 지시할 때만 합니다.

개발 진행

기획을 바꾸고 싶으면 어떻게 하나요?

“정리해봐: …”부터 시작합니다. 사람과 본 세션이 함께 설계·결정하고 구현 세션은 합의 안의 상세 구조를 정합니다. 기획서(PRD)나 결정 기록(ADR) 변경이 필요하면 수정안을 승인합니다. 역할과 인계를 따릅니다. 문서를 직접 고쳐도 되지만, 그때도 관련 작업에 영향이 있는지 에이전트에게 확인시키는 것이 좋습니다.

에이전트가 방향을 잘못 잡은 것 같아요.

“멈추고 지금까지 한 것과 남은 것을 정리해줘”라고 말한 뒤 다시 정하면 됩니다. 같은 실패를 반복하면 원인과 수정 결과를 확인하고 모델·추론 강도 정책에 따라 조정합니다.

어디까지 진행됐는지 모르겠어요.

“티켓 진행 상태 정리해줘”라고 하면 됩니다. 현재 요약은 시작 문서와 티켓에, 제출 후 최종 리뷰·CI·머지 증거는 PR 완료 코멘트와 checks에 있습니다. 기록 규칙을 따릅니다.

PR이 너무 커서 읽기 어려워요.

“이 PR을 작은 PR로 나눠줘”라고 요청합니다. PR은 30분 안에 검토할 수 있는 크기를 기준으로 합니다.

머지하면 바로 실제 서비스에 반영되나요?

아니요. 머지는 바뀐 코드를 공식 코드에 합치는 것까지입니다. 실제 사용자가 쓰는 서비스에 올리는 배포는 사람이 “배포해”라고 지시할 때만 합니다.

에이전트가 실제 데이터를 망가뜨리지는 않나요?

시험은 실제 서비스와 분리된 환경에서 합니다. 실제 데이터베이스 변경, 데이터 복원, 비밀값 교체처럼 되돌리기 어려운 일은 사람이 지시한 범위에서만 합니다.

개발 에이전트를 하나만 써도 되나요?

네. Codex와 Claude Code 중 하나만 써도 같은 지침과 절차로 일합니다. 리뷰는 에이전트가 새 서브 에이전트를 띄워 알아서 합니다. 다른 에이전트의 교차 리뷰는 원할 때만 요청합니다.

어떤 모델을 골라야 하나요?

Codex는 GPT-6.1 Sol, Claude Code는 Opus 5.5를 사용합니다. 보통 medium으로 시작하고 작업 난이도에 맞춰 같은 모델의 추론 강도를 조절합니다. 상세한 선택·지원 확인은 모델 정책을 따릅니다.

이 페이지와 다른 문서의 내용이 다르면요?

링크된 원래 문서가 맞습니다. 이 페이지는 이해를 돕는 안내이며, 지금 어디까지 만들어졌는지는 START-HERE의 현재 상태에서 확인합니다.
