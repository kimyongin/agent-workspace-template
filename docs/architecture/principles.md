# 코드 설계 원칙

## 핵심 컨셉

도메인과 유스케이스를 중심으로 업무 로직을 구현하고, HTTP·MCP·Supabase·외부 서비스를 포트와 어댑터로 연결한다. 필요한 일관성은 명시적으로 보장하며, 실제 사용자 기능을 완성하는 과정에서 최소한의 공통 구조를 만든다.

이 문서는 코드 변경을 판단하는 기준이다. 구체적인 플랫폼 구성은 [아키텍처](hexagonal-review.md), 파일 배치는 [폴더 구조](../design/template-structure.md), 작업 방법은 [Matt 스킬](../development/matt-skills.md)이 담당한다.

아래 원칙은 템플릿의 초기 설계 선택이다. 새 프로젝트의 도메인과 실제 경험에 따라 수정할 수 있다. 변경이 현재 원칙과 충돌하면 구현을 국소적으로 우회하기 전에 원칙의 적용 범위와 타당성을 검토한다. 일반적으로 적용할 새 방향이면 원칙과 관련 가이드·스킬·구현을 함께 갱신하고, 한정된 사례만 예외로 남긴다.

## 1. 업무 규칙과 실행 흐름을 구분한다

도메인은 업무의 의미, 유효한 값과 상태 변화의 조건을 표현한다. 유스케이스는 필요한 데이터를 읽고 도메인 규칙을 적용한 뒤 결과를 저장하는 실행 흐름과 트랜잭션 경계를 정한다.

예를 들어 할 일 완료 가능 여부는 도메인이 판단한다. 할 일을 읽고 완료 결과와 기록을 함께 저장하는 순서는 유스케이스가 담당한다. 실제 SQL과 트랜잭션 실행은 저장 어댑터가 담당한다. 업무 규칙을 화면·MCP 핸들러·DB 프로시저에 중복 구현하지 않는다.

## 2. HTTP와 MCP는 같은 유스케이스를 사용한다

진입점은 인증된 문맥과 입력을 내부 형식으로 변환하고 결과를 해당 프로토콜로 반환한다. 동일한 업무는 공통 유스케이스를 실행한다. 웹과 MCP의 도구 이름이 같을 필요는 없지만 결과·권한·변경 범위·오류와 재시도 의미는 같아야 한다.

기능 동등성은 노출된 이름의 개수로 판단하지 않는다. 편집 가능한 필드, 단건 조회, 전체 페이지 탐색, 목적별 행위까지 계약과 교차 테스트로 확인한다. 시스템 내부 테이블의 직접 CRUD까지 공개하는 원칙은 아니다.

## 3. 핵심 코드는 인프라 구현에 의존하지 않는다

도메인과 유스케이스는 필요한 입출력을 포트로 표현한다. 어댑터가 그 계약을 구현하고, 조립 지점에서 실제 구현을 연결한다. 핵심 코드에는 SDK·SQL·HTTP 요청 객체·환경변수 접근을 두지 않는다. 시간처럼 판단에 영향을 주는 값도 검증 가능한 입력으로 전달한다.

Supabase는 기본 플랫폼으로 적극 사용한다. 포트의 목적은 업무 규칙을 이해하고 수정하고 독립적으로 테스트할 수 있게 하는 것이다. 가상의 여러 DB 지원을 위해 인터페이스를 늘리지 않는다.

## 4. 일관성과 실패의 의미를 명시한다

함께 성공해야 하는 변경은 하나의 로컬 DB 트랜잭션으로 확정한다. 시간이 오래 걸리거나 재시도가 필요한 후속 처리는 큐로 분리한다. 원본 변경과 필수 작업 등록은 함께 확정하며, 접수와 실제 완료는 구분한다.

중복 실행을 막는 멱등성, 오래된 값의 덮어쓰기를 막는 충돌 검사, 과거 사실을 남기는 이력은 서로 다른 목적을 가진다. [ADR-0018](../adr/0018-server-ids-and-request-idempotency.md)의 채택한 방향은 서버 생성 트랜잭션에서 내부 ID를 발급·저장하고, 호출자가 재시도 동안 유지하는 요청 키로 같은 요청의 성공 결과를 재현하는 것이다. 같은 키의 다른 입력은 거절하고, 새로운 요청의 수정·삭제에는 대상 ID와 expected_version을 검사한다. 현재 인증·권한은 재시도에도 확인한다. 데이터·변경 기록·필수 큐·요청 성공 결과는 함께 확정한다.

자동 ID의 날짜 기반 형식·기존 UUID와 참조·서버 내부 예약 원장의 충돌 방지는 유지한다. 외부 발급 식별자는 입력값을 보존한다. 외부 작업은 의도를 로컬 변경과 함께 등록하고 커밋 후 실행하며, 공급자의 멱등 키·작업 ID·상태·결과로 재시도를 관리한다. 시간 경과만으로 외부 결과 불명을 실패로 확정하지 않는다. 공급자 기능이 없는 작업은 중복 실행·비용의 한계를 명시한다.

이는 채택한 계약이며 구현·검증 revision과 구체 수명·오류 계약은 [스펙 #289](https://github.com/kimyongin/agent-workspace-template/issues/289)가 소유한다. 공개 사전 예약과 준비 단계 발급은 제거하고 웹·HTTP/MCP·제품 스킬 호출자는 요청 키 계약으로 함께 전환한다. 운영 적용은 별도 배포 증거로 확인한다.

## 5. 데이터 정본과 수명을 분명히 한다

[ADR-0012](../adr/0012-current-state-and-unified-records.md)를 따른다. 엔터티·할 일·원칙은 최신 값의 정본이고 과거 내용과 판단 근거는 통합 기록에 남긴다. 기존 원칙 과거본·적용 snapshot은 보존 자료로 다루며 새 쓰기에 요구하는 구조가 아니다.

일반 기록과 로그 메모는 편집 가능하고 그 편집의 추가 로그를 만들지 않는다. 로그의 사건 식별정보는 유지한다. 별도 정정 체인이나 최초 메모 불변 보존을 요구하지 않는다. 메모에 필요한 내용을 남기되 모든 과거 원본의 전체 복원을 보장하지 않는다.

업무 변경은 입력한 메모를 그대로 기록 본문으로 저장하고, 메모가 비어 있으면 대상·행위·변경 항목처럼 확인 가능한 사실로 기본 설명을 생성한다. 웹은 작은 중앙 확인 단계에서 기록 메모·기록 태그와 변경 의사를 확인한 뒤 업무 변경과 기록을 함께 확정한다. MCP는 명시한 요청을 같은 트랜잭션으로 실행하며 추가 승인 단계를 만들지 않는다. 실패·무변경·동일 요청은 성공 기록을 중복 생성하지 않는다. 기록 편집은 같은 원본의 색인을 최신화한다.

본문으로 충분한 정보는 서술한다. 원칙 참고를 필수 연관키로 만들지 않는다. 선택적 다중 엔터티 관계와 수행 회차 식별은 실제 정확 조회·업무 상태 판정에 사용한다. 대상 삭제 뒤 기록의 당시 문맥을 보존하고, 과거 식별정보를 현재 존재하는 대상의 보증으로 취급하지 않는다.

기존 자료를 보존하는 이관안을 검증한 뒤 구 구조를 제거한다. 검색 색인은 원본에서 다시 만들 수 있는 파생 자료다. HTTP/MCP는 같은 업무 의미를 사용한다. 상세 인계와 검증은 [통합 기록 설계](unified-record-model.md)에 있다.

## 6. 도메인별로 구성하고 실제 필요에서 공통화한다

관련 모델·유스케이스·포트를 기능별로 가까이 둔다. 작은 기능은 타입과 함수로 시작하고, 실제 여러 사용처의 공통성이 확인되면 추출한다. 범용 payload 저장소, 명령 엔진, 모든 도메인에 강제하는 이력 체계를 선행 구축하지 않는다.

새 추상화에는 이를 사용하는 구체적인 기능과 줄어드는 중복이 있어야 한다. 새 도메인을 추가할 때 기존 모든 기능을 함께 수정해야 한다면 경계를 다시 검토한다.

## 7. 에이전트 지침과 서버 보장을 구분한다

에이전트용 배포 단위는 MCP 연결과 제품 스킬을 함께 담는 플러그인이다. 기능을 추가할 때 서버 도구 계약과 플러그인의 작업 안내를 함께 검토한다. 패키지가 통합되어도 서버 실행과 에이전트 지침의 책임은 구분한다.

제품용 스킬은 자료 탐색·결과 정리·도구 사용 순서를 안내한다. MCP 도구 계약은 실제 입력·출력·부수효과를 설명한다. 권한·업무 규칙·데이터 일관성은 서버가 강제한다. 스킬을 따르는지에 따라 데이터 보호 수준이 달라져서는 안 된다.

개발용 AGENTS.md, 제품용 스킬, 사용자가 저장하는 사용자 원칙(principles) 데이터는 별도 책임이다. 이 문서의 코드 설계 원칙은 개발 기준이며 사용자 원칙과 다르다. 특정 클라이언트의 스킬 지원을 모든 MCP 클라이언트의 기본 능력으로 가정하지 않는다.

## 8. 보장하는 경계에서 검증한다

도메인 규칙은 DB 없이 테스트한다. 저장·권한·트랜잭션·경쟁은 실제 격리 DB에서, HTTP/MCP 계약은 진입점에서, 사용자 흐름은 웹과 MCP를 연결해서 확인한다. 모의 구현의 성공만으로 실제 저장이나 권한 보장이 검증됐다고 판단하지 않는다.

검사 도구와 실제 서비스의 증거 범위는 [검사 도구의 한계](../development/verification.md#검사-도구의-한계)에서 구분한다.

아키텍처의 완료 기준은 폴더 형태가 아니라, 업무 규칙을 독립적으로 검증하고 여러 진입점에서 일관되게 실행할 수 있는가이다.

## 9. 실제 사용처를 기준으로 구 계약을 정리한다

API·MCP·저장 계약을 변경하면 웹·서버·제품 스킬·검사 도구의 호출자를 새 계약으로 함께 전환하고, 사용하지 않는 구 경로·도구·입력 alias·어댑터·임시 trigger를 제거한다. 호환 코드는 실제 이전 버전 사용처를 지원할 때만 둔다. 확인된 사용처가 없으면 가상의 외부 클라이언트를 이유로 구 인터페이스를 유지하지 않는다([ADR-0013](../adr/0013-retire-unused-contracts.md)).

실제 외부 사용처가 있는 경우에는 지원 대상·전환 방법·종료 조건과 정리 작업을 GitHub issue에 기록한다. 전환을 확인한 뒤 호환 코드를 제거한다. 사용처 현황이 불명확하면 소유자에게 확인하고, 미확인을 영구 지원 요구로 바꾸지 않는다.

인터페이스 제거와 과거 자료 삭제는 구분한다. 저장된 업무 기록·당시 문맥은 보존하고 새 조회 계약으로 읽을 수 있게 한다. 변경한 공개 경계에서 새 업무 흐름, 제거된 입력의 거부, 과거 자료 보존을 검증한다. 과거 migration은 유지하며 필요한 DB 변경은 전진 migration으로 수행한다. 코드 변경 승인은 운영 DB 적용이나 서비스 배포 승인과 별개다.
