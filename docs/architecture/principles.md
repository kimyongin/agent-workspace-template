# 코드 설계 원칙

## 핵심 컨셉

도메인과 유스케이스를 중심으로 업무 로직을 구현하고, HTTP·MCP·Supabase·외부 서비스를 포트와 어댑터로 연결한다. 필요한 일관성은 명시적으로 보장하며, 실제 사용자 기능을 완성하는 과정에서 최소한의 공통 구조를 만든다.

이 문서는 코드 변경을 판단하는 기준이다. 구체적인 플랫폼 구성은 [아키텍처](hexagonal-review.md), 파일 배치는 [폴더 구조](../design/template-structure.md), 작업 절차는 [개발 방법](../development/workflow.md)에서 관리한다.

## 1. 업무 규칙과 실행 흐름을 구분한다

도메인은 업무의 의미, 유효한 값과 상태 변화의 조건을 표현한다. 유스케이스는 필요한 데이터를 읽고 도메인 규칙을 적용한 뒤 결과를 저장하는 실행 흐름과 트랜잭션 경계를 정한다.

예를 들어 할 일 완료 가능 여부는 도메인이 판단한다. 할 일을 읽고 완료 결과와 기록을 함께 저장하는 순서는 유스케이스가 담당한다. 실제 SQL과 트랜잭션 실행은 저장 어댑터가 담당한다. 업무 규칙을 화면·MCP 핸들러·DB 프로시저에 중복 구현하지 않는다.

## 2. HTTP와 MCP는 같은 유스케이스를 사용한다

진입점은 인증된 문맥과 입력을 내부 형식으로 변환하고 결과를 해당 프로토콜로 반환한다. 동일한 업무는 공통 유스케이스를 실행한다. 웹과 MCP의 도구 이름이 같을 필요는 없지만 결과·권한·변경 범위·오류와 재시도 의미는 같아야 한다.

기능 동등성은 노출된 이름의 개수로 판단하지 않는다. 편집 가능한 필드, 단건 조회, 전체 페이지 탐색, 목적별 행위까지 계약과 교차 테스트로 확인한다. 시스템 내부 테이블의 직접 CRUD까지 공개하는 원칙은 아니다.

## 3. 핵심 코드는 인프라 구현에 의존하지 않는다

도메인과 유스케이스는 필요한 입출력을 포트로 표현한다. 어댑터가 그 계약을 구현하고, 조립 지점에서 실제 구현을 연결한다. 핵심 코드에는 SDK·SQL·HTTP 요청 객체·환경변수 접근을 두지 않는다. 시간처럼 판단에 영향을 주는 값도 검증 가능한 입력으로 전달한다.

Supabase는 기본 플랫폼으로 적극 사용한다. 포트의 목적은 업무 규칙을 이해하고 수정하고 독립적으로 테스트할 수 있게 하는 것이다. 가상의 여러 DB 지원을 위해 인터페이스를 늘리지 않는다.

## 4. 일관성과 실패의 의미를 명시한다

함께 성공해야 하는 변경은 하나의 로컬 DB 트랜잭션으로 확정한다. 시간이 오래 걸리거나 재시도가 필요한 후속 처리는 큐로 분리한다. 원본 변경과 필수 작업 등록은 함께 확정하며, 접수와 실제 완료는 구분한다.

중복 실행을 막는 멱등성, 오래된 값의 덮어쓰기를 막는 충돌 검사, 과거 사실을 남기는 이력은 서로 다른 목적을 가진다. 해당 문제가 있는 작업에 필요한 장치를 적용한다. 외부 서비스 부수효과의 실패·재시도·복구는 각 작업 계약에서 정한다.

## 5. 데이터 정본과 수명을 분명히 한다

도메인 데이터는 목적별 모델과 저장 구조를 가진다. 일반 내용은 현재값을 편집하고, 과거 상태가 실제로 필요한 데이터에만 이력을 둔다. 검색 색인 같은 파생 데이터는 원본과 구분하며 원본에서 다시 만들 수 있어야 한다.

할 일과 수행 기록, 도메인의 현재값과 당시 결과 기록은 각자의 의미와 수명을 가진다. 관련 객체의 삭제·정정이 다른 데이터를 보존하는지, 연결만 해제하는지, 작업 자체를 거부하는지 해당 기능의 계약에서 정한다. 같은 사실을 서로 독립적으로 편집하는 두 정본으로 만들지 않는다.

## 6. 도메인별로 구성하고 실제 필요에서 공통화한다

관련 모델·유스케이스·포트를 기능별로 가까이 둔다. 작은 기능은 타입과 함수로 시작하고, 실제 여러 사용처의 공통성이 확인되면 추출한다. 범용 payload 저장소, 명령 엔진, 모든 도메인에 강제하는 이력 체계를 선행 구축하지 않는다.

새 추상화에는 이를 사용하는 구체적인 기능과 줄어드는 중복이 있어야 한다. 새 도메인을 추가할 때 기존 모든 기능을 함께 수정해야 한다면 경계를 다시 검토한다.

## 7. 에이전트 지침과 서버 보장을 구분한다

에이전트용 배포 단위는 MCP 연결과 제품 스킬을 함께 담는 플러그인이다. 기능을 추가할 때 서버 도구 계약과 플러그인의 작업 안내를 함께 검토한다. 패키지가 통합되어도 서버 실행과 에이전트 지침의 책임은 구분한다.

제품용 스킬은 자료 탐색·결과 정리·도구 사용 순서를 안내한다. MCP 도구 계약은 실제 입력·출력·부수효과를 설명한다. 권한·업무 규칙·데이터 일관성은 서버가 강제한다. 스킬을 따르는지에 따라 데이터 보호 수준이 달라져서는 안 된다.

개발용 AGENTS.md, 제품용 스킬, 사용자가 저장하는 판단 기준은 별도 책임이다. 특정 클라이언트의 스킬 지원을 모든 MCP 클라이언트의 기본 능력으로 가정하지 않는다.

## 8. 보장하는 경계에서 검증한다

도메인 규칙은 DB 없이 테스트한다. 저장·권한·트랜잭션·경쟁은 실제 격리 DB에서, HTTP/MCP 계약은 진입점에서, 사용자 흐름은 웹과 MCP를 연결해서 확인한다. 모의 구현의 성공만으로 실제 저장이나 권한 보장이 검증됐다고 판단하지 않는다.

아키텍처의 완료 기준은 폴더 형태가 아니라, 업무 규칙을 독립적으로 검증하고 여러 진입점에서 일관되게 실행할 수 있는가이다.
