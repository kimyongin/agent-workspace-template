# 통합 기록 도메인 설계와 구현 인계

## 상태와 정본

2026-10-05 대화에서 합의한 모델이다. [PRD](../product/concept.md)와 [ADR-0012](../adr/0012-current-state-and-unified-records.md)가 의미를 소유하며, 현재 소스·통합·실제 서비스 검증의 상태는 [통합 실행 명세 #120](https://github.com/kimyongin/agent-workspace-template/issues/120)의 하위 티켓·PR 증거가 관리한다. 이전 #110·#111은 2026-10-06 대체된 계획으로 종료했다. 설계 중간의 불변 로그·정정 체인·강제 snapshot 및 기존 활동의 두 목록 동시 조율 제안은 최종 결정이 아니다.

## 책임

| 개념 | 정본과 책임 |
| --- | --- |
| 엔터티 | 도메인 앱의 업무 대상과 최신 속성 |
| 할 일 | 예정된 행동·현재 수행 상태·반복 규칙과 회차 |
| 원칙 | 현재 판단 기준 문서 0~1개 |
| 일반 기록 | 직접 작성 자료와 수행 결과의 편집 가능한 최신 내용 |
| 로그성 기록 | 업무 사건의 식별정보와 편집 가능한 설명 메모 |
| 활동 | 통합 기록을 읽는 관점. 별도 업무 객체·탭·ID 없음 |

RAG은 기록에서 과거 근거를 찾고, 최신 연락처·상태·원칙은 해당 도메인의 조회로 확인한다. 기록이 현재 값의 대체 정본이 되지 않는다. 같은 기록 형식 안에서 자료/수행 결과/업무 사건의 의미를 구분할 수 있지만 전체/부분 메모에 별도 모드를 요구하지 않는다.

## 관계와 동작

- 엔터티 관련 정확한 목록과 필터에는 선택적 다중 대상 식별을 사용한다. 모든 본문 언급을 자동 관계로 만들지 않는다.
- 할 일의 참고 자료는 본문 인용/링크로 충분하다. 명시적 참고 목록이 필요해지면 기능 근거를 먼저 확인한다. 수행 결과 식별정보와 반복 회차 연결은 상태 판정에 사용하며 참고만으로 완료 처리하지 않는다.
- 원칙 참고는 정말 필요할 때 본문에 설명한다. 기존 적용 원칙 배열이나 snapshot을 새 쓰기 계약의 필수 관계로 유지하지 않는다.
- 업무 대상이 삭제돼도 관련 기록의 당시 문맥은 남긴다. 식별정보로 현재 대상을 확인할 수 없으면 삭제/접근 불가를 표현한다. 기록의 내용으로 최초 원본 전체 상태를 복원할 수 있다고 주장하지 않는다.
- 일반 기록 편집과 로그 메모 편집은 추가 로그를 만들지 않는다. 로그의 사건 정보는 바꾸지 않으며 메모 수정으로 원래 업무 상태를 되돌리지 않는다. 수행 결과 연결/삭제의 상태 규칙은 기존 일회성·반복 계약을 별도 검증한다.
- 기본 메모 자동 완성은 저장 전이다. 예: 고객 이름 변경 사실을 채우고 사용자가 오타 수정 이유를 보충한다. UI와 에이전트 도구가 같은 업무 계약을 사용한다. 외부 요약 모델 호출은 이 합의의 필수 조건이 아니다.
- 원칙 수정은 현재 값을 갱신하고 변경 메모를 기록한다. 이전 원칙을 별도 활성 후보로 유지·자동 승격하지 않는다. 동시성 토큰은 삭제/재생성에서도 과거 요청을 잘못 수락하지 않도록 설계한다.

## 화면과 module

상위 탐색은 엔터티 / 할 일 / 기록 / 원칙 네 탭이다. 할 일은 현재 업무 관리, 기록은 모든 업무 자료·결과·변경 메모의 조회/검색이다. 기록의 직접 작성·편집은 같은 탭의 폼/모달에서 제공한다. 로그도 메모 편집을 제공하되 사건 필드는 읽기 전용이다. 조회·검색·화면 이동을 사용 로그로 수집하지 않는다.

첫 목록 설계의 두 층 선택은 역할 분리 원칙으로 활용한다. 공통 목록 module은 요청 취소·응답 수락·페이지/복원·검색 metadata를 관리하고, 화면별 조율은 해당 화면 module이 맡는다. 결과와 검색 안내는 같은 응답 세대에서 수락한다. 새 할 일/기록 화면에는 이전 두 목록의 sibling readiness를 강제하지 않는다. 상세 편집은 일반 기록과 로그 메모의 허용 입력을 구분하고 기존 초안·요청키·충돌·초점 보호를 재사용한다.

## 구현 인계와 검증

기존 리팩터링 후보를 독립 과제로 실행하지 않는다. 제품 목표를 구현하는 각 티켓에서 필요한 구조 개선을 함께 수행한다. 기능 티켓은 저장·공통 업무 계약·HTTP/MCP·화면·검증을 사용자 행동 하나로 묶으며, 앱 내부 호출자를 함께 전환하고 실제 사용처가 없는 구 계약은 제거한다. 호환의 유지·종료는 [구 계약 정리 기준](principles.md#9-실제-사용처를-기준으로-구-계약을-정리한다)을 따른다.

| 사용자에게 제공할 변화 | 담당 티켓 |
| --- | --- |
| 제품 목표와 도메인 합의를 정본 문서에 반영 | [#121](https://github.com/kimyongin/agent-workspace-template/issues/121), 이전 #118과 PR #119 문서 초안 포함 |
| 일반 기록과 로그 메모를 추가 로그 없이 편집 | [#129](https://github.com/kimyongin/agent-workspace-template/issues/129) |
| 업무 변경 전 기본 메모를 확인하고 변경과 함께 저장 | [#130](https://github.com/kimyongin/agent-workspace-template/issues/130) |
| 현재 원칙 하나와 과거 근거의 통합 기록 | [#131](https://github.com/kimyongin/agent-workspace-template/issues/131) |
| 할 일·일반 기록의 선택적 다중 엔터티 대상 | [#132](https://github.com/kimyongin/agent-workspace-template/issues/132) |
| 네 탭에서 최신 업무와 통합 기록 탐색 | [#133](https://github.com/kimyongin/agent-workspace-template/issues/133) |
| 기존 자료 보존과 이전 호출자 전환 후 호환 종료 | [#134](https://github.com/kimyongin/agent-workspace-template/issues/134) |

제품 스킬의 새 세션 업무 준비는 #122, 요청 범위의 변경 실행과 결과 확인은 #123이 담당한다. 이 티켓들은 도메인 저장 기능을 다시 구현하지 않는다. #134는 알려진 소비자와 외부 호환 조건을 구분해 계약을 정리한다. 웹·에이전트 실제 교차 사용 검증은 #124, 별도 프로젝트 초기화는 #125, 선택한 고객 관리 도메인의 전환과 독립 서비스 검증은 #127·#128이 담당한다. #126에는 고객 전화번호·이메일·상담 일정과 상담 내역 기록의 요구를 반영한다. 보류는 해제했으며 계정·외부 연동·운영 실행 조건은 별도 확인한다. 정확한 선행 관계와 최신 상태는 #120의 GitHub 하위 이슈·차단 관계를 따른다.

과거 원칙·적용 snapshot·기존 관계는 격리된 자료 이관 dry-run에서 보존을 검증한다. 과거 미기록 사실이나 당시 원문을 만들어내지 않으며 실제 운영 이관은 별도 실행 범위다.

### 기본 메모와 호환 전환의 인계

엔터티·할 일의 저장 전 미리보기는 현재 소유자의 자료와 버전으로 확인 가능한 사실을 읽어 제목·요약·본문의 기본 메모를 만든다. 최종 메모는 실제 변경과 같은 트랜잭션에 저장한다. 미리보기 응답은 저장 완료가 아니며, 실패·무변경·동일 요청 재시도에는 추가 성공 기록을 만들지 않는다. 할 일 완료와 회차 수행은 그 결과 기록 하나의 제목·요약·본문을 메모로 사용하며 별도 변경 기록을 중복 생성하지 않는다. 기존 `change_note`만 받는 호출의 이유도 기본 메모 본문에 포함해 RAG에서 읽을 수 있게 한다.

#130의 호환 확장에서는 기존 `ChangeContext` 등 읽기 소비자를 위해 사건의 `before`/`after` 자료를 유지했다. 새 변경 기록은 사건 식별정보·대상 문맥·최종 메모를 보존한다. 저장 전 미리보기와 기본 메모 생성에는 내부의 최신 변경 전후 값을 계속 사용한다. 이미 저장된 캡처는 보존하고 새 조회 계약으로 읽을 수 있게 한다. 누락된 이력을 만들어내거나 snapshot/diff 선택·정정 체인을 추가하지 않는다. 구 계약 정리와 혼합 버전의 처리 기준은 [릴리스 계약](../deployment/release.md#통합-기록-계약과-혼합-버전)을 따른다.

백엔드는 기존 공통 업무 interface와 격리 DB에서 소유자 격리·원자성·실패 rollback·동일 요청·원칙 동시성·다중 대상·로그 없는 기록 편집·색인 최신화를 검증한다. 원칙 적용 관계를 보존하는 과거 테스트는 새 의미와 이관 보존 검사로 변경한다. 프론트는 기존 브라우저 fixture에서 늦은 응답/검색 안내·필터·초안·저장 후 GET 실패·반응형·초점을 확인한다. 실제 DB/API/MCP 및 화면 연동은 fixture 결과와 구분한다.

물리적 DDL·도구/경로 이름·이관 명령·filter DTO와 상세 구현 순서는 구현 티켓에서 작성한다. 사용자 결정을 새로 요구하는 범위 변경이 생기면 구체적인 변경안을 제시한다. 현재 설계만으로 운영 이관·배포·비용이 드는 호출을 수행하지 않는다.
