# 제품 요구사항(PRD) — 에이전트 워크스페이스 템플릿

- 소유: 사람 ([ADR-0008](../adr/0008-document-ownership.md)). 에이전트는 변경안을 제안하고 사람이 승인한다.
- 갱신: 2026-10-06
- 목표/구현 구분: 아래 통합 기록 모델과 제품 성공 기준은 대화에서 합의한 목표다. 앱 전환과 제품 검증은 [통합 실행 명세 #120](https://github.com/kimyongin/agent-workspace-template/issues/120)의 하위 티켓에서 진행하며 아직 구현하지 않았다. 이전 #110·#111은 대체된 계획으로 종료했다.

## 어떤 템플릿인가

같은 핵심 컨셉을 공유하는 여러 도메인 앱을 쉽게 만드는 **구현형 템플릿**이다. 사람과 외부 에이전트가 같은 데이터와 업무 기능을 사용하고, 업무 과정에서 쌓인 계획·활동·원칙을 다음 판단에 활용한다.

저장소를 복제하고 서비스 설정을 연결한 뒤 도메인 엔터티의 속성·업무 규칙·화면·제품 스킬을 조정하면 새 앱으로 쓸 수 있어야 한다. 일반적인 데이터 관리는 속성과 화면 변경 중심으로 시작하고, 고유한 계산·상태 전환은 정해진 확장 위치에 추가한다. 이 템플릿은 에이전트와 함께 작업하는 초보자도 사용할 수 있어야 한다.

## 대상 사용자와 해결하는 문제

| 대상 | 설명 |
| --- | --- |
| 템플릿으로 앱을 만드는 사람 | 개발 에이전트와 함께 업무 앱을 만들려는 초보 개발자와 비개발자. 무엇을 왜 만들지 정하고 중요한 결정을 승인하며, 구현은 개발 에이전트에게 맡긴다 |
| 만들어진 앱을 쓰는 사람 | 자신의 할 일·기록·판단 기준을 쌓고 웹 화면과 AI 에이전트로 업무를 이어 가는 개인 사용자 |

| 문제 | 이 템플릿의 해결 |
| --- | --- |
| 해 둔 일과 결과가 흩어져 다음 판단에 쓰이지 않는다 | 한 일을 제목·요약·본문으로 기록하고, 다음 업무에서 검색해 원문을 확인한다 |
| 사람이 쓰는 앱과 AI 에이전트가 쓰는 도구가 따로 놀아 데이터와 결과가 어긋난다 | 웹 앱과 에이전트 플러그인이 같은 업무 기능과 데이터를 쓴다 |
| 업무 분야가 바뀔 때마다 로그인·할 일·기록·검색 같은 기본 기능을 처음부터 만든다 | 저장소를 복제하고 업무 대상과 화면·제품 스킬만 바꿔 새 앱을 시작한다 |

## 제품의 세 가지 성공 기준

세 목표는 모두 중요하며 하나를 선택하거나 다른 목표를 제외하지 않는다. 아래는 2026-10-05 제품 목표 논의에서 합의한 기준이며 아직 검증 완료를 뜻하지 않는다. 구현·검증 명세와 후속 작업은 [#120](https://github.com/kimyongin/agent-workspace-template/issues/120)에서 연결한다.

| 목표 | 성공한 모습 |
| --- | --- |
| 업무의 연속성 | 새 대화나 다른 에이전트에서도 최신 상태와 과거 근거를 찾아 업무를 이어간다. 사용자가 필요한 자료를 하나씩 모아 전달하지 않아도 된다 |
| 업무 관리의 편의성 | 엔터티·할 일·기록·원칙의 핵심 조회와 변경을 웹과 에이전트 양쪽에서 같은 규칙으로 수행한다. 한쪽에서 만든 데이터를 다른 쪽에서 이어서 사용하며, 에이전트에게는 도구 이름·검색 방식·태그 대신 업무 의도로 요청한다 |
| 새 앱 제작의 용이성 | 비개발자가 업무를 설명하고 중요한 결정을 내리면 개발 에이전트가 필요한 질문·설계·코드/화면/제품 스킬 변경·검증을 진행한다. 사람이 직접 해야 하는 계정 연결·비밀값 입력 등은 안내하고, 독립 서비스 설정·배포 후 실제 로그인과 웹/에이전트 업무 수행까지 검증한다 |

업무 연속성의 설명용 예시는 “이 고객의 다음 상담을 준비해줘”라는 요청이다. 에이전트는 고객의 최신 정보·관련 할 일·현재 원칙을 확인하고, 과거 상담 기록을 검색해 필요한 원문을 읽은 뒤 준비안을 제시한다. 이 예시는 검증 앱을 고객 관리로 선택했다는 뜻이 아니다.

- 조회와 준비안 작성은 요청 안에서 수행하되, 저장은 사용자가 요청한 범위에서 수행한다. “준비하고 기록해줘”처럼 저장까지 지시했다면 같은 행동의 승인을 다시 요구하지 않는다.
- 자료가 부족하거나 서로 다르면 확인된 사실과 불확실한 내용을 구분하고 가능한 부분을 진행한다. 결과를 크게 바꿀 정보만 사용자에게 질문한다. 검색 장애·색인 지연과 실제 자료 부재를 구분한다.
- 웹과 에이전트의 상호작용 방식은 각 접점에 맞게 구성하되 핵심 업무의 권한·규칙·결과는 같아야 한다.
- 템플릿 완성은 교체 지침이나 로컬 동작만으로 판정하지 않는다. 별도 프로젝트에서 실제 다른 도메인으로 업무 대상·속성·규칙·화면·제품 스킬을 바꾸고, 독립된 서비스 설정·배포·실제 로그인·웹/에이전트 업무와 공통 기능 유지까지 검증한다. 검증 앱·업무 범위·외부 연동 여부와 대상·도메인별 검증 시나리오는 미정이다. 이 기준의 합의는 즉시 새 앱을 제작하거나 운영에 배포하거나 비용을 발생시키라는 실행 지시가 아니다.

### 공통 검증 기준

| 검증 장면 | 통과 기준 |
| --- | --- |
| 기존 대화를 전달하지 않은 새 대화에서 업무 요청 | 에이전트가 필요한 최신 상태·현재 원칙·관련 과거 기록을 직접 찾아 업무를 이어간다 |
| 과거 자료를 활용한 준비안 또는 판단 | 필요한 원문을 확인하고 사용자가 참고 자료를 다시 열어볼 수 있다 |
| 자료 누락·내용 충돌·검색 장애 | 사실과 불확실성을 구분하고 가능한 작업을 진행하며 중요한 정보만 질문한다. 장애·지연을 자료 없음으로 단정하지 않는다 |
| 준비만 요청 / 저장까지 요청 | 준비만 요청하면 데이터를 변경하지 않는다. 저장까지 요청하면 해당 범위에서 실행하고 실제 반영을 확인한다 |
| 웹에서 만든 데이터를 에이전트가 변경하고 다시 웹에서 확인 | 핵심 업무의 결과·권한·규칙이 같고 접점을 바꿔도 작업을 이어간다 |
| 도구 이름이나 검색 절차를 지정하지 않은 업무 요청 | 제품 스킬이 필요한 도구·조회·검색·원문 확인 절차를 안내하고 에이전트가 수행한다 |
| 비개발자의 업무 요구로 별도 앱 제작 | 개발 에이전트가 설계·변경·검증을 진행하고 사람에게 필요한 결정과 직접 수행할 설정을 안내한다 |
| 새 도메인과 독립 서비스로 실제 사용 | 업무 대상·속성·규칙·화면·제품 스킬이 양쪽 접점에 일관되게 반영되고 공통 기능이 유지된다. 배포 후 실제 로그인과 웹/에이전트 업무 수행을 확인한다 |

검증의 실행 조건·자료·관측 결과와 미확인은 후속 검증 티켓에 남긴다. 위 기준은 제품의 목표이며 현재 앱이나 새 도메인 교체 검증이 완료됐다는 주장이 아니다.

## 필수 기본 기능

다음은 선택 모듈이 아니라 모든 앱이 갖는 기본 기능이다. 구현 순서를 나누는 것은 이 기능을 제외한다는 뜻이 아니다.

| 기능 | 의미 |
| --- | --- |
| 할 일 | 앞으로 수행할 행동. 한 번 하는 일회성 할 일과 일정 규칙에 따라 되풀이하는 반복 할 일이 있다 |
| 기록 | 일반 업무 자료·수행 결과와 앱 전반의 업무 변경 메모를 같은 형식으로 남기고 한 화면에서 조회한다 |
| 사용자 원칙(principles) | 사용자당 현재 판단 기준 문서 0~1개. 과거 변경은 통합 기록에 남긴다 |
| 검색(RAG)과 원문 확인 | 통합 기록에서 과거 근거를 회수한다. 최신 업무 값은 해당 도메인의 조회로 확인한다 |
| 웹 앱과 에이전트 플러그인 | 같은 업무를 수행하는 두 사용자 접점 |

할 일과 기록의 관계·삭제 영향은 명확히 정하되 계획과 수행 결과를 하나의 상태로 취급하지 않는다.

### 최신 상태와 통합 기록

- 엔터티·할 일·원칙은 최신 값을 관리한다. 원칙은 사용자당 현재 문서 0~1개이며 수정은 최신 값 갱신, 삭제는 현재 문서 제거다. 과거 원칙을 별도 현재 후보로 승격하지 않는다.
- 과거 내용은 모든 도메인에 흩어진 저장본 대신 통합 기록의 메모로 회수한다. 메모에 전체 내용을 담을 수도 변경점만 담을 수도 있으며 별도 snapshot/diff 모드를 강제하지 않는다. 남기지 않은 과거 전체 내용을 재구성할 수 있다고 보장하지 않는다.
- 일반 기록은 편집 가능하며 그 편집의 추가 로그를 생성하지 않는다. 로그성 기록도 설명 메모는 편집 가능하고 추가 편집 로그를 생성하지 않는다. 사건 시각·대상·행동 등 식별정보는 유지한다. 불변 메모·정정 체인은 요구하지 않는다.
- 원칙 참고는 정말 필요할 때 기록 본문에 설명한다. 필수 원칙 입력이나 적용 원칙 연관키를 요구하지 않는다. 원칙 자체의 생성·수정·삭제는 업무 사건으로 기록한다.
- 할 일·일반 기록은 엔터티 여러 개에 선택적으로 연결할 수 있다. 관련 정확 조회에 쓰는 연결과 본문에 설명하는 배경을 구분한다. 참고 자료는 기본적으로 본문 인용/링크로 표현하며, 수행 결과/회차 관계와 구분한다.
- 대상 삭제 뒤에도 관련 기록의 당시 문맥은 보존한다. 최신 값은 해당 도메인 조회, 과거 내용·판단 근거는 기록 RAG으로 확인한다.

### 네 탭과 기록 화면

- 상위 탭은 엔터티 / 할 일 / 기록 / 원칙이다. 기록은 대화에서 말한 활동 화면과 같으며 별도 활동 탭이나 업무 객체를 만들지 않는다.
- 기록 화면은 자료·수행 결과·변경 메모의 읽기와 검색을 중심으로 하며, 작성·편집은 같은 탭의 폼/모달에서 제공한다.
- 등록·수정·삭제·수행 같은 업무 사건을 남긴다. 조회·검색·화면 이동 같은 사용 로그는 포함하지 않는다.

### 두 태그 사전

- 엔터티에는 엔터티 태그, 할 일과 기록에는 활동 태그를 사용한다. 두 사전의 이름·ID·연결 범위는 독립적이며 같은 이름을 각각 가질 수 있다.
- 원칙에는 태그가 없다. 관련 엔터티와 활동은 대상 연결로 찾으며 엔터티 태그를 활동 태그로 자동 복제하지 않는다.

### 변경 메모와 일관성

- 엔터티·할 일·원칙의 업무 변경은 확인 가능한 사실로 기본 메모를 저장 전에 자동 완성한다. 사용자/에이전트가 이유·근거·필요한 전체 내용을 보충·수정하고 업무 변경과 최종 메모를 함께 저장한다.
- 함께 성공해야 하는 변경과 필수 기록은 같은 트랜잭션에서 확정한다. 실패·무변경·동일 요청 재시도는 성공 기록을 중복 생성하지 않는다.
- 일반 기록 편집과 로그 메모 편집은 추가 로그를 만들지 않는다. 기록 편집으로 원래 업무 상태를 되돌리지 않으며, 편집 결과는 검색 색인에도 반영한다.
- 기록에 비밀값·인증 정보를 넣지 않는다. 필요한 사건 식별정보만 구조화하며 모든 서술을 연관키로 바꾸거나 별도 관계망을 만들지 않는다.
- 기존 원칙 저장본·적용 자료·단일 대상 관계는 기존 자료를 보존하는 이관안을 검증한 뒤 전환한다. 운영 실행은 별도 지시 범위다.

최신 결정은 [ADR-0012](../adr/0012-current-state-and-unified-records.md)와 [구현 인계](../architecture/unified-record-model.md)를 따른다. Template-19/20은 이전 세 탭·원칙 과거본 계약의 구현 근거이며 현재 목표와 구분한다.

### 일회성 할 일과 반복 할 일

- **일회성 할 일**은 수행하면 완료하고 그 결과를 기록으로 남긴다.
- **반복 할 일**은 매일, 매주(요일 선택), 매월(날짜 선택) 규칙으로 회차(날짜)가 정해진다. 앱이 정해진 시각에 작업을 자동 실행하거나 알림을 보내는 기능이 아니다.
- 반복 할 일의 회차에 연결된 기록이 하나 이상 있으면 그 회차를 수행한 것이고, 없으면 아직 하지 않은 일이다. 지난 회차에 기록이 없으면 하지 않은 회차로 표시한다.
- 한 회차에 기록을 여러 개 남길 수 있고 지난 회차에도 나중에 기록할 수 있다.
- 반복 할 일은 완료하지 않고 중단한다. 중단하면 이후 회차가 생기지 않고 기존 기록은 남는다. 중단한 반복 할 일은 다시 재개할 수 있다.

## 사람과 에이전트의 사용 방식

사람에게는 HTTP API를 사용하는 웹 앱을, 외부 에이전트에게는 MCP 연결과 제품 스킬을 함께 패키징한 플러그인을 제공한다. 서버에서 두 접점은 같은 유스케이스를 실행하므로 결과·권한·변경 범위가 같다([ADR-0001](../adr/0001-hexagonal-shared-usecases.md)).

앱은 데이터를 보관하고 권한과 업무 규칙에 따라 정확하게 조회·변경한다. 외부 에이전트는 자료를 읽고 해석하며 사용자 요청에 따라 작업한다. 앱 자체에 대화형 추론 엔진을 내장하지 않는다.

플러그인의 MCP 연결은 데이터 조회와 업무 실행 도구를, 제품 스킬은 어떤 자료를 먼저 찾고 원문을 어떻게 확인하며 결과를 어떻게 기록할지를 제공한다. 도구 접근과 업무 안내가 함께 제공되는 것이 기본 사용 경험이다. 지원 클라이언트는 Claude와 Codex다([ADR-0005](../adr/0005-plugin-delivery-claude-codex.md)).

사용자는 데이터 관리, 할 일 수행, 기록 확인을 웹과 에이전트 사이에서 이어갈 수 있어야 한다. 예를 들어 웹에서 만든 할 일을 에이전트가 읽고 결과를 저장하면, 웹에서 그 결과를 확인하고 다음 대화에서 다시 찾을 수 있다.

## 할 일과 기록이 지식이 되는 과정

```text
업무 계획 → 수행 → 결과 기록
                     ↓
새 질문 → 현재 원칙 조회·통합 기록 검색 → 원문 확인 → 외부 에이전트의 판단
                                                    ↓
                                             다음 작업과 기록
```

모델을 재학습시키는 대신 저장된 자료를 작업 시점에 회수한다. 기록할 때 핵심 의미를 짧은 요약에 담고 자세한 근거는 본문에 남긴다. 검색 방식은 [ADR-0004](../adr/0004-summary-single-vector-search.md)를 따른다.

검색 결과는 원본으로 이어져야 한다. 에이전트가 참고한 기록을 사람도 웹에서 열어 확인할 수 있어야 한다. 검색 결과 없음과 검색 장애·색인 지연을 구분해, 아직 찾지 못한 자료를 존재하지 않는 자료로 오해하지 않게 한다.

시간이 오래 걸리는 작업은 처리 중임을 알리고 결과가 준비되면 확인할 수 있게 한다. 작업 접수와 실제 완료를 구분하고, 실패한 작업은 확인하고 다시 처리할 수 있어야 한다.

## 기본 예제 엔터티

특정 도메인 대신 테이블 하나의 중립적인 예제 엔터티를 제공한다.

```text
Entity
  id
  prop1
  prop2
  ...
```

- `id`는 식별자이고 `prop1`·`prop2` 등은 같은 엔터티의 명시적인 속성·컬럼이다.
- 메인·서브 테이블이나 부모·자식 엔터티를 추가하지 않는다. 동적인 키–값 저장소나 범용 payload 저장소를 만드는 의미도 아니다.
- 기본 화면은 엔터티의 목록·상세·생성·편집을 제공하고, 엔터티 상세에서 관련 할 일·기록을 보고 이동할 수 있다. 원칙은 계정 전체의 현재 판단 기준이다.
- 새 앱에서는 엔터티와 속성의 이름·타입·검증, 화면과 제품 스킬을 변경한다.
- 기본 템플릿에는 홈카페·고객 관리 같은 특정 도메인 모델을 넣지 않는다.

예제 테이블 하나라는 범위는 도메인 교체용 예제에 한정된다. 인증·할 일·기록·원칙·검색에 필요한 공통 저장 구조는 별도로 유지한다. 속성의 타입·필수값·검증은 구현 티켓에서 정한다.

## 범위

| 구분 | 범위 |
| --- | --- |
| 템플릿 완성 범위 | 필수 기본 기능, 단일 예제 엔터티와 공통 화면, Claude·Codex 플러그인, 새 프로젝트 초기화·배포·운영 절차 |
| 첫 구현 범위 | 일회성 할 일 작성·조회·완료 결과 저장, 반복 할 일 작성·조회·회차 기록·중단·재개, 직접 기록 작성·조회, 검색과 원문 확인 |
| 이후 구현 범위 | 사용자 원칙 관리·적용, 태그 관리, 예제 엔터티, 도메인 전환 검증 |

첫 구현 범위와 이후 구현 범위는 순서일 뿐이며 모두 템플릿 완성에 필요하다. [Template-02](../tickets/template-02-implementation-base.md)는 초기 구현의 배경이며, 현재 구현 순서와 완료 기준은 [통합 실행 명세 #120](https://github.com/kimyongin/agent-workspace-template/issues/120)과 하위 티켓이 관리한다.
