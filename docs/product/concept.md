# 제품 컨셉

## 어떤 템플릿인가

사람과 외부 에이전트가 같은 데이터와 업무 기능을 사용하고, 업무 과정에서 쌓인 기록을 다음 판단에 활용하는 도메인 앱 템플릿이다.

사람에게는 HTTP API를 사용하는 웹 앱을, 외부 에이전트에게는 MCP 연결과 제품 스킬을 함께 패키징한 플러그인을 제공한다. 앱은 도메인 데이터, 할 일, 기록과 판단 기준을 관리한다. 연구·고객 관리·학습 등 새 프로젝트는 이 기반 위에 고유한 데이터와 업무 기능을 추가한다.

## 에이전트에게 제공하는 플러그인

플러그인은 앱의 기능과 사용 방법을 함께 전달하는 제품 단위다. MCP 연결은 데이터를 조회하고 업무를 실행할 수 있는 도구를 제공한다. 제품 스킬은 어떤 자료를 먼저 찾고, 원문을 어떻게 확인하며, 결과를 어떻게 정리하고 기록할지 안내한다. 설치 정보와 두 구성을 묶어 사용자가 연결한다.

예를 들어 사용자가 이전 작업을 검토해 달라고 요청하면 스킬이 관련 기록 탐색과 근거 확인을 안내하고, 에이전트가 MCP 도구로 실제 자료를 읽는다. 사용자 요청에 따라 수행한 작업의 결과도 같은 도구로 저장한다. 도구 접근과 업무 안내가 함께 제공되는 것이 기본 사용 경험이다.

여러 에이전트에 연결할 수 있도록 공통 MCP 계약과 제품 스킬의 내용을 유지하되, 패키지 형식·설치 방식·스킬 지원은 각 클라이언트에 맞춰 제공하고 검증한다. 동일 패키지 하나가 모든 클라이언트에서 동작한다고 가정하지 않는다.

## 앱과 에이전트의 역할

앱은 데이터를 보관하고, 권한과 업무 규칙에 따라 정확하게 조회·변경한다. 외부 에이전트는 필요한 자료를 읽고 해석하며, 사용자의 요청에 따라 작업을 수행한다. 앱 자체에 대화형 추론 엔진을 내장하는 것을 전제로 하지 않는다.

웹 앱과 에이전트 플러그인은 같은 업무를 수행하는 두 사용자 접점이다. 서버에서는 각각 HTTP와 MCP를 통해 같은 유스케이스를 실행하므로 결과·권한·변경 범위가 같아야 한다. MCP 단독 연결은 기술적 연동 경로이며, 스킬을 포함한 플러그인 사용 경험의 검증을 대신하지 않는다.

## 할 일과 기록이 지식이 되는 과정

할 일은 앞으로 수행할 행동이고, 기록은 실제 수행한 내용과 결과다. 사전에 할 일을 만들지 않아도 기록을 작성할 수 있다. 두 데이터의 관계와 삭제 영향은 명확히 정하되, 계획과 수행 결과를 하나의 상태로 취급하지 않는다.

쌓인 할 일과 기록은 다음 질문에 필요한 근거가 된다. 에이전트는 관련 자료를 검색하고 원문을 읽어 추론에 활용한다. 이것이 이 템플릿의 RAG 활용 방식이다. 모델을 재학습시키는 대신 저장된 자료를 작업 시점에 회수한다.

```text
업무 계획 → 수행 → 결과 기록
                     ↓
새 질문 → 관련 자료 검색 → 원문 확인 → 외부 에이전트의 판단
                                          ↓
                                   다음 작업과 기록
```

검색 결과는 원본으로 이어져야 한다. 에이전트가 참고한 기록을 사람도 웹에서 열어 확인할 수 있어야 한다. 검색 결과가 없다는 사실과 검색 장애·색인 지연을 구분해, 아직 찾지 못한 자료를 존재하지 않는 자료로 오해하지 않게 한다.

## 사용 경험의 원칙

사용자는 데이터 관리, 할 일 수행, 기록 확인을 웹과 에이전트 사이에서 이어갈 수 있어야 한다. 예를 들어 웹에서 만든 할 일을 에이전트가 읽고 결과를 저장하면, 웹에서 그 결과를 확인하고 다음 대화에서 다시 찾을 수 있다.

시간이 오래 걸리는 작업은 처리 중임을 알리고 결과가 준비되면 확인할 수 있게 한다. 검색 색인, 대량 데이터 가져오기, 파일 변환 등이 그 예다. 작업 접수와 실제 완료를 구분하고, 실패한 작업은 확인하고 다시 처리할 수 있어야 한다. 이 예시들이 모두 초기 구현 범위에 포함되는 것은 아니다.

## 기본 범위와 확장

| 구분 | 범위 |
| --- | --- |
| 공통 기능의 목표 | 할 일·기록·판단 기준·태그·검색, 웹 앱과 MCP·스킬 통합 플러그인 |
| 첫 구현 범위 | 할 일 작성·조회·완료 결과 저장·직접 기록 작성·검색·원문 확인 |
| 후속 공통 기능 | 판단 기준, 태그 관리, 반복 일정의 구체적 범위 확정과 구현 |
| 도메인 확장 | 고객·연구 등 실제 업무 모델과 목적별 기능 |
| 요구가 있을 때 추가 | 공유·첨부·실시간 갱신 등 별도 권한과 사용 흐름이 필요한 기능 |

공통 기능을 모두 갖춘 뒤에야 새 앱을 만들 수 있도록 설계하지 않는다. 첫 사용자 흐름을 완성하고 필요한 기능을 순차적으로 확장한다. 현재 구현 상태와 미정 사항은 [시작 문서](../START-HERE.md)와 [첫 기능 티켓](../tickets/template-01-task-record-search.md)에서 관리한다.

코드 구성의 기준은 [코드 설계 원칙](../architecture/principles.md), 구체적인 실행 구조와 Supabase 활용은 [아키텍처](../architecture/hexagonal-review.md)를 따른다.
