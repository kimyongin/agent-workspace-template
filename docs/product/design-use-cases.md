# 설계 검토용 대표 사용 사례

## 목적과 적용 범위

2026-10-22 사용자 대화에서 설계 변경의 방향성을 검토할 때 다시 대입할 대표 사례를 보존하기로 합의했다. 여러 시스템에서 온 자료를 사용자가 정의한 업무 구조 안에서 구분하고 연결하는 장면을 중심으로 한다.

이 문서는 제품 목표의 배경과 설계 검토 사례를 소유한다. 확정된 기능·식별·변경·복원 정책은 [PRD](concept.md), 중요한 구조 결정은 [ADR](../adr/README.md), 구현 범위와 검증 증거는 GitHub Issues·PR이 소유한다. 사례에 등장하는 자료 종류·식별자 종류·관계 이름은 예시이며 제품 기본값이나 외부 플랫폼의 실제 API 계약을 뜻하지 않는다.

아래 커머스 사례를 첫 검토 사례로 삼되 템플릿을 커머스 전용 제품으로 제한하지 않는다. PRD에서 선택한 고객 관리 검증 앱을 대체하거나 새 도메인의 구현·외부 연동·운영 실행을 승인하는 문서도 아니다.

## 설계가 해결하려는 업무

사용자는 자료 종류와 입력 항목을 정의하고, 식별자가 어느 체계에서 온 값인지와 어떤 항목으로 자료를 유일하게 구분할지를 설정한다. 사람과 외부 에이전트는 같은 자료·업무 규칙을 사용한다.

- 같은 문자열도 식별자 종류가 다르면 다른 의미를 가진다. 상품 번호와 주문 번호, 서로 다른 플랫폼의 번호를 문자열만으로 합치지 않는다.
- 한 자료에 제조사 품번·공급사 품번·바코드 등 여러 식별자를 보관할 수 있다. 자료의 정체성을 결정하는 항목과 일반 식별자 항목의 역할은 구분한다.
- 같은 식별자가 어떤 자료 종류에서는 고유한 값이고 다른 자료 종류의 일반 항목에서는 반복되는 참고 값일 수 있다.
- 서로 다른 자료가 업무상 같은 대상을 가리키는 관계는 명시적으로 설정한다. 식별값이 같다는 이유로 자동 병합하거나 자동 연결하지 않는다.
- 일반적인 자료 정의·입력·조회·연결은 설정으로 표현하고, 고유한 계산·상태 전환은 템플릿의 정해진 확장 위치에서 구현한다. 자료 정의만으로 모든 도메인 업무가 완성된다고 가정하지 않는다.

## 대표 사례: 다채널 상품·주문 관리

### 업무 장면과 자료 모델

한 상품을 여러 마켓에 등록하고 주문을 처리하는 사용자가 있다고 가정한다. 자체 SKU, 마켓 등록 상품, 주문, 주문품목, 배송을 별도 자료 종류로 정의한다.

| 자료 종류 | 자료 식별자 예시 | 함께 보관할 정보·일반 식별자 예시 | 명시적인 자료 관계 예시 |
| --- | --- | --- | --- |
| 자체 SKU | 사내 상품 식별자와 `SKU-001` | 제조사 품번·공급사 품번·바코드 | 하나의 SKU에 여러 마켓 등록 상품 연결 |
| 마켓 등록 상품 | 쿠팡 상품 식별자 또는 네이버 상품 식별자와 원본 값 | 판매명·판매 상태·플랫폼에서 제공한 다른 식별자 | 자체 SKU, 해당 상품을 주문한 주문품목 연결 |
| 주문 | 쿠팡 주문 식별자 또는 네이버 주문 식별자와 원본 값 | 주문 시각·주문 상태 | 주문품목·배송 연결 |
| 주문품목 | 앱에서 자동 발급한 식별자 | 수량·주문 시점 가격·플랫폼 상품 식별자 | 소속 주문·마켓 등록 상품 연결 |
| 배송 | 관리 대상 배송을 구분하는 식별자 | 운송장 번호 등 참고 식별자 | 해당 주문 연결 |

이 관계 목록은 예시다. 플랫폼의 실제 상품/옵션 구조, 주문·배송의 분할/묶음, 관계의 단일/복수는 구체 도메인의 요구를 확인해 정의한다.

### 설계를 대입할 구체 장면

1. **같은 문자열, 다른 체계:** 마켓 등록 상품 A는 `쿠팡 상품 식별자 + "00123"`, B는 `네이버 상품 식별자 + "00123"`을 사용한다. 같은 자료 종류 안에서도 둘을 별개로 등록할 수 있어야 한다. A와 같은 종류·값으로 별도 상품을 등록하면 중복으로 거절해야 한다. `"123"`은 `"00123"`과 구분한다.
2. **같은 출처, 다른 식별자 종류:** 한 플랫폼이 서로 다른 번호 체계를 제공하고 이를 같은 자료 종류에서 사용해야 하는 장면을 가정한다. 출처와 문자열이 같아도 식별자 종류가 다르면 충돌하지 않아야 한다. 실제 플랫폼이 어떤 체계를 제공하는지는 별도 확인한다.
3. **한 상품, 여러 등록 건:** 두 마켓 등록 상품을 같은 자체 SKU에 연결한다. 등록 상품은 각각의 식별자와 상태를 가진 별도 자료로 유지한다. SKU 연결을 해제해도 상대 자료 자체를 삭제하지 않는다.
4. **여러 식별자와 반복 값:** 자체 SKU에 제조사 품번과 공급사 품번을 함께 보관한다. 같은 마켓 상품을 가리키는 상품 식별자는 여러 주문품목의 일반 식별자 항목에 반복될 수 있다. 각 주문품목의 자료 식별자는 별도로 유지한다. 참고 식별자 저장과 실제 자료 연결은 별도 동작이다.
5. **자료의 연속성:** 등록 상품의 이름이나 상태를 편집한 뒤에도 주문품목과 기록이 같은 상품을 가리켜야 한다. 자료 식별자 수정·삭제·복원의 허용 정책은 [항목 기반 식별자](concept.md#항목-기반-식별자)를 따른다. 삭제 후 같은 식별자로 별도 자료를 만들어 기존 연결과 기록을 조용히 승계하지 않는다.
6. **사람과 에이전트의 왕복:** 웹에서 등록 상품과 주문품목을 연결한 뒤 에이전트가 해당 상품의 주문품목을 확인한다. 에이전트는 워크스페이스·자료 종류·식별자 종류를 구분하고 현재 권한 안에서 조회한다. 에이전트가 요청받은 변경을 수행하면 웹에서도 같은 결과와 연결을 확인할 수 있어야 한다.

### 실제 도메인을 정할 때 확인할 식별 범위

플랫폼에서 발급한 번호가 플랫폼 전체, 판매자 계정, 상점, 다른 상위 자료 중 어디에서 유일한지 확인해야 한다. 판매자 A와 B가 같은 번호를 쓸 수 있다면 플랫폼 이름과 문자열만으로는 구분할 수 없다.

이 사례 문서는 계정 범위를 식별자 종류에 포함할지, 별도 범위로 모델링할지 결정하지 않는다. 실제 발급 범위를 확인한 뒤 제품 요구와 참조·중복 계약을 함께 검토하며, 확인 전에는 플랫폼 전체 유일성을 가정하지 않는다.

## 다른 도메인에 대입할 사례

| 도메인 | 자료 예시 | 확인할 설계 성질 |
| --- | --- | --- |
| 구매·부품 관리 | 부품·공급사 등록 품목·발주·발주품목 | 사내·제조사·공급사 품번을 구분하고 같은 부품에 대한 공급사별 자료를 명시 연결할 수 있는가 |
| 제조·재고 관리 | 품목·생산 로트·개별 제품·입출고 | 품목 번호·로트 번호·제조번호의 의미와 유일성 범위를 구분하고 자료 사이 관계를 표현할 수 있는가 |
| 물류·자산 관리 | 배송·운송장·장비·자산 | 관리 대상의 정체성과 외부 참고 식별자를 구분하고 외부 번호만으로 자동 연결하지 않는가 |

이는 모델을 검토할 후보 사례이며 해당 도메인의 전용 계산·규정·업무 흐름이 구현돼 있다는 뜻은 아니다.

## 설계 변경을 검토할 때의 질문

관련 설계를 바꿀 때 해당 장면을 골라 변경 전후의 동작을 설명한다. 사례와 맞지 않으면 그 원인이 사례의 가정인지, 변경하려는 정책인지, 실제 구현의 제약인지 구분한다. 제품 목표를 바꾸는 결정은 PRD·ADR에 반영하고 구현·검증 결과는 해당 이슈에 남긴다.

| 검토 질문 | 사례에서 확인할 결과 |
| --- | --- |
| 같은 문자열을 서로 다른 체계에서 사용해도 구분되는가? | 다른 종류의 `"00123"`이 충돌하지 않고 원본 값이 보존된다 |
| 고유한 자료 식별자와 반복 가능한 일반 식별자가 구분되는가? | 상품의 중복 등록은 막고 여러 주문품목의 참고 상품 식별자는 허용한다 |
| 출처만으로 구분되지 않는 번호 체계나 계정 범위를 설명할 수 있는가? | 같은 출처의 다른 종류를 구분하고 실제 발급 범위의 미확인을 드러낸다 |
| 자료 사이의 동일성·연결을 임의 추정하지 않는가? | 마켓 등록 상품은 별도 자료로 유지하고 SKU·주문품목과는 명시 관계로 연결한다 |
| 변경·삭제·복원 뒤에도 자료의 연속성을 설명할 수 있는가? | 기존 연결·기록의 대상과 새 자료 등록·기존 자료 복원이 혼동되지 않는다 |
| 설정 변경과 정의 교환 뒤에도 같은 업무 의미가 유지되는가? | 이름 변경·복사·가져오기에서 식별자 종류의 정체성과 참조 대응을 이름만으로 추정하지 않는다 |
| 웹과 에이전트가 같은 결과를 얻는가? | 같은 공간·대상·권한·입력에 동일한 업무 규칙을 적용한다 |
| 다른 도메인도 기본 구조로 표현할 수 있는가? | 커머스의 자료 이름이나 전용 정책을 템플릿 기본 구조에 고정하지 않는다 |

관련 기능 설계와 구현 범위는 [식별자 항목 #543](https://github.com/kimyongin/agent-workspace-template/issues/543), 기존 자료 관계·모델 교환 결정은 [ADR-0024](../adr/0024-entity-relations-and-data-model.md)에서 확인한다. 이 문서의 사례를 읽거나 검토한 것만으로 실제 기능 검증을 완료했다고 기록하지 않는다.
