# 도메인 앱 설계·개발·운영

## 작업의 시작

이 스킬은 저장소와 함께 사용하는 개발 지침이다. 아래 상대 링크는 이 파일 기준이며 저장소 루트는 세 단계 위다. 다른 checkout에서 작업하면 그 checkout의 AGENTS.md와 docs를 정본으로 사용한다. 전역 경로·원본 프로젝트 이름·설치된 특정 플러그인에 의존하지 않는다.

1. 사용자가 요청한 결과, 대상 프로젝트와 환경, 이미 승인한 변경 범위를 확인한다. 현재 디렉토리만으로 운영 대상을 추정하지 않는다.
2. [문서 시작점](../../../docs/START-HERE.md)과 관련 기능 티켓을 읽고 실제 파일·Git branch/commit·작업 변경을 확인한다. 문서의 제안 트리와 실제 구현을 구분한다. 기존 사용자 작업을 보존한다.
3. 아래 표에서 현재 작업에 필요한 문서만 읽는다. 문서 전체를 매번 읽거나 내용을 스킬에 복제하지 않는다. 링크가 없어졌다면 대상 저장소에서 정본을 찾고, 핵심 계약을 확인할 수 없으면 그 결정만 사용자에게 확인한다.
4. 필요한 런타임·Docker·브라우저·네트워크·연결 도구를 작업 범위에 맞춰 확인한다. 플러그인 접근 권한과 CLI 자격 증명은 별개다. 명령은 실제 package/config/CI와 도움말에서 찾으며 문서의 예시를 실행 가능한 명령으로 간주하지 않는다.

| PR·머지·배포 | [PR·리뷰 규칙](../../../docs/development/workflow.md), [배포 방법](../../../docs/deployment/release.md) | 작은 PR, 머지 조건 충족 시 머지, 요청한 배포 단계의 실제 결과·revision |
| 운영 점검·장애·복구 | [운영 방법](../../../docs/operations/runbook.md), 보안, 실제 배포 기록 | 영향·원인·실행 조치·복구 증거·남은 작업 |

여러 요청이 섞이면 필요한 결과를 순서대로 연결한다. 스킬 이름이나 모드 선택을 사용자에게 반복해서 요구하지 않는다. 배정·재개 때 [모델과 추론 강도 정책](../../../docs/development/workflow.md#모델과-추론-강도-선택갱신)과 [갱신 가능한 선택표](../../../docs/development/agent-models.json)를 읽고 [배정 preflight와 재개 경로](../../../docs/development/agent-model-execution.md)로 개발일 조회·선택·지원과 실행 가능성을 확인한다. 이 스킬에 공급자 모델명을 영구 정본으로 고정하지 않는다. 선택 모델/추론 강도를 명시 인자로 전달하며 preflight만으로 기존 세션의 설정이 바뀌었다고 주장하지 않는다. 변경 적용을 지원하지 않는 재개는 정본의 새 세션 인계를 따른다.

설계·배정을 진행하거나 구현을 이어받을 때는 [세션 배정과 인계](../../../docs/development/workflow.md#세션-배정과-인계)와 [티켓 인계 필드](../../../docs/tickets/README.md#인계와-작업-배정)를 따른다. 사람과 본 세션이 설계·결정하고 구현 세션은 합의 안의 상세 구조를 정한다. 본 세션이 범위·의존성·통합·최종 리뷰/CI·머지를 조정하며 새 세션에 전달한 작업도 기존 승인 범위 안에서 수행한다.

배정·중요 변화·결과 인계의 사용자 보고는 [세션 운영 브리핑](../../../docs/development/workflow.md#세션-운영-브리핑)을 따르고 근거는 [티켓 실행 기록](../../../docs/tickets/README.md#세션-실행-기록)에 연결한다. 명시 배정과 실제 실행 확인을 구분하며 리뷰어 인계는 독립 리뷰 규칙을 유지한다.

## 프로젝트와 함께 바꾸는 지침

템플릿의 문서와 이 스킬은 도메인 앱을 시작하는 초기 기준이다. PRD·ADR은 사람이 소유하고 가이드·티켓·스킬은 에이전트가 소유한다([ADR-0008](../../../docs/adr/0008-document-ownership.md)). 이름·범위·기술 선택처럼 PRD·ADR에 속하는 변경은 변경안을 만들어 사람의 승인을 받는다. 가이드와 이 스킬의 절차는 PRD·ADR 안에서 직접 발전시킨다.

변경마다 관련 PRD·ADR·계약·가이드·스킬과의 충돌을 확인한다. [개발 방법](../../../docs/development/workflow.md)의 기준에 따라 구현 오류, 일반 기준의 변경, 제한된 예외를 구분한다. 일반적인 새 방향이면 해당 정본·관련 개발/제품 스킬·소비 코드·테스트를 같은 작업에서 갱신한다. 단순히 한 곳의 조건문이나 예외 문구를 추가하고 끝내지 않는다.

예외는 조건과 이유가 한정된 경우에만 범위·재검토 조건을 남긴다. 영향 분석 결과 수정이 필요한 곳만 다루고, 단계적 전환은 남은 대상과 종료 조건을 명시한다. 문서 충돌 자체를 별도 승인 사유로 삼지 않으며 실제 사용자 요청·권한·미정 결정에 따라 판단한다. 리뷰와 인계에도 구현과 현재 지침의 일치 여부를 포함한다.

## 설계와 구현의 경계

설계 요청은 검토 가능한 문서와 티켓으로 완성한다. 현재 시나리오, 변경 데이터와 정본, 불변 조건, HTTP/MCP 행위·필드·오류, 비동기 완료 의미, 검증 기준과 미정 결정을 적는다. 필요한 문서의 담당 위치에 반영하고 다른 문서는 링크로 연결한다.

되돌리기 비싼 기술 가정은 앱 코드 전에 [기술 실험](../../../docs/development/workflow.md#기술-실험) 규칙에 따라 `experiments/`에서 작게 시험하고 결과를 티켓에 남긴다.

설계의 일반적인 “계속”을 앱 구현이나 운영 배포 지시로 확대하지 않는다. 사용자가 구현을 요청했다면 확정 계약 안의 배치·함수명 같은 일상 판단은 직접 해결한다. 미정인 권한·업무 의미를 조용히 만들지 말고 해당 계약을 정리한다. 기존 승인을 반복 확인하지 않는다.

결정과 상세 기준은 아래 정본에 있으며 이 스킬에 다시 적지 않는다. 작업 전에 해당 행의 문서를 읽는다.

구현 순서:

1. 기능 하나에 필요한 DB·공통 유스케이스·HTTP/MCP·웹 화면·제품 스킬·테스트를 함께 연결한다. 공통 기반에는 즉시 사용할 기능과 종료 조건을 둔다.
2. 도구 schema·설명과 제품 스킬의 안내를 같은 변경에서 맞춘다. 개발 스킬은 제품 패키지에 넣지 않는다.

보안·디자인의 상세 수치와 플랫폼 API는 정본 문서와 실제 버전에 맞춰 확인한다. 관련 전문 스킬/공식 도구가 있으면 활용하되 특정 설치를 필수 전제로 만들지 않는다.

## 리뷰·검증·인계

리뷰 요청에서는 발견 사항을 먼저 제시하고 구현 요청이 없다면 코드를 수정하지 않는다. 계약 위반·권한 누출·부분 저장·중복 처리·플러그인 불일치처럼 실제 영향을 설명한다. 문제가 확인되지 않으면 그 사실과 검사 범위를 적고 형식적인 지적을 만들지 않는다.

검증은 위험이 발생하는 경계에서 한다. 도메인은 단위, 저장·권한·경쟁은 격리 DB, HTTP/MCP는 실제 진입점, 웹은 영향받는 E2E, 플러그인은 패키지 검사와 실제 지원 클라이언트 행동으로 확인한다. 공통 UI의 여러 화면 변경은 전체 E2E를 따른다. 인코딩·링크·diff 검사를 문서 변경에도 적용한다.

필드·필터와 화면 복원 변경은 [기능 계약과 교차 검증](../../../docs/development/workflow.md#기능-계약과-교차-검증), 초기화·공유 환경·실패 후 재실행은 [검증 환경과 증거](../../../docs/development/workflow.md#검증-환경과-증거)를 적용한다. 절차의 상세를 이 스킬이나 인계 대화에 복제하지 않는다.

실행할 수 없는 필수 검사는 정확한 revision·명령·환경·데이터 조건과 함께 CI 또는 가능한 격리 환경으로 인계한다. 운영 DB를 시험 대상으로 바꾸지 않는다. 모의 테스트·빌드·패키지 설치를 실제 DB·보안·스킬 행동 검증의 대체 증거로 쓰지 않는다.

해당 기능 티켓에 변경 계약·실행 명령·결과·미검증 항목·다음 작업을 기록하고 [변경과 완료 기록](../../../docs/development/workflow.md#변경과-완료-기록)에 따라 시작 문서·티켓 요약·체크박스를 맞춘다. 구현·자동 검증·머지·배포·실클라이언트 완료를 각각 보고한다. 알려진 환경 제약을 숨기고 완료로 표시하지 않는다.

## 배포와 운영의 실행 범위

변경은 `main`에 직접 푸시하지 않고 [PR·리뷰 규칙](../../../docs/development/workflow.md)에 따라 작은 PR로 올린다. [머지 조건](../../../docs/development/workflow.md#머지)을 충족하면 머지한다. 머지만으로 서비스 배포를 시작하지 않으며, 머지가 배포 workflow를 실행하는지도 확인한다. 단순 Git 작업 때문에 새 모델 선택을 요구하지 않는다.

배포 요청은 대상 환경·검증 revision·실제 workflow·비밀 설정 위치·복구 artifact를 확인하고 배포 문서의 호환 순서를 적용한다. 플러그인은 패키지 식별자·버전·연결 대상·서버 호환성을 별도로 기록한다. 이미 승인된 대상·범위를 재확인하지 않되, 대상이 불명확하면 읽기 전용 준비를 마친 뒤 필요한 정보만 묻는다.

운영 점검은 우선 로그·큐 상태·최근 배포·영향 범위를 읽어 원인을 좁힌다. 승인된 장애 복구 범위에서 필요한 조치를 수행한다. 단순 조회 요청을 데이터 복원·큐 삭제·자격 증명 폐기로 확대하지 않는다. 고위험 조치의 승인 범위가 부족하면 실행 대상·영향·복구 방법을 구체화한 뒤 승인받는다.

재처리는 실패 원인·원본/권한/버전·중복 부수효과를 확인한 후 제한된 양부터 수행한다. 같은 실패가 반복되거나 영향이 확대되면 재시도를 멈추고 증거를 남겨 다음 조치를 판단한다. 큐 비우기를 성공으로 간주하지 않는다. 반복 점검·알림 예약은 사용자가 요청했을 때만 설정한다.
