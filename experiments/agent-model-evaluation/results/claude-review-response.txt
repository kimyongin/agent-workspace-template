**Finding 1 — Missing ownership check (access control bypass)**
- **File/line:** `review.mjs:3–5`
- **Defect:** After `db.get`, there is no check `if (actorId !== task.ownerId) throw new Error('forbidden')`. Any authenticated actor can complete any task regardless of ownership.
- **Impact:** Complete violation of the owner-only contract. Any actor ID passes through unchallenged.
- **Test:** Call `completeTask(db, 'attacker', taskOwnedBy('victim'), rev)` → expect `'forbidden'` thrown, but currently resolves successfully.

---

**Finding 2 — Stale-revision check precedes the write but does not guard it (TOCTOU / lost update)**
- **File/line:** `review.mjs:5–6`
- **Defect:** The conflict check (`task.revision !== expectedRevision`) is a plain in-memory comparison performed before the write. Because `db.update` has no conditional/CAS predicate and there is no transaction, a concurrent writer can increment the revision between line 5 and line 6. The stale check then silently passes and the newer value is overwritten.
- **Impact:** Concurrent updates are lost; the "stale expectedRevision must never overwrite" contract is violated.
- **Test:** Interleave two calls that both read `revision = 1`; the first write bumps it to `2`, the second write (also expecting `1`) still passes the check and overwrites with `revision = 2` again, discarding the first writer's changes.

---

**Finding 3 — Non-atomic status update and activity append (partial commit)**
- **File/line:** `review.mjs:6–7`
- **Defect:** `db.update` and `db.appendActivity` are two independent, sequential awaits with no rollback logic. If `db.appendActivity` rejects (network error, constraint violation, etc.), the task row already has `status: 'done'` / incremented revision, but no activity record exists. There is no compensating write (e.g. reverting status) and no transaction wrapping them.
- **Impact:** The system enters an inconsistent state: the task is marked done but the audit trail has no `'completed'` entry. The contract "status and completed activity commit atomically or neither commits" is broken.
- **Test:** Inject a `db.appendActivity` that throws; verify the task row is still `status: 'done'` (i.e. the partial write persisted) while no activity record was created.

---

**Finding 4 — Return value exposes stale snapshot, not the persisted new revision**
- **File/line:** `review.mjs:8`
- **Defect:** The function returns `{ ...task, status: 'done' }` where `task` is the value fetched at line 3 — it has the **old** `revision`. The contract requires returning the **persisted new revision** (`task.revision + 1`), but that incremented value is only sent to `db.update`; it is never included in the return object.
- **Impact:** Every caller receives stale revision metadata. If they use it as the next `expectedRevision`, they will immediately get a `'conflict'` error on the next operation. Callers that store or display the revision will show incorrect data.
- **Test:** Call `completeTask(db, owner, id, 1)` where the stored revision is `1`; assert `result.revision === 2`. Currently `result.revision === 1`.
