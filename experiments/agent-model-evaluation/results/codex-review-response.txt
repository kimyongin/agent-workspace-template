- **Stale-revision race (lost update)** — `review.mjs:5-6`
  Revision is checked before an unconditional `db.update`. Two callers can both read revision `N`, pass line 5, and each update independently. A stale completion can overwrite a concurrent update because `update` has no version predicate.
  Test: pause both requests after `get`; let another writer update the task to revision `N+1`; resume completion with expected `N`; expect conflict and no overwrite. Also run two completions concurrently with expected `N`; at most one should succeed.

- **Status/activity are not atomic** — `review.mjs:6-7`
  Independent calls allow partial commits: `update` may succeed and `appendActivity` fail, leaving a completed task with no completion activity. Conversely, there is no transaction guaranteeing all-or-nothing behavior under failures.
  Test: make `appendActivity` throw after a successful `update`; expect both task status/revision and activity log to remain unchanged. Verify the inverse failure path as applicable.
